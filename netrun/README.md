# netrun — проект Godot (VR-клиент, сервер мира, плоская сборка)

Один проект Godot, три сборки (docs/netrun.md, «Сервер мира и клиент»). Рендерер — Mobile.

## Версии (закреплены на сезон)

- **Godot 4.7.2-stable** (из docs/netrun-vr-hardware.md). Шаблоны экспорта — той же версии; на машине разработки их может не быть,
  экспорт APK проверяет CI (задача G1).
- **gdUnit4 6.2.1** — лежит в `addons/gdUnit4` (источник: github.com/MikeSchulze/gdUnit4, тег v6.2.1). Проверен на Godot 4.7.2.
  Обновлять только осознанно, вместе с версией Godot.
- **OpenXR Vendors 5.1.0** — пока НЕ добавлен. Понадобится, если потребуется passthrough на Pico (П4) или вендорские
  расширения; требует Gradle-сборку и один вендор на шаблон экспорта. Для MVP на стандартном OpenXR не нужен.
- Очки — обычная Pico 4 (стандартный OpenXR).

## Pico 4: известные ограничения (проверено на очках 2026-10-04)

Очки: Pico 4, PICO OS 5.13.7, рантайм OpenXR Pico(XRT) 3.0.1. Установка, запуск, журналы — `tools/pico.sh`; стенд с очками на
devbox — docs/netrun-devbox.md, «Очки Pico 4 по USB».

- **`xr/openxr/foveation_eye_tracked=false`** (project.godot; комментарий в файле не живёт — редактор его переписывает). С этим
  расширением (Godot 4.7 запрашивает его по умолчанию на Vulkan/Mobile) процесс падает сразу после строки
  `OpenXR: Running on OpenXR runtime`, до GDScript: SIGSEGV, fault addr 0x4020, поток VkThread, верхние кадры — системный
  `XRRuntime.apk`, под ними вызов `xrGetSystemProperties` из `OpenXRAPI::get_system_info`. Рантайм объявляет `XR_META_foveation_eye_tracked`,
  а айтрекера у Pico 4 нет: godotengine/godot#115744, настройка — PR #117868 (Godot 4.7-dev4+). На очках: без настройки — падение,
  с ней — клиент работает (`start mode=client`, `xr enabled=true`). `foveation_with_subsampled_images` не трогаем: при
  `foveation_level` 0 (по умолчанию) не действует. Включать расширение снова — только с прошивкой Pico, где это исправлено, и после проверки на очках.
- **APK очков собирается без `server/` и `tests/`** (exclude_filter пресета). Глобальный `class_name` оттуда в коде клиента экспорт не
  замечает, а на очках это ошибка разбора: так `main.gd` (ссылки на `WorldServer`, `BotClient`) не грузился. Сервер и бота `main.gd`
  грузит по пути; сторож — `tests/client_export_test.gd`.
- **Адрес и токен — файл `netrun.cfg`** (`NetConfig.from_sources`), без пересборки APK: у каждых очков свой токен терминала.
  Кладётся с devbox/Mac одной командой, пока очки подключены по USB (или по `adb connect`):
  `PICO_SERIAL=<serial> netrun/tools/pico.sh provision --host=10.10.0.10 --token=t03:<секрет>` (токен можно и переменной `NETRUN_TOKEN`,
  чтобы он не попал в историю shell). `provision --show` показывает файл (секрет скрыт), `provision --reset` удаляет.
  Файл — во внешнем каталоге приложения `/sdcard/Android/data/com.megablok10.netrun/files/netrun.cfg`: `adb push` пишет туда в любой
  сборке, приложение читает без разрешений. Запасной путь — `user://netrun.cfg` (`run-as` в отладочной сборке). **`adb uninstall`
  стирает файл** (`install -r` — нет): после смены подписи APK `provision` повторить. Клиент читает файл при старте; в журнале
  строка `net.config file=… host=… terminal=t03 token=set` (сам токен в журнал не пишется, в `args` запуска его тоже скрывает),
  неверное поле — `net.config.warn`, нет токена — `net.skip reason=no_token looked=<пути>`. Аргументы (`--host=`, `--port=`, `--token=`)
  перекрывают поля файла; в пресете `command_line/extra_args` адрес и токен больше не нужны (годится для сборки на ПК и отладки).
  Почему не `am start --esa`: Godot 4.7 снимает `command_line_params` у экспортированной активности (`GodotAppLauncher`), а
  неэкспортированную `GodotApp` оболочка adb не запускает — аргументы до игры не доходят (`args=""`).
- **Граница.** Нет границы (`GuardianSystem::Failed to init Boundary` в logcat) — рантайм открывает поверх приложения её настройку
  (`com.pvr.seethrough.setting`), приложение через ~1 с встаёт на паузу, XR-сессия остаётся IDLE, до связи дело не доходит
  (`app.pause`). Нужен человек в очках: задать границу (сидячую), потом запуск.
- **Режим рук.** Контроллеры спят, включено отслеживание рук — система приложение не запускает («vr app is not support hand mode»),
  показывает диалог: взять контроллер.
- **Подпись.** APK из CI и локальный экспорт подписаны разными ключами отладки: `adb install -r` поверх отказывает
  (`INSTALL_FAILED_UPDATE_INCOMPATIBLE`), на очках остаётся старая сборка. Сначала `adb uninstall com.megablok10.netrun`.

## Структура

- `main.tscn`, `main.gd` — точка входа, выбирает режим.
- OpenXR включён только на Android (`openxr/enabled.android` в project.godot): плоская сборка и сервер его не поднимают. Риг — `client/xr_rig.tscn`, математика — `shared/rig_math.gd`. На ПК с рантаймом OpenXR: `-- --client --xr-mode on`.
- `shared/` — код, общий для сервера и клиента (в т.ч. `run_mode.gd` — выбор режима).
- `shared/breach/` — движок взлома деки (порт мини-игры телефона, docs/netrun-deck-design.md §3, §7.4, §10): `BreachRules` (строка/столбец, совпадение, исход),
  `BreachGrid.generate` (решаемая сетка, ловушки вне пути), `BreachAttempt`, `BreachRun` (таймер, события реплик ICE; фабрики `for_storage` / `for_charge` /
  `for_decrypt`), `BreachAutoSolver` (боты). Числа и реплики — `data/rules/breach.json` (выгружает Kotlin-тест `:rules`), клетка — `Vector2i(строка, столбец)`.
  Тесты `tests/breach_*_test.gd`; golden от Kotlin (`tests/fixtures/breach_golden.json`) проигрывает `breach_golden_test.gd`.
- `server/node/vault_breach.gd` — взлом хранилищ на узле (К3); клиент — `client/ui/breach_panel.gd`, `breach_cell.gd`, копия попытки `shared/breach/breach_mirror.gd`.
- `server/` — сервер мира. `client/` — клиент Pico 4 и плоская сборка. `tests/` — тесты gdUnit4.
- `export_presets.cfg` — пресеты: «Client Pico 4 (Android)» (OpenXR, arm64), «Server (dedicated)» (метка `dedicated_server`),
  «Flat debug (Linux)». Ключ подписи Android в репозиторий не кладём (в CI — ключ отладки).

## 3D-ассеты

`assets/models/<группа>/*.glb` — модели для Pico 4 в стиле Blackwall (Cyberpunk 2077): свет в линиях и точках, поверхности чёрные. Окружение (env), предметы (props),
существа (ice: Soft и Black ICE с клипами), аватар (avatar), дека на запястье и жетоны демонов (deck). **Канон и все правила — `assets/ARCHITECTURE.md`**
(принципы, координаты, роли материалов, каталог модулей, проверки, бюджеты, решения владельца), стиль — `assets/STYLE.md`, каталог и числа —
`assets/models/MANIFEST.md`. `.glb` несут только форму и цвета вершин: вид (аддитивность, свечение, дыхание штрихов, тир, шрам ICE, отражение в полу)
делают шейдеры `assets/shaders/*.gdshader`, которые подставляет `AssetMaterials.apply` (`assets/asset_materials.gd`); `client/node_assets.gd` вызывает его
при создании каждой модели. Тир узла — параметр материала окружения (путь модуля от тира не зависит).

Исходники — Blender-скрипты `assets/src/*.py` (Blender запускается только на devbox). Сборка, проверка и кадры — `assets/tools/pipeline.sh`
(`build` собирает все ассеты на devbox и проверяет их `assets/src/validate.py`, `shots`, `demo`, `fps`); кадры настоящей сцены клиента —
`assets/preview_node.tscn` (отдельным процессом Godot на дисплее devbox, см. комментарий в `preview_node.gd`). `validate.py` — чистый Python по самим
`.glb` (бюджеты, роли, размеры, origin), CI гоняет его отдельным шагом; импорт, клипы, метки и посадку на сетку проверяет `tests/assets_models_test.gd`.
Файлы `.glb.import` лежат в git (стабильные uid); после смены `.glb` — `godot --headless --path netrun --import`.

## Руки

`client/hand_view.gd` (`HandView`, по одному на руку, дети `XRRig`) рисует руки игрока облаком светящихся точек: поза от контроллера (курок и хват сгибают пальцы) или от трекинга рук (`XRHandTracker`,
если он есть). Скелет и кинематика — `shared/hand_skeleton.gd`, шейдер — `assets/shaders/hand_particles.gdshader`, калибровка grip — `comfort.cfg` (`hand_pitch_deg`, `hand_offset_x/y/z`). Подробности и
что не проверено на очках — `assets/ARCHITECTURE.md`, п. 15. Кадры без очков: `assets/preview_hands.tscn` (на devbox, отдельным процессом Godot на дисплее).

## Узел в ассетах (A3)

Клиент рисует узел готовыми моделями: `client/node_view.gd` (`NodeView`) собирает комнату и предметы по описанию сервера, `client/node_assets.gd` даёт
пути и одевает модели шейдерами (тир узла из graph.json — BASE, HARD или NIGHTMARE — красит окружение, файлы одни на все тиры), `client/ice_view.gd` — ICE, `client/avatar_view.gd` —
чужие нетраннеры; сцена-оркестратор — `client/rig_test_scene.gd`. Сервер без графики и ассетов не читает.

- **Комната.** 8x8 ячеек по 2 м (`NodeLayout.cell_center`): пол, потолок на 5 м, стены по периметру, четыре угла с колонной, колонны-укрытия (`NodeLayout.PILLARS`),
  площадка выхода из четырёх помостов, за южной стеной две двери выхода (`EXIT_DOORS`) и два кольца цифрового тоннеля. Повторяющиеся модули — один
  `MultiMesh` на модуль и вариант (пол, потолок и стены в трёх вариантах: узор не повторяется), у стен, углов, дверей и колонн ещё зеркальный `MultiMesh` — отражение в полу.
  Вокруг комнаты — дальний план: «пласты данных» (наш и такие же выше и ниже на 7 м) из участков 11 м (`far_field`, `far_floor`, `far_ceiling`).
- **Предметы.** `vault_open` / `vault_closed` на слоте шарда (шард лежит / слот пуст), над ним вращается и парит `shard` (`shard_encrypted`, если слот
  помечен `enc`); `portal` на слоте портала, `portal_locked` — когда узел назначения в локдауне (`open: false` или отказ `portal_denied` / lockdown) и пока
  за игроком идёт охота Black ICE (поле `hunt` снимка state); `lockdown_gate` вместо дверей при уровне trace LOCKDOWN (сервер выход при этом не закрывает —
  это сигнал среды); `seat` в точке входа, `sensor` у западной стены (голова качается), `dead_deck` из поля `dead` события node (сервер его пока не шлёт).
- **ICE.** Клип выбирается по состоянию из снимка (`IceView.clip_for`): Soft — patrol / idle (подозрение стоит) / patrol быстрее (поиск); Black — idle,
  hunt (поиск и охота), catch (охота вплотную к игроку). Над головой знак: «?» подозревает, «!» ищет, «!!» охотится (цвет модели состояние не передаёт).
- **Аватары.** `avatar/runner` с неоном под номер игрока (девять оттенков), лицом по ходу движения (сервер шлёт только позицию).
- **Сетка (A3).** Раньше слоты стояли на рёбрах и вершинах ячеек, а площадка портала r = 1,5 м у слотов (−7; −6) и (4; −13) заходила за стену на ~0,7 м.
  Теперь `SPAWN` (−1; −1), `SHARD_SLOTS` (−1; −9), (−5; −13), (5; −13), `PORTAL_SLOTS` (−5; −1), (−5; −9), (3; −9) — центры ячеек, не ближе 1 м к стене
  (площадки порталов — не ближе 1,7 м); `EXIT_POS` (4; 0) — вершина четырёх ячеек (четыре помоста вписывают круг r = 2). Аватар на сервере появляется
  в `SPAWN`, риг клиента стоит там же. Проверка — `tests/node_layout_test.gd`, сборка сцены — `tests/node_scene_test.gd`.
- **Бюджет.** Самый тяжёлый узел (NIGHTMARE, три хранилища, три портала, мёртвая дека, три ICE, девять чужих аватаров) — около 19 тыс. треугольников при
  потолке 100 тыс.; число вызовов отрисовки — в `docs/netrun-stage1-results-flat.md` (замер в окне).

## Управление: телепорт и поворот при телепорте

Решения владельца (4 октября 2026, после теста на Pico 4): ходьба стиком и рывок 30° отменены — слишком укачивают. Движение — только
телепортом. Позже в тот же вечер на Pico 4 выяснилось, что плавный поворот стиком тоже укачивает, а поворот самим игроком — нет, и поворот
стиком убран: по умолчанию `turn_mode = none`, поворачивается сам игрок (вертящееся кресло), а развернуться сильнее помогает поворот
при телепорте (ниже). Плавный и рывковый поворот остались настройками. Код: `client/xr_rig.gd` (`XRRig.drive` — один шаг по готовому вводу, его же зовут тесты), чистая математика —
`shared/rig_math.gd`, прицел — `client/ui/teleport_aim.gd`, затемнение (моргание и виньетка в одном квадрате с шейдером, без постобработки) —
`client/ui/comfort_fx.gd`.

- **VR.** Телепорт и поворот — **один правый стик**. Отклонил за порог 0,7 в любую сторону и держишь — дуга-прицел от правого контроллера
  (поза `aim`, `RightAim` в `xr_rig.tscn`; нет данных позы — от руки) и кольцо на полу: зелёное — можно, красное — нельзя или перезарядка
  (на кольце растёт индикатор). Рядом со стрелкой на полу видно, куда будешь смотреть после прыжка: стрелка **плавно** разворачивается
  вслед за положением стика относительно текущего взгляда (вверх — не менять, вправо/влево — ровно 90°, вниз — 180°, между ними — промежуточные
  углы; 8° у «вверх» — без поворота; слабее 0,6 угол не читается; `RigMath.facing_deg`). Вернул стик к центру (ниже 0,3 дольше 0,05 с) —
  телепорт: экран темнеет 0,1 с, в самой тёмной точке риг переезжает и поворачивается вокруг головы на выбранный угол (`XRRig._step_blink`),
  проявляется 0,1 с; берётся последнее положение «держу», а не путь стика к центру. Нажатие стика (`primary_click`) — отмена; отмена,
  отказ клиента или сервера поворот отменяют. Мир на глазах не вращается. Вращение мира левым стиком по X (`turn_mode = smooth`: плавно
  вокруг головы, 60°/с, разгон 0,25 с, остановка 0,2 с, виньетка по краям до 45 %; `snap`: рывок 30°) — только по настройке. Захват (grip) и
  удержание выхода (menu) — как раньше. Во время цифрового тоннеля (`XRRig.movement_locked`) телепорт запрещён (прицела нет).
- **Плоская сборка** (разработка и боты): T зажата — прицел по взгляду в пол (ПКМ + мышь — наклон взгляда), отпустить — телепорт, C — отмена;
  при зажатой T Q/E выбирают поворот при телепорте (∓90°); WASD — только с `--walk`; плавный или рывковый поворот стиком — `--turn=smooth` или `--turn=snap`.
- **Правила.** Дальность `TELEPORT_RANGE` = 4 м по полу (от риг-а, не от руки), перезарядка `TELEPORT_COOLDOWN` = 1,2 с, цель внутри комнаты
  (`NodeLayout.clamp_to_room`), прицел «в себя» (< 0,25 м) телепорт не запрашивает. Луч руки вниз — пересечение с полом (рука должна быть
  выше пола не меньше чем на 0,2 м), горизонтальный и выше — дальняя точка по горизонтали. `TELEPORT_TRACE` = 0 — задел под шум телепорта, не используется.
- **Сервер решает** (`NetServer._handle_teleport`, сообщение `WorldMsg.TELEPORT` `{t: tp, p: [x, z]}`): сессия с аватаром, не тоннель,
  цель в комнате, расстояние от позиции аватара ≤ предел + 0,5 м (поза клиента запаздывает), с прошлого телепорта ≥ предел перезарядки − 0,2 с.
  Пределы сервера (`RigMath.TELEPORT_RANGE_LIMIT` = 6 м, `TELEPORT_COOLDOWN_LIMIT` = 0,6 с) выше значений по умолчанию, чтобы настройка на очках
  могла их менять, но не обходить; клиент никогда не доверяется. Успех: аватар в точке, база предела скорости потока поз (`_pos_time_ms`) сбрасывается,
  в журнал сервера `teleport ok`. Отказ — `{t: tp_no, reason: range|cooldown|tunnel|room, p: [x, z], left}`, клиент возвращает риг на позицию
  сервера (с морганием; если затемнение ещё не дошло до переноса — переноса не будет вовсе). Поток поз и предел скорости (8 м/с) остаются.
- **Чужие аватары.** В `av` у записи аватара, который прыгал, 4-й элемент — счётчик скачков (`NetServer.avatar_entry`). `StateBuffer` не
  интерполирует и не экстраполирует между снимками с разным счётчиком: аватар стоит на старом месте и прыгает на новое, не «ползёт»; потеря
  пакета скачок не прячет (счётчик в каждом пакете). Перенос сервером (`NetServer.teleport`, переход через портал) тоже считается скачком.
- **Боты** (`tests/bot/bot_client.gd`) двигаются прыжками по тем же правилам: не дальше `RigMath.TELEPORT_RANGE`, пауза `HOP_PAUSE` (перезарядка + 0,05 с);
  осторожный путь EXPOSED_RUN — короткими прыжками. Круги LOITER — прыжками по точкам круга (дуга не больше 0,8 рад).
- **Настройка без пересборки.** Необязательный `user://comfort.cfg` (`client/comfort_config.gd`, секция `[comfort]`): `turn_mode` (`none` | `smooth` | `snap`),
  `turn_speed_deg_s` (10…120), `turn_vignette` (0…0,8), `turn_ramp_up_s`, `turn_ramp_down_s` (0,05…2), `teleport_range` (1…6), `teleport_cooldown`
  (0,6…10), `teleport_blink_s` (0,03…0,4; каждая половина моргания). Нет файла — значения из кода; неверное поле — значение по умолчанию и
  `comfort.warn` в журнале; всё ограничено пределами (серверными для телепорта). На очках — `tools/pico.sh tune ключ=значение …`
  (правит файл, перезапускает приложение, печатает строку `comfort` из журнала; `tune --reset` — удалить файл). Адрес сервера и токен через
  файл не передаются. Значения по умолчанию: поворот none (стик мир не вращает; числа smooth — 60°/с, разгон 0,25 с, остановка 0,2 с, виньетка 0,45); телепорт 4 м, 1,2 с, моргание 0,1 + 0,1 с.
- **Замеры в журнале клиента** (для проверки на очках): `node.perf node=… tier=… build_ms=… first_frame_ms=… draws=… prims=… objects=…` при входе в
  узел (сборка комнаты, первая отрисовка — туда попадает первый показ шейдеров — и через 2 с вызовы отрисовки/примитивы/объекты в кадре),
  `perf frames=… avg_ms=… max_ms=… slow=… draws=… prims=… objects=…` раз в 10 с, `frame.slow ms=… limit_ms=17.36` — только кадр, пропустивший
  обновление экрана (`shared/frame_stats.gd`; раньше порог был ровно 1/72 с и срабатывал на каждом кадре при ровных 72 Гц).
- **Журнал клиента.** `comfort turn=… speed=… vignette=… ramp_up=… ramp_down=… range=… cooldown=… blink=… file=none|user walk=…` при старте;
  `rig.teleport from=x,z to=x,z dist=… ok=… face=…` на каждую попытку (face — поворот при телепорте, градусы вправо); `teleport.denied reason=… by=client|server` на отказ. Тесты: `rig_math_test.gd`
  (математика), `teleport_test.gd` (протокол и сервер), `teleport_client_test.gd` (управление), `teleport_proto_test.gd` (настоящий клиент),
  `comfort_config_test.gd`, `state_buffer_test.gd` (скачок), боты — `gray_node_test.gd`.
- **Не проверено без очков:** поза `aim` и совпадение дуги с указанием контроллера, высота пола относительно рук в сидячем режиме
  (`XR_PLAY_AREA_SITTING`, рука должна быть выше пола), читаемость прицела и виньетки, ощущения.

## Дека на руке: вкладки ДЕКА | ДОБЫЧА | ЧАТ | ЗВОНКИ

Решение владельца (4 октября 2026, `docs/netrun.md`): в очках на деке левой руки — мессенджер и звонки. **Очки — второй экран телефона**:
телефон остаётся в кармане включённым и хозяином личности, истории сообщений и WebRTC-звонка; дека показывает то, что он отдаёт, и передаёт
ему команды (ответить заготовкой, принять, отклонить, завершить, заглушить). **Голос звонка в очках** (микрофон и динамики Pico) — следующий
этап, здесь только интерфейс. По умолчанию это **прототип на фиктивных данных**: владелец оценивает ощущения и читаемость на Pico 4.

**Связь с телефоном.** По умолчанию — фиктивная (`FakePhoneLink`, сценарий по таймеру). Настоящая (`RemotePhoneLink`: очки слушают порт, телефон подключается
к ним, токен в `?token=`) включается аргументом `--phone=remote [--phone-port=7420] [--phone-token=…]` или секцией `[phone]` в `netrun.cfg` на очках
(`mode="remote"`, `port=7420`, `token="…"`); аргументы сильнее файла; `--phone=off` — только вкладка ДЕКА. Файл на очки кладёт
`netrun/tools/pico.sh provision --phone=remote --phone-token=…` (токен `--show` скрывает). С `remote` клиент играет звуки телефона (`PhoneSounds`)
и пишет в журнал `phone link=remote port=… token=set|none`, `phone.online online=… callsign=…`, `phone.sound kind=…` (токен — никогда).
Порт не поднялся (занят) — `phone.warn` («связь с телефоном не поднялась, показываю фиктивную») и фиктивная связь. Тесты: `phone_client_test.gd`.

- **ДЕКА** — вверху полоса RAM («занято/ёмкость», красная, если занято больше; метка «ПО УМОЛЧАНИЮ», пока Мост не прислал `session.data.ram` — тогда 6),
  ниже ПРОГРАММЫ: плашка на программу — имя, тир, состояние (готов / перезарядка N / активен N с / не работает в Сети) и вторая строка — цепочка
  кодов моноширинным 19 px (`DeckTheme.V_CODE`) и эффект словами (`HudLogic.EFFECT_TITLES`). Выбор и применение — левые X/Y (`rig_test_scene.gd`).
  Рабочие программы — только демоны с `origin: phone:*` (`GrayNode.deck_from_items`): добытый в узле демон — груз, он не работает и не занимает RAM.
  Данные: `ev deck` (`WorldMsg.EV_DECK`: ram, used, daemons, loot, eddies; шлётся при входе и после каждого взятого шарда) плюс `state.cd`
  с `st` (ready | cooldown | active | unsupported) и `until` (время сервера `k`); склеивает их `HudLogic.program_entries`.
- **ДОБЫЧА** — шарды, добытые демоны и эдди забега: вид (ШАРД / ДЕМОН), название, тир, метка ОТКРЫТ / ЗАШИФРОВАН.
  Вкладка появляется с первым `ev deck` (без сервера — как раньше, одна ДЕКА). Пусто — «Добычи пока нет». Снимки: `assets/preview_deck.tscn` (на devbox).
  Новая добыча (шард, положенный в деку) мигает в списке ~2,4 с; пока вкладку не открыли — на ней бейдж с числом нового и жёлтая полоска у строки.
- **Отправка добычи (К5б).** У строки шарда или демона из ГРУЗа — «ОТПРАВИТЬ» (у принесённого с телефона и защищённого кнопки нет: в строке `loot` поле
  `give`). Кнопка открывает выбор получателя (`DeckGive`): нетраннеры в Сети первыми (кто в том же узле — «ЗДЕСЬ», список приходит событием `give_list`
  на `{t: give_list}`), затем контакты телефона (`PhoneLink.contacts()` — [{key, title}]; у `FakePhoneLink` ключи придуманы, настоящий Мост такой ключ не
  примет, ответ `bad_contact`). Выбор → подтверждение с последствиями («вернуть нельзя») → `{t: give, item, to: {runner: id аватара} | {phone: ключ}}`.
  Сервер (`GiveService`, `server/node/give_service.gd`) проверяет, что предмет в ГРУЗе сессии и его можно отдать, что получатель в Сети и не в исходе,
  что ключ похож на ключ и не свой, и одной операцией `op.give_item` Моста (6.7) двигает ценность; повтор после обрыва безопасен (`rid` с версией
  предмета, предмет перечитывается). Исход забега отправителя и получателя ждёт отдачу в полёте. Ответ — событие `give`: отправителю `dir: out`
  (строка на ДОБЫЧЕ «ОТПРАВЛЕНО: … > …» либо «НЕ ОТПРАВЛЕНО: причина»), получателю-нетраннеру `dir: in` («ПОЛУЧЕНО от …», строка мигает,
  бейдж на вкладке, тихий тон и слабый импульс `DeckFeedback.loot_cue`). Отданный шард слота не возвращается на постамент после выхода отправителя.
  Тесты: `give_service_test.gd` (сервер), `deck_give_test.gd` (дека), `give_client_test.gd` (настоящий клиент, сеть и фейковый Мост).
- **Шард в руку и в деку (К5).** Grip рядом с хранилищем (0,4 м) берёт шард: сервер проверяет расстояние и вид хранилища. Правая рука с шардом у деки
  (ближе 20 см к её центру; рамка деки светится) + grip — шард «втягивается» (`shard_stowed`, строка `shard.stowed` в журнале); взятый левой рукой уходит в
  деку сразу; вдали от деки grip с шардом ничего не делает (бросать нельзя). Серверу об укладке сообщать нечего: предмет в деке Моста с момента grab. Вид
  хранилища — поле `vault` слотов (`ev node`, `ev shards`, для каждой сессии своё): `open` (парит шард, берётся), `closed` (шард внутри меньше и
  полупрозрачный, не берётся), `empty`; шард — `shard.glb` / `shard_encrypted.glb` по `enc` и подпись «ТИР n». Пока взлома нет, флаг графа
  `settings.vault_requires_open` выключен и лежащий шард открыт всем; К3 включил его по умолчанию (`"auto"`, см. «Взлом хранилища»).
- **Взлом хранилища (К3).** Шард в хранилище берётся только после взлома мини-игрой на панели в мире — тем же движком, что на телефоне
  (`shared/breach/`, правила и числа 1:1, docs/netrun-deck-design.md §3, §7). Сквозной путь:
  1. **Площадка.** Телепорт ближе `NodeLayout.VAULT_SNAP_RADIUS` (1,6 м) к хранилищу ставит риг на площадку в `VAULT_PAD_DIST` (0,85 м) перед ним и
     разворачивает взгляд к нему (`XRRig.teleport_snap` + `face_toward` в самой тёмной точке моргания); то же считает сервер (`NetServer.teleport_snap`,
     `NodeLayout.snap_to_vault_pad`) — клиенту не верим. С площадки и панель, и парящий шард в досягаемости сидя.
  2. **Панель.** `BreachPanel` (`client/ui/breach_panel.gd`): 48 × 32 см, SubViewport 768 × 512, поза — `BreachPanelLayout.pose` (0,65 м от головы к
     хранилищу, на 12° ниже взгляда, лицом к голове) считается один раз, когда панель появилась, и дальше стоит в мире. Появляется в `SHOW_DIST` (2,2 м) от
     хранилища, где можно что-то сделать; для хранилища, открытого для игрока, панели нет. До взлома: «ВЗЛОМ · узел · тир», демоны с цепочками (все, что
     влезает в RAM, отмечены; снять лишних можно), полоса RAM и «НАЧАТЬ ВЗЛОМ» — или причина словами: ПУСТО · пополнение через N мин (`access: empty`),
     ОСТЫВАЕТ · N мин (`cooldown`), занято другим (`busy`). Во взломе: сетка слева (7×7 — клетка ≈ 3,6 см), справа таймер, trace, буфер, цели (совпавшая — ✓),
     реплика ICE (`IceLines` из `breach.json`), «ЗАВЕРШИТЬ». Рамка панели красится по уровню trace; ловушка — вспышка рамки и импульс левого контроллера
     (панель не трясётся). Ввод — указка правого контроллера и курок: второй экземпляр `DeckPointer` (`WorldUI.breach_pointer`), плоская сборка — мышь.
  3. **Клиент подсвечивает, сервер подтверждает.** `BreachMirror` (`shared/breach/breach_mirror.gd`) держит ту же сетку и считает доступные клетки по правилу
     строка/столбец сразу; тап уходит серверу (`bk_tap`), ответ `bk_tick` подтверждает или откатывает. Порченые коды (ловушки среди обычных кодов) клиенту
     не выдаются; о них он узнаёт из ответа на тап (`trap`).
  4. **Сервер.** `VaultBreach` (`server/node/vault_breach.gd`) на узле: проверка («рядом» — `BREACH_REACH` 3 м, не пусто, не занято, не остывает, демоны в
     деке, цепочки ≤ RAM), номер попытки `n = max(world.breach_n, breach.n) + 1` пишется в `session.world.breach_n` ДО показа сетки, `BreachRun.for_storage`,
     таймер `advance(delta)`, тапы. Мир идёт: ловушка поднимает trace игрока на `settings.trap_trace[тир узла]` (5 / 8 / 12), провал (FAIL) поднимает
     тревогу узла на `alert_per_fail`. Все цели совпали — попытка кончается сразу (исход SUCCESS тот же, добивать буфер не нужно).
  5. **Итог.** Буфер полон, таймер, «ЗАВЕРШИТЬ», телепорт, выброс/флэтлайн/выход, обрыв связи, уход в тоннель — всё это итог по собранному (`resolve`):
     подсмотреть сетку и уйти без последствий нельзя. Он уходит в Мост операцией `run.breach` (`BridgeApi.run_breach`, rid `breach:<сессия>:<n>`,
     контракт docs/netrun-bridge-protocol.md 6.6): Мост считает эдди, открывает хранилища (`session.opened`), ставит остывание узла, решает сигнал СБ.
     `run.finish` дожидается `run.breach` (общий счётчик операций в полёте). Совпавший EXTRACT_SHARD открывает хранилище за этой сессией
     (`GrayNode.open_vault`, `settings.vault_open_sec`, по умолчанию 60 с): взять шард может только она, чужой `op.take_from_node` Мост отклонит (`claimed`).
     Рестарт сервера мира посреди взлома — попытки не было; открытые хранилища он находит в `session.opened`.
  6. **Флаг `vault_requires_open`** (graph.json, `settings`): `"auto"` (по умолчанию) — включён у узла графа, когда есть Мост (фейковый тоже); `true` / `false`
     задают явно; `--vault-requires-open=true|false|auto` у сервера переопределяет граф (стенды без взлома — `false`). Одиночный узел (`--single-node`),
     учебный узел и запуск без Моста берут шард, как раньше. Тестовые графы `tests/fixtures/graph_test.json` и `tutorial_graph.json` задают `false`.
  7. **Без Моста** (`--tokens=`, плоский стенд без фикстуры) итог считается на месте: совпавший EXTRACT_* открывает хранилище, эдди и сигнала СБ нет.
  8. **Бот.** `BotClient` перед взятием шарда из закрытого хранилища взламывает его автосолвером по сетке, какой её видит клиент (`breach_pick`: демоны
     EXTRACT_SHARD, до 3 попыток); сценарий-тест — `tests/breach_world_test.gd`. Живой журнал клиента: `breach.request|start|tap|end|no|cancel`.
  Снимки панели: `assets/preview_breach.tscn` (на devbox), `docs/netrun-deck-results/k3-*.png`. На очках не проверено: читаемость и промахи по клеткам
  7×7, комфорт (панель на 0,65 м), укачивание, ощущение площадки (поворот при посадке), импульс на ловушку.
- **Заряд защитных демонов (К6).** GHOST, JITTER, TIMESKEW, BLACKOUT вне взлома срабатывают только **заряженными** (решение владельца, docs/netrun-deck-design.md §3.3):
  1. **Заряд заранее.** У незаряженного защитного демона на вкладке ДЕКА кнопка «ЗАРЯДИТЬ» (плоская сборка — клавиша C для выбранного). Сервер (`ChargeBreach`,
     `server/node/charge_breach.gd`) запускает тот же движок в режиме `BreachRun.for_charge`: цель — цепочка самого демона, сетка и таймер по тиру демона
     (`breach.json`: 5×5/45 с, 6×6/60 с, 7×7/75 с), буфер = длина цепочки + 2, **ловушек нет**; мир идёт. Сетка заменяет вкладки на деке (`DeckCharge`,
     `client/ui/deck_charge.gd`), доступные клетки подсвечивает клиент (`BreachMirror`), сервер подтверждает тапы; на время сетки дека на запястье плавно растёт
     до масштаба 1 (`WorldUI.CHARGE_DECK_SCALE`, 32 × 24 см; клетка ≥ 2,8 см), потом возвращается. Протокол — `charge {daemon}` и те же `bk` / `bk_tick` / `bk_end` /
     `bk_no` с `mode: "charge"` (`WorldMsg`); `bk_tap` и `bk_cancel` общие. Собрана цепочка — демон заряжен (`state.cd` `st: "charged"`, на плашке «ГОТОВ К
     ЗАПУСКУ»); время вышло, «ОТМЕНА», телепорт, выброс, обрыв — попытка просто брошена, повторить можно сразу. Заряд и взлом хранилища друг друга исключают
     (`bk_no`: `charging` / `active`). Заряд не взлом: ни `run.breach`, ни сигнала СБ, ни trace.
  2. **Запуск одним нажатием.** Левый X запускает выбранного демона, если он заряжен, иначе первого заряженного (`rig_test_scene.launch_target`); Y листает сначала заряженных;
     плоская сборка — цифры слотов. Заряд расходуется одним запуском (`DaemonService.apply`), дальше перезарядка из `data/daemons/effects/<ЭФФЕКТ>.json`; заряжать во
     время перезарядки нельзя. Удачный запуск — импульс левого контроллера и «активен N с» на плашке; запуск без заряда — слово на деке («Не заряжен: нажмите ЗАРЯДИТЬ») и слабый импульс.
  3. **Окна эффектов.** Запуск открывает окно `duration_sec` (стартовые числа: GHOST 20/30/45 с, JITTER 15/20/30 с, TIMESKEW 30/40/50 с с перезарядкой 90/90/75 с, BLACKOUT
     8/10/12 с с перезарядкой 240/240/180 с — подбираются на плейтесте). `DaemonSession.active_effects(now)` отдаёт `GHOST`, `TIMESKEW`, `BLACKOUT`, пока окно
     открыто: их берут `run.breach` (`active`, конец взлома), запись `session.world.effects` при достижении уровня TRACE (правило P3 Моста) и при переходе
     между узлами. Мост учитывает окно в момент решения: окно, открытое после того как сигнал уже решён, его не меняет. JITTER Мосту не нужен — он замораживает trace.
  4. **Бот.** Перед `use` GHOST бот заряжает его автосолвером (`BotClient._step_charge`, журнал `charge_log`). Журнал клиента: `charge.request|start|tap|end|no|cancel`.
  Снимки: `assets/preview_charge.tscn` (на devbox), `docs/netrun-deck-results/k6-*.png`; чек-лист очков — `docs/netrun-deck-results/k6-checklist.md`.
  **Расшифровка шарда на месте (К7).** На ДОБЫЧЕ у зашифрованного шарда кнопка «РАСШИФРОВАТЬ», если среди рабочих демонов есть DECRYPT тира не ниже тира шарда
  (`DeckDecrypt.best`, то же правило, что `DecryptRules.bestDecrypter`; нет дешифратора — кнопки нет, при прямой просьбе сервер отвечает `bk_no no_decrypter`).
  Клиент шлёт `decrypt {item}`; сервер (`DecryptBreach`, рядом с `ChargeBreach`) ведёт сессионную попытку в режиме движка `for_decrypt` (цепочка шифр-замка 3/4/5 по
  тиру шарда, сетка и таймер по тиру, буфер = цепочка + 2, ловушек нет) на той же сетке деки, что у заряда (`DeckCharge`, mode = decrypt). Одна мини-игра на игрока:
  взлом, заряд и расшифровка друг друга исключают; отмена, таймер, телепорт, выброс, обрыв бросают попытку без последствий. Совпала цепочка — сервер зовёт Мост
  `op.decrypt_item` (протокол, 6.8: в `payload` меняется ровно флаг «расшифрован»; версия предмета берётся свежей, `rid = decrypt:<сессия>:<предмет>:<ver>`,
  обрыв — повтор того же запроса, потерянный ответ после коммита распознаётся по перечитанному предмету; исход забега ждёт запрос в полёте) и присылает свежий
  `ev deck`: шард в ГРУЗе «ОТКРЫТ», после выхода он приходит на телефон открытым. Коллектору отдельной записи расшифровка в Сети не пишет (решение владельца).
  События: `bk`/`bk_tick`/`bk_end {item, title, decrypted, early?, error?}`/`bk_no {reason}` с mode = decrypt (WorldMsg.DECRYPT). Журнал клиента: `decrypt.request|start|end|no`.
  Тесты: `decrypt_world_test` (бот-автосолвер, отказы, обрыв и потерянный ответ Моста), `decrypt_client_test`, JUnit `ValueOpsDecryptTest`. Снимки: `assets/preview_decrypt.tscn`
  (на devbox), `docs/netrun-deck-results/k7-*.png`; чек-лист очков — `docs/netrun-deck-results/k7-checklist.md`.
- **ЧАТ** — диалоги (непрочитанные сверху, новые к старым: позывной, последняя строка, время, жёлтый бейдж; фракционный помечен «ФРАКЦИЯ»).
  Диалог открывается нажатием и сразу помечается прочитанным (`mark_read`). Внутри: последние 8 сообщений пузырями (свои справа зелёные,
  собеседника слева; во фракционном виден автор; у своих «✓» отправлено, «✓✓» доставлено, «!» + «НЕ ДОСТАВЛЕНО» словами) и **шесть
  заготовок ответа** — ОК, Принято, Жди, Я в Сети, Позвони, Не могу говорить: нажатие = `send_text` в открытый диалог. Свободного текста и
  голосовых сообщений в очках нет (`docs/netrun.md`). В шапке личного диалога — «ПОЗВОНИТЬ», «‹ ЧАТЫ» — назад. Сообщение, пришедшее в открытый
  диалог на виду, читается сразу.
- **ЗВОНКИ** — карточка текущего звонка и журнал. Входящий: позывной, пульсирующая зелёная рамка, «ОТКЛОНИТЬ | ПРИНЯТЬ» (отменяющая слева,
  как в приложении); в разговоре: таймер, «ЗАГЛУШИТЬ» (затем «СНЯТЬ ЗАГЛУШКУ», метка «МИКРОФОН ВЫКЛ»), «ЗАВЕРШИТЬ»; исходящий: «ВЫЗЫВАЕМ…»,
  «ОТМЕНА». Журнал — направление (↙ входящий, ↗ исходящий, красный — пропущенный), время, длительность и «ПОЗВОНИТЬ» в каждой строке (при занятой
  линии кнопка серая).
- **Бейджи** на вкладках: ЧАТ — все непрочитанные; ЗВОНКИ — пропущенные, которых ещё не видели (открыл вкладку — сброс). **Входящий или
  исходящий звонок сам выводит вкладку ЗВОНКИ** (во время разговора вкладку можно сменить — назад не вернёт).
- **Без телефона** (`--phone=off`, аргумент клиента) вкладок ЧАТ и ЗВОНКИ нет: остаётся одна ДЕКА, указатель молчит. Голая `DeckPanel` без
  `set_phone` ведёт себя так же — поэтому `DeckPanel`, `WorldUI.attach`, `hud_logic` и их тесты работают как раньше.

**Данные.** `shared/phone_link.gd` — абстракция `PhoneLink` (сигналы `threads_changed`, `message_received(thread_id, msg)`, `call_changed(state)`;
`threads()`, `messages(id, limit)`, `send_text`, `mark_read`, `call_state()`, `accept_call`, `decline_call`, `hangup`, `set_muted`, `start_call(peer)`,
`call_log()`; формат словарей — в комментарии класса). Дека работает только с ней, не с сетью мира. Её реализует **`client/fake_phone_link.gd`**
(фиктивный сценарий; настоящая связь с телефоном — позже, дека не меняется). Сценарий идёт по часам `advance()` (их крутит `WorldUI._process`) и
по умолчанию включён, круг 150 с: на старте 4 диалога (ВОБЛА, ШЕРШЕНЬ, ЛИС и фракционный ВОЛЬНЫЕ; в нём одно непрочитанное) и 4 записи журнала;
на 5, 10, 16 с — сообщения; на 24 с — звонок ВОБЛЫ (звонит 45 с, потом пропущенный, как `RING_TIMEOUT_MS` в приложении); на 70 с — фракционная
реплика; на 82 с — звонок ШЕРШЕНЯ; на 130 с — сообщение. На заготовки отвечают (ВОБЛА, ШЕРШЕНЬ, во фракционном — ШЕРШЕНЬ) через 4 с; «Позвони»
вызывает перезвон через 6 с; ЛИС «не в сети»: сообщение ей получает статус «НЕ ДОСТАВЛЕНО», звонок ей обрывается через 1,2 с. Звонки ведут
себя как `CallManager`: занятая линия новый вызов не принимает, каждый законченный звонок оставляет строку журнала.

**Управление.** Нажимает **указатель правого контроллера** (`client/ui/deck_pointer.gd`, подключает `WorldUI.attach`): луч из позы `aim`
(`rig.right_aim`; нет данных — из руки `right_hand`) пересекается с плоскостью панели, точка попадания переводится в пиксель SubViewport
(`shared/deck_pointer_math.gd`, `DeckPointerMath.ray_to_view`, покрыта тестами: края, промах, обратная сторона, поворот панели) и уходит туда
событиями мыши; под лучом кнопка подсвечивается, на панели видна точка (на нажатии белая) и от руки идёт короткий луч (слабый — если
целишься рядом с панелью). **Курок** правого контроллера (`trigger_click`; на случай отсутствия привязки ещё и ось `trigger` глубже 0,75) —
левая кнопка мыши, **левый стик по Y** листает список, пока луч на панели. Правый стик (телепорт, поворот при телепорте), захват (`grip_click`)
и левые X/Y не затронуты; `trigger_click` правой руки нигде больше не использовался (проверено `grep`). **Плоская сборка** — тот же код: луч из камеры
через курсор мыши, ЛКМ — нажатие (клик по панели не доходит до захвата предметов), колесо — прокрутка. Нажатая кнопка срабатывает на отпускании
внутри неё; нажал на одной и отпустил на другой — ничего.

**Размер и читаемость.** Размер вьюпорта и ширина панели — две константы в одном месте, `DeckPanel.VIEW_SIZE` (512 × 384 px) и `DeckPanel.PANEL_WIDTH_M` (0,32 м; высота по
соотношению сторон — 24 см); размеры деталей в пикселях — `client/ui/deck_theme.gd`. Масштаб деки на руке — отдельная константа `WorldUI` (на запястье `WRIST_DECK_SCALE` = 0,75, ветка
рук): панель в итоге 24 × 18 см. 1 px = 0,625 мм (на запястье 0,47 мм): кнопка карточки звонка 52 px ≈ 2,4 см, заготовки, вкладки и кнопки шапки 48 px ≈ 2,25 см, строка списка
58 px ≈ 2,7 см; текст 19 px (заглавная ≈ 13 px ≈ 6 мм на запястье ≈ 47' на 45 см). Нажимаемое не меньше 2 см после масштаба сверяют тесты (`DeckPanel.px_to_cm`, `deck_tabs_test.gd`: по
константам и по настоящим кнопкам после раскладки). Было 320 × 240 на 16 × 12 см. Цвета и шрифты — токены `docs/ux/ui-style-guide.md` (`client/ui/deck_theme.gd`: Fira Sans Condensed и
IBM Plex Mono из приложения, `client/ui/fonts/`, около 1,1 МБ в APK), рамки со срезом рисует `MbShape` (StyleBoxFlat срез не умеет), компоненты — `MbFrame`, `MbButton`, `MbTabs`, `MbRow`,
мелочи — `DeckUi`. Положение и масштаб деки вкладки не трогают (ими владеет `WorldUI._place`: на запястье — якорь `HandView.wrist_anchor` и `WRIST_DECK_SCALE`; индикатор trace уходит ниже деки, `WRIST_TRACE_POS` считается от её высоты); указатель берёт трансформацию самой поверхности деки вместе с масштабом и размер панели до
масштаба, поэтому подходит любой якорь, а невидимую деку (на запястье её прячут, пока у руки нет позы) не нажимает. Снимки для оценки сделаны плоской сборкой с камерой, у которой угловая
плотность пикселей такая же, как у Pico 4 (≈ 20 px на градус: vFOV 32° при высоте окна 648 px), панель на 45 см, в том числе в масштабе 0,75 и в позе «на запястье» под углом к глазам.

**Стоимость.** Текстура не перерисовывается без изменений и не чаще `DeckPanel.MAX_FPS` = 30: грязной деку делает событие данных, подсветка под лучом
или перерисовка любого Control внутри (сигнал `draw`). Идущий звонок перерисовывает деку редко: таймер — раз в секунду, пульс рамки входящего —
6 ступеней за 1,2 с (≈ 5 в секунду). Тесты (`deck_tabs_test.gd`) считают `redraw_count`: простой — 0 перерисовок за 2 с; перемена в каждом кадре при 72 Гц — не больше 61 за 2 с (кап);
пульс — не больше 18 за 3 с; таймер — 2–5 за 3 с. В журнале клиента в строке `perf` есть `deck_redraws=N` (накопленное число перерисовок) — по нему на очках видно, сколько стоит дека.

**Отклик.** Входящее сообщение — импульс левого контроллера 0,05 с и два тихих тона; входящий звонок — серия из трёх импульсов раз в 2,2 с и рингтон, пока звонит; ответ на звонок
и завершение — короткий импульс; нажатие на панель — лёгкий импульс правой руки. Звук синтезируется при старте (`DeckFeedback.make_tone_stream`, `AudioStreamWAV`), готовых
аудиофайлов нет; играет `AudioStreamPlayer3D` на руке. Нет вибрации или звука — молча.

**Журнал клиента** (`pico.sh log`): `phone link=fake|off tabs=N` при старте, `phone.warn` (неверный `--phone=`), `phone.msg thread=…`, `phone.call phase=… peer=… muted=…`, `phone.reply thread=… text=…`,
`deck.tab id=deck|loot|chat|calls`, `deck.info ram=… default=… used=… programs=… loot=… eddies=…`, `perf … deck_redraws=N`. Тесты: `phone_link_test.gd`, `phone_logic_test.gd`, `deck_pointer_math_test.gd`, `deck_tabs_test.gd`, `deck_loot_test.gd`, `deck_world_test.gd`, `deck_pointer_test.gd`,
`deck_feedback_test.gd`, `phone_client_test.gd`.

**Не проверено без очков:** поза `aim` и совпадение луча с указанием контроллера на Pico 4, привязка `trigger_click` (запасная — ось `trigger`), знак и скорость прокрутки левым стиком,
вибрация (`trigger_haptic_pulse("haptic", …)`) и звук на очках, читаемость и точность попадания в кнопки ≈ 2,2–2,7 см при дрожании двух рук, положение панели относительно кисти и нужен ли
поворот панели к голове, влияние на кадры (`perf`, `deck_redraws`). Если нативная картинка или ввод в очках окажутся плохими, запасной вариант — Compose-экраны Android в слое OpenXR (`docs/netrun.md`).

## Как запускать

Режим: сервер, если `--headless` или метка `dedicated_server`/аргумент `--server`; клиент — на Android или `-- --client`;
иначе плоская сборка (`-- --flat`). Аргументы пользователя идут после `--`.

```sh
godot --headless --path netrun                         # сервер мира; выход по Ctrl+C / SIGTERM
godot --headless --path netrun -- --exit-after=5       # сервер, сам выйдет через 5 с
godot --path netrun -- --flat                          # плоская отладочная сборка (с окном)
godot --headless --path netrun --import                # импорт проекта (CI, первая загрузка)
```

Сеть (V2): сервер слушает ENet-порт 7777; токены пока из аргумента (вместо Моста, F1/M5), клиент берёт адрес и токен из аргументов.

```sh
godot --headless --path netrun -- --tokens=t1:alice,t2:bob --grace=20    # сервер: токен:сессия, окно возврата аватара, с
godot --path netrun -- --flat --host=127.0.0.1 --port=7777 --token=t1    # плоский клиент
```

Тест переподключения (сервер и клиент в одном процессе, `tests/net_reconnect_test.gd`): возврат в окно — тот же аватар
`node_07/avatar_<сессия>`, после окна — аватар убран, повторный вход — новый; плохой токен отклоняется. Окно в тесте 1,5 с;
значение по умолчанию 20 с (`NetConfig.DEFAULT_GRACE_SEC`) проверяется отдельно. Тихий обрыв сеть замечает за ~5 с (`NetServer.PEER_TIMEOUT_MS`).

Настоящий клиент (`ProtoClient`) после обрыва возвращается сам (V6а): `NetClient.auto_reconnect_sec` = 2 с, до 60 попыток, в журнале
`net.reconnect attempt=N` (и `net.gave_up`, если попытки кончились). Не возвращается, если забег закончился (событие `ended`) или игрок вышел сам
(`stop_reconnect`), и если связи ещё не было (плохой токен, сервер не запущен). У бота и тестов автопереподключение выключено (`0`):
они возвращаются сами. Живой прогон — `docs/netrun-stage1-results-flat.md`.

## Мост (F1)

Сервер мира берёт токен терминала и операции с ценностями у Моста (`:netrun-bridge`, протокол — `docs/netrun-bridge-protocol.md`).
Выбор — аргументом `--bridge=`:

- `--bridge=fake` (по умолчанию) — `FakeBridge` в том же процессе, данные из `tests/fixtures/bridge_fixture.json`
  (другая фикстура — `--bridge-fixture=res://…`). Kotlin не нужен. Токены очков в фикстуре: `t03:token-t03` и `t04:token-t03`
  (сессия `s_fake000000000001` active, `…02` pending). Без `--bridge`, но с `--tokens=` работает старая заглушка (токен -> сессия).
- `--bridge=ws://хост:порт` — `BridgeClient` по WebSocket (`/netrun/v1` добавляется сам), ключ роли world — `--bridge-key=` или
  переменная `NETRUN_KEY_WORLD`.

Токен в `auth` очков — `терминал:токен` или JSON `{"terminal","token"}` (клиент: `--token=t03:token-t03`).

С настоящим Мостом локально (два терминала, из корня репозитория; Java 17+):

```sh
# 1. Мост (ключи ролей — в окружении; --test нужен только фейковому серверу мира в тестах Kotlin)
export NETRUN_KEY_WORLD=kw NETRUN_KEY_MASTER=km
./gradlew :netrun-bridge:run --args="--port 7410 --db /tmp/netrun-bridge.db"

# 2. Мастер заводит данные (put с ролью master по WebSocket, протокол раздел 5): узел node_07, терминал t03 с
#    token_sha256 = sha256 токена очков. Сессию создаёт только приём карточек телефона (M2) — пока её нет,
#    verify вернёт "" и очки получат отказ. Для проверки без телефона запустите Мост с --test и NETRUN_KEY_TEST
#    и сдайте деку op.submit_deck ролью test (см. netrun-bridge/src/test/…/FakeWorldRunTest.kt).

# 3. Сервер мира
godot --headless --path netrun -- --bridge=ws://127.0.0.1:7410 --bridge-key=kw
godot --path netrun -- --flat --host=127.0.0.1 --port=7777 --token=t03:<токен очков>
```

Если Мост не отвечает, сервер мира пробует снова раз в 2 с, а запрос токена получает отказ через 4 с (очки не пускаются).
Повтор операций после обрыва безопасен: `rid` детерминированные (`take:<сессия>:<предмет>`, `leave:…`, `finish:<сессия>`).
Тесты: `tests/fake_bridge_test.gd`, `tests/bridge_client_test.gd`; со стороны Моста — `FakeWorldRunTest` (фейковый сервер мира).

### Сервер мира одноразовый (M5)

Всё, что должно пережить рестарт, лежит в Мосте. `GrayNode` при старте ждёт связи, подписывается на `session/deck/node/item` и по
снимку: ставит активные сессии своего узла в окно возврата (`NetServer.expect_session`, `--grace=` секунд; вернулся клиент с тем же
токеном — тот же забег, нет — `run.finish` emergency/`disconnect`), возвращает шард держателю (`restore_holder`) или на постамент,
запоминает `lockdown_until`. Игрок возвращается в точку входа; перезарядки демонов и trace начинаются заново (в Мосте их нет).
Узел пишет `node.data.world = {up, players}`, связь игрока — `session.data.world` (`put_doc` с повтором при `version_conflict`).
`take` и `run.finish` при недоступном Мосте повторяются с тем же детерминированным `rid`. Дека берётся из `payload` предметов
`deck:<сессия>`, если там есть id демона (формат `ItemPayload` серверу мира пока неизвестен), иначе дека по умолчанию.
Тест без сети — `tests/restart_test.gd` (FakeBridge переживает «убитый» сервер).

Живой прогон с настоящим Мостом — `netrun/tools/live_run.sh` (на devbox, Gradle не на Mac): Мост (`--test --seed`, активная сессия,
дека и шард кладутся файлом), сервер мира, бот `--bot=ghost_run --bot-reconnect --bot-hold=10`; после взятия шарда сервер убивается
`kill -9` и поднимается снова, бот возвращается и выходит чисто, `tools/check_bridge.gd` проверяет документы (сессия closed/clean,
шард и дека у игрока в `outbox`, тревог аудитора нет). Итог — строка `LIVE_RUN PASS|FAIL: …`.

Экспорт (нужны шаблоны 4.7.2): `godot --headless --path netrun --export-debug "Client Pico 4 (Android)"`,
`--export-release "Server (dedicated)"`, `--export-debug "Flat debug (Linux)"`.

godot --headless --path netrun -s -d res://addons/gdUnit4/bin/GdUnitCmdTool.gd --add res://tests --ignoreHeadlessMode

В CI тот же запуск идёт через `netrun/tools/gdunit_ci.sh` со сторожем: 05.10 один прогон встал на 50 минут (журнал оборвался на строке `start` клиента,
таймер таймаута gdUnit не сработал — замер главный поток движка, не `await` теста). Сторож при «нет вывода 240 с» печатает таблицу потоков
(на раннере — стеки через gdb), убивает процесс и один раз повторяет набор; красные тесты не повторяет. Предел одного теста — 120 с
(`gdunit4/settings/test/test_timeout_seconds` в `project.godot`): зависший `await` теперь падает «Test timed out», а не ждёт 5 минут.

## Выход (N6)

Удержание 3 с (VR — `menu_button`, настройка `XRRig.exit_button`; плоская сборка — Esc) → клиент шлёт серверу пакет
`{"t":"exit","reason":"manual_hold"}`; полоса прогресса — предмет мира перед глазами. Снятие очков и любой «уход из игры» (пауза приложения
`NOTIFICATION_APPLICATION_PAUSED`, потеря фокуса — сигнал OpenXR `session_visible`, остановка сессии `session_stopping`, датчик
на лбу `user_presence_changed`) — не сразу: окно **15 секунд** (`AwayGuard.GRACE_SEC`, решение владельца, 4 октября 2026). Вернулся
быстрее — игра идёт дальше (сервер держит аватар при обрыве 20 с, клиент переподключается сам). Не вернулся за 15 с (по таймеру
при потере фокуса или в момент возвращения после паузы) — та же отправка с причиной `headset_off`; если приложение спит дольше
20 с, сервер сам оформляет обрыв (`connection_lost`). Раньше пауза выбрасывала игрока сразу — под охотой это сжигало деку. В Godot 4.7
у `OpenXRInterface` нет сигнала `focus_lost`, на который рассчитывал прежний код. Журнал: `away.begin|end|exit source=pause|focus|session|presence sec=…`. Сервер (`NetServer.exit_event`) отдаёт
`{session, reason, under_hunt, deck_burned}`; флаг охоты ставит снаружи `set_under_hunt(session, bool)`. Обрыв связи выходом не
считается: по истечении окна возврата — событие `connection_lost`. Логика — `shared/exit_logic.gd` и `shared/away_guard.gd`, тесты `exit_logic_test.gd`, `net_exit_test.gd`, `away_guard_test.gd`, `away_exit_test.gd`.

## Серый узел (N7)

`server/node/gray_node.gd` собирает узел node_07 (геометрия — `shared/node_layout.gd`: комната, укрытия, шард, площадка выхода,
2 ICE с патрулём): на сессию TraceMeter и DaemonSession (дека `ghost_1`, `jitter_1`), ICE шагает 10 раз/с и не видит игрока под
GHOST, сервер раз в 0.1 с шлёт снимок (`WorldMsg.STATE`: trace, ICE, перезарядки) и события (`WorldMsg.EVENT`). Шард берётся
через сервер (`grab`, не дальше 3.5 м), в Мосте это `op.take_from_node`; забег закрывает одна `run.finish`: чистый выход на
площадке (`leave`) — добыча на телефон, выброс ICE / флэтлайн / обрыв — добыча остаётся в узле.

Плоская сборка: 1–9 — применить демона из деки, X — выйти чисто на площадке, F / ЛКМ — взять шард; VR: левый X — применить
выбранного, Y — выбрать следующего. Бот — `tests/bot/bot_client.gd` (сценарии GHOST_RUN и EXPOSED_RUN; двигается прыжками-телепортами), тест — `tests/gray_node_test.gd`.

## Граф узлов (W1)

`data/graph.json` — 12 узлов (BASE 6, HARD 4, NIGHTMARE 2), тоннели-связи (симметричные, до трёх на узел: i-я связь — слот
портала `NodeLayout.PORTAL_SLOTS[i]`), у каждого узла тир, число Soft ICE, число шардов; Black ICE — только в NIGHTMARE (по тиру,
в данных его нет). `entries` — узел входа по терминалу (`t01 → node_01`…), `default_entry` — для остальных; вход всегда не NIGHTMARE.
`settings` — все числа: `tunnel_sec`, `portal_dwell_sec`, `shard_refill_sec` по тирам, `refill_retry_sec`, `alert_*`, `lockdown_sec`.
Проверка данных — `NodeGraph.errors()` (симметрия, связность, слоты, тир входа); тест `node_graph_test.gd`.

Граф — режим по умолчанию: `godot --headless --path netrun` (или `-- --graph=<путь>`); прежний одиночный серый узел node_07 — `-- --single-node`.
Шарды сервер мира не создаёт: узел пополняется только из запаса, заложенного мастером (предметы `node:<узел>` в Мосте); пустой узел просто ждёт.
Битый граф в журнал (`push_error`) и сервер работает одним узлом.

- **Переход.** Игрок простоял `portal_dwell_sec` в радиусе портала → `GraphWorld.transit_check` (связь есть, узел не в локдауне,
  нет охоты Black ICE) → сессия уходит в «тоннель» (`NetServer.TUNNEL_NODE`: ни снимков, ни ICE, trace стоит, позиции клиента не
  принимаются), клиенту — событие `tunnel`; через `tunnel_sec` сессия приходит в новый узел у возвратного портала, клиенту — `node`
  (`arrive`). `DaemonSession` (trace, дека, перезарядки, GHOST) переходит тем же объектом; узлы ходят по общим часам `GraphClock`.
  Отказ — событие `portal_denied` (`lockdown | hunt | busy | not_linked`). Выход из забега в тоннеле закрывает забег в узле,
  откуда игрок ушёл.
- **Клиент.** `rig_test_scene.apply_node` рисует шарды и порталы узла по описанию сервера; `begin_tunnel`/`end_tunnel` — `TunnelFx`:
  тёмная сфера вокруг головы с тусклым потоком в шейдере, плавное затемнение; ход блокируется (`XRRig.movement_locked`), камера не
  двигается и не вращается; риг ставится на место входа под непрозрачной сферой. Шард в руке идёт с игроком из узла в узел.
  Вид тоннеля и читаемость порталов — только на очках (в тестах проверена логика).
- **Пополнение.** Шард, вынесенный на телефон или в другой узел, пустит слот (`NetServer.lock_object`, ответ клиенту `empty`) на
  `shard_refill_sec[тир]`; затем слот берёт свободный шард `node:<узел>` из Моста (сервер мира шардов не создаёт — их выпускает
  Мост), нет свободного — повтор через `refill_retry_sec`. Без Моста слот просто оживает. Добыча, оставшаяся в узле окончания
  (выброс, флэтлайн, обрыв), слот не пустит.
- **Остывание.** Тревога узла 0…1: растёт, когда trace игрока впервые достиг TRACE (`alert_per_trace`) и при выбросе
  (`alert_per_eject`); остывает за `alert_cool_sec`; при полной зрение и внимание ICE выше на `alert_boost`.
- **Локдаун.** После выброса Soft ICE: с Мостом — `node.lockdown_until` (ставит Мост по run.finish), без Моста — сервер мира на
  `lockdown_sec`. Закрытый узел не принимает через портал; портал в закрытый узел на карте серый.
- **Мост.** `session.data.world.node` — где игрок сейчас (после рестарта сервера мира узел находит игрока по нему).
  Ограничение действующего Моста (`ValueOps.activeSession`): `take_from_node` и `run.finish` требуют `node == session.node`,
  а в графе шард берут в узле, куда игрок прошёл тоннелем, — до правки Моста (принимать узел из `world.node` сессии) вне узла
  входа вынос шарда Мост отклонит; `FakeBridge` это допускает.
- **Бот.** `BotClient.Scenario.GRAPH_RUN` (`route`, `use_ghost`; из командной строки `--bot=graph_run --bot-route=node_02,node_03`):
  идёт порталами по маршруту, в последнем узле берёт шард и выходит чисто. Тест `graph_world_test.gd`: забег через три узла с
  возвращением добычи на телефон, trace и дека сохранены, пополнение, локдаун, тревога, 12 узлов по тирам.

## До 10 клиентов (P1)

- **Видимость по узлу:** у сессии есть узел (`NetServer.node_of`, по умолчанию `node_07`; `set_node`). `GrayNode` шлёт `state` и позиции
  аватаров только сессиям своего узла; у остальных пакеты просто не уходят.
- **Чужие аватары:** сообщение `av` (`WorldMsg.AVATARS`) — раз в 0.05 с, каждому игроку все остальные в его узле: `[[id, x, z], …]`
  и время сервера `k`. `state` (ICE, trace, дека) — раз в 0.1 с, тоже с `k`. Позицию свою клиент шлёт 20 раз/с.
- **Сглаживание на клиенте:** `StateBuffer` (снимки по времени сервера, интерполяция, пропущенный пакет, опоздавший пакет, скачок времени),
  `ServerClock` (смещение часов по самому быстрому пакету окна), `RemoteTracks` (всё вместе). Показ с задержкой: аватары 0.1 с, ICE 0.15 с
  (он приходит вдвое реже). Тесты — `tests/state_buffer_test.gd`.
- **Нагрузка:** `tests/multi_client_test.gd` — 10 ботов `BotClient.Scenario.LOITER` в одном узле; печатает `[P1-LOAD]`: трафик на клиента
  (полезная нагрузка, без заголовков ENet/UDP) и время шага сервера.

## e2e с телефоном (M6)

Сценарий `scripts/e2e/scenarios/netrun-run.sh` (общий стенд двух эмуляторов, `scripts/e2e/README.md`): Alice с эмулятора сдаёт Мосту
двух демонов (QR стойки подаётся debug-командой `DEBUG_SET netrun`), курок очков изображает роль `test` Моста (`session.confirm`:
настоящего курка у очков пока нет), бот `--bot=ghost_run --bot-daemon=<id предмета GHOST>` проходит узел по токену терминала. Затем
флэтлайн (`black_ice`) закрывается тестовым путём Моста: сервер мира без ICE и trace 100 исход сам не выдаёт. Мост запускается с
`--phone host:port=ключ` (только `--test`): эмулятор за NAT виден как 127.0.0.1, такой адрес Мост по строкам не запоминает.
Тот же Мост шлёт записи мира на коллектор стенда (`--collector`), а в конце сценарий проверяет их приём, флаг нетраннера и повтор отправки после
перезапуска Моста с той же базой (M6b).
