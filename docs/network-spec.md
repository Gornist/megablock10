# Мегаблок №10 — спецификация локальной сети

> Публичная редакция: конкретные IP-адреса, подсети, диапазоны, порты, имя сети и пароли из документа убраны (`<GATEWAY_IP>`, `<SERVER_IP>`, `<SUBNET>` и т. п.). Полная версия хранится у владельца сети.

Документ для агента, который пишет веб-дашборд и мобильное приложение. Описывает сеть, на которой всё будет работать, и что из неё следует для кода.

**Статусы пунктов**
- `[ФАКТ]` — уже есть или решено владельцем.
- `[ПЛАН]` — принято как рабочее решение, но не куплено/не настроено.
- `[ПРЕДЛОЖЕНИЕ]` — разумное значение по умолчанию, можно менять.
- `[TBD]` — неизвестно, не придумывай значение, спроси владельца или сделай настраиваемым.

## 1. Назначение и жёсткие ограничения

- `[ФАКТ]` Сеть для кибербанк-LARP «Мегаблок №10»: около 100 игроков, формат «подводная лодка» (закрытое пространство), здание-мегаблок плюс 5–6 наружных зон.
- `[ФАКТ]` Интернета в сети нет и не будет. Всё должно работать полностью офлайн.
- `[ФАКТ]` Клиенты — только Android-телефоны игроков. iOS не поддерживается.
- `[ФАКТ]` Сеть на оборудовании Ubiquiti UniFi.
- `[ПЛАН]` Один SSID на всё здание и наружные зоны, одна подсеть, без VLAN. Телефоны свободно ходят между точками доступа (роуминг), IP при этом не меняется.
- `[ФАКТ]` Приложение (репозиторий `Gornist/megablock10`) общается по локальной сети: обнаружение соседей через NSD/mDNS, текстовый чат по TCP, присутствие (онлайн/офлайн/last seen), обмен контактами по QR. Голос, голосовые сообщения и фото — вторая очередь.

## 3. Топология

```
                          (интернета нет)
                                |
                        [ UCG-Ultra ]  <GATEWAY_IP>
                        gateway + DHCP + UniFi Network
                                |
                     [ USW-Pro-24-PoE ]  <SWITCH_IP>
        ______________|________|____________________|_______________
        |             |        |                    |               |
  [Flex Mini]    AP-IN-01..N   AP-OUT-01..K     AP-OUT-M (mesh,   [ADMIN
   |    |         (U7 Lite,     (U7 Outdoor,       без кабеля       порт]
 [СЕРВЕР] [ноут]   проводные)    проводные)        данных)
 <SERVER_IP>                                         ↑ беспроводной
                                                    uplink к проводной AP
                                                    (макс. 2 хопа)

  Все AP → один SSID «TBD» → телефоны игроков (~100), одна подсеть <SUBNET>
```

Правила топологии:
- `[ПЛАН]` Проводной бэкхол везде, где возможно. Mesh (wireless uplink) только для наружных точек, до которых нельзя протянуть кабель.
- `[ПЛАН]` При mesh: не более 2 хопов, уровень между дочерней и проводной точкой не хуже −60 дБм, не более 3 дочерних на одного родителя.
- `[ПЛАН]` Meshing включить только на родителях и дочерних точках. На остальных выключить, иначе проводная точка при сбое кабеля тихо уйдёт на беспроводной uplink с потерей примерно половины скорости.

## 4. Адресация `[ПРЕДЛОЖЕНИЕ]`

Конкретные адреса, диапазоны и подсети в публичный репозиторий не вынесены — они у владельца сети. Схема:

- Одна подсеть `<SUBNET>`, без VLAN, одна широковещательная область.
- Инфраструктура (шлюз `<GATEWAY_IP>`, коммутатор `<SWITCH_IP>`, локальный сервер `<SERVER_IP>`, точки доступа `<AP_RANGE>`) — статика или DHCP-резервации в отдельном диапазоне.
- Отдельный DHCP-пул `<DHCP_POOL>` для телефонов игроков.
- Время аренды DHCP на весь срок игры (не менее суток), чтобы адрес телефона не менялся.
- DHCP выдаёт DNS-сервер `<SERVER_IP>` (локальный сервер).

## 5. Wi-Fi: настройки

Один SSID (`[TBD]` имя и пароль), назначен на все точки, WPA2-PSK (`[ПРЕДЛОЖЕНИЕ]` — наиболее совместим со смесью Android-моделей).

| Параметр | Значение |
|---|---|
| Client Device Isolation | **выключено** (телефоны ходят друг к другу напрямую) |
| Multicast and Broadcast Filtering | **выключено** (иначе ломается NSD/mDNS) |
| IGMP Snooping | включено |
| Multicast Enhancement (IGMPv3) | включить и проверить, при проблемах отключить |
| Proxy ARP | выключено |
| Band Steering | включено |
| BSS Transition (802.11v) | включено |
| Fast Roaming (802.11r) | протестировать с ним и без него на 3–4 моделях Android |
| Minimum RSSI | выключено на старте; при «залипании» на дальней точке пробовать около −75…−80 дБм |
| UAPSD | протестировать |
| 5 ГГц | ширина канала 20 или 40 МГц (не 80), неперекрывающиеся каналы |
| 2.4 ГГц | ширина 20 МГц, мощность снижена |
| Мощность | подбирать под слабейший клиент (телефон): на улице не ставить максимальную на всех точках |
| Цель по покрытию | на границе зоны около −67 дБм, соседние зоны перекрываются |

## 6. Сервисы на локальном сервере `[ПРЕДЛОЖЕНИЕ]`

Адрес `<SERVER_IP>`. Нужен, чтобы Android не считал Wi-Fi «без интернета».

1. **DNS-заглушка** (dnsmasq или AdGuard Home). Переопределить на `<SERVER_IP>`:
   - `connectivitycheck.gstatic.com`
   - `connectivitycheck.android.com`
   - `clients3.google.com`
   - и другие проверочные домены, которые реально видны в DNS-логе телефонов (у Xiaomi и части других вендоров они свои). Логировать все запросы на время тестов.
2. **HTTP на порту 80** (nginx): на `/generate_204` и `/gen_204` отвечать `204 No Content`.
   - HTTPS-пробу подменить нельзя без доверенного сертификата, поэтому на одну заглушку полагаться нельзя. Основная защита — привязка сокетов приложения к Wi-Fi (см. раздел 7).
3. **Backend приложения** — `[TBD]`: порты, протокол, нужен ли вообще relay. Если есть, его адрес всегда `<SERVER_IP>`.
4. **Дашборд** — `[TBD]` порт (значение задаётся в настройках; в публичном репозитории не фиксируется). Работает на этом же сервере (см. раздел 8).

Если сервер недоступен, DNS-заглушка пропадает, но прямая связь телефонов по локальным адресам должна продолжать работать. Приложение не должно зависеть от сервера для базового обмена сообщениями.

## 7. Требования к мобильному приложению (сетевые)

- **Привязка к Wi-Fi.** Если Wi-Fi не прошёл проверку интернета и включена мобильная передача данных, Android может пустить трафик приложения через сотовую сеть, и локальные адреса не отвечают. Приложение должно привязывать процесс/сокеты к Wi-Fi-сети через `ConnectivityManager` (`requestNetwork` с `TRANSPORT_WIFI` + `bindProcessToNetwork`), не требуя `NET_CAPABILITY_VALIDATED`/`INTERNET`.
- **Никакой зависимости от интернета:** никаких обращений к внешним хостам, аналитике, облачным SDK.
- **Роуминг.** Телефон сам решает, когда перейти на другую точку. Неизбежны паузы от десятков миллисекунд до нескольких секунд. Приложение обязано: держать keep-alive, автоматически переподключаться с backoff, хранить очередь неотправленных сообщений и повторять отправку, не считать короткий разрыв уходом в «офлайн» (для статуса присутствия использовать тайм-аут, а не мгновенный сброс).
- **Обнаружение.** NSD/mDNS на Android капризен: после переподключения заново регистрировать и искать сервис, не полагаться только на него. Запасной путь: известный адрес `<SERVER_IP>` (если появится backend), при необходимости ручной ввод адреса.
- **Тип NSD-сервиса и порты** — `[TBD]`.
- **Формат QR контакта** (из репозитория): `MB10:CONTACT:v1:<publicKey>:<callsign>:<faction>`. Ключи ECDSA генерируются на устройстве при первом запуске.
- **Голос/фото** (вторая очередь) идут по unicast; multicast для них не нужен.
- Приложение **никогда** не обращается к API UniFi и не хранит его ключ.

## 8. Дашборд: источники данных

Дашборд работает на локальном сервере и общается с контроллером сам. Браузер и телефон к API UniFi напрямую не обращаются.

- **Официальный локальный API:** UniFi Network Integration API
  - база: `https://<GATEWAY_IP>/proxy/network/integration/v1`
  - аутентификация: заголовок `X-API-KEY`
  - требуется UniFi Network 9.3+ и UniFi OS 9.3.43+
  - ключ создаётся в консоли: Settings → Control Plane → Integrations → Create API Key (на новых версиях UniFi OS раздел Integrations рядом с Settings; названия меняются от релиза к релизу)
  - сертификат самоподписанный: сервер должен либо отключать проверку TLS для этого хоста, либо закрепить сертификат
  - ключ наследует права создавшего администратора, хранить только на сервере (переменная окружения/файл с правами 600), отозвать после игры
- **Доступные ресурсы** (по описаниям сторонних клиентов): sites, networks, WLANs, firewall, devices, clients. Набор ограничен. Точную схему брать из OpenAPI самой консоли (Settings → Integrations), не угадывать поля.
- **Чего может не хватить:** уровень сигнала клиента, история роуминга, загрузка по точкам, события. Их даёт классический (неофициальный) API `/proxy/network/api/...` с сессией по логину и паролем. Он может ломаться при обновлениях UniFi, использовать только если без него никак, и вынести в отдельный слой.
- **Идеи для экранов** `[ПРЕДЛОЖЕНИЕ]`:
  - карта/список точек: онлайн/офлайн, проводная или mesh, число хопов, число клиентов
  - список клиентов: имя, IP, к какой точке подключён, уровень сигнала
  - лента событий: точка упала, точка ушла в mesh, клиент перешёл на другую точку
  - здоровье сервисов: DNS-заглушка, HTTP 204, backend приложения
  - сопоставление присутствия из приложения (callsign) с клиентом сети

## 8а. Решения владельца по открытым вопросам `[ФАКТ]`
- Порт дашборда/коллектора выбран владельцем; адрес сервера приложение получает из QR персонажа от мастера (docs/provisioning-qr.md) или из настроек сборки (`mb10.collectorUrl`); в публичном коде реального адреса нет.
- Тип NSD-сервиса остаётся `_mb10chat._tcp.`.
- Отдельный relay не нужен: достаточно коллектора на `<SERVER_IP>`.
- Дашборд — **только мониторинг** сети (чтение UniFi API), без управления.

### Как это реализовано в приложении (раздел 7)
| Требование | Реализация |
|---|---|
| Привязка к Wi-Fi | `presence/WifiBinder`: `requestNetwork(TRANSPORT_WIFI, без INTERNET)` + `bindProcessToNetwork`; разрешение `CHANGE_NETWORK_STATE` |
| Переподключение NSD после смены сети | `WifiBinder` → `PresenceService.refresh()`: регистрация и поиск заново, известные пиры живут отсрочку 15 с |
| Короткий разрыв ≠ офлайн | дебаунс потери пира 12 с (было 4) |
| Очередь неотправленных и повтор | `chat/OutboxStore` (таблица `outbox`, миграция Room 12→13), повтор 2/4/8/15/30/60 с, срок жизни 12 ч; деньги и передачи предметов в очередь не ставятся (`OutboxPolicy`); дубли на приёме отсекаются |
| Запасное обнаружение | heartbeat на коллектор несёт порт чата, ответ — список недавних игроков с адресом соединения; `PresenceService.updateServerPeers`. Подсказка — ещё один адрес игрока рядом с адресами NSD (не замена); адрес `127.x` (сервер видит устройство за NAT, стенд на эмуляторах) — берётся только порт, host — из записи NSD того же игрока |
| Несколько адресов игрока | kit `PeerTable`: по источникам (NSD с историей из 3 адресов, статические, подсказки сервера); лучший адрес первым — свежий или последний удачный; `NOT_REACHED` уводит адрес в конец, пока по нему снова не дойдёт (исход каждой отправки — `LineSocketClient` → `reportSend`). Отправка — только `PeerDirectory.send(ключ, строка)`: перебирает их по порядку, к следующему — после `NOT_REACHED`; экраны видят `OnlinePlayer` без адреса |
| Без зависимости от интернета | внешних хостов, STUN/TURN и облачных SDK в приложении нет |

Проверки на стенде: сценарии `wifi-bind` и `network-drop` (`scripts/e2e`). Роуминг между точками и нагрузка 30–100 телефонов на эмуляторах не воспроизводятся — это приёмочные проверки 3 и 5 на реальных телефонах.

## 10. Приёмочные проверки

1. Отключён любой внешний канал: телефоны видят друг друга, чат идёт, статус присутствия работает.
2. На Android не появляется «Подключено, интернета нет» с последующим отключением; при включённой мобильной передаче трафик приложения идёт по Wi-Fi.
3. Прогулка между зонами с `ping -i 0.2` до сервера в Termux: потери пакетов и длительность пауз при каждом переходе, на 3–4 моделях.
4. Отключение проводной точки: клиенты перебираются на соседние, дашборд показывает падение.
5. Нагрузка на 30–50, затем 100 телефонов: NSD-обнаружение, чат, число клиентов на точку.
6. Проверка уровня сигнала на границах зон около −67 дБм и у mesh-точек не хуже −60 дБм до родителя.
