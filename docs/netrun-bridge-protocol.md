# Протокол Моста «Сеть» (контракт C1)

Контракт между Мостом (`:netrun-bridge`) и его клиентами по WebSocket: сервер мира (Godot), инструменты мастера, фейки
(F1). Телефон с Мостом по WebSocket не говорит — только карточками kit `Handover` (раздел 8). По этому документу пишутся
B0 (хранилище), B1 (WebSocket), B3 (операции с ценностями), F1 (фейки), V2 (токен терминала), M2/M3/M5.

Версия протокола — **1** (`NETRUN_PROTO = 1`). Она не связана с `WireVersion` приложения: канал телефона живёт по своим
версиям kit.

## 1. Транспорт

- `ws://<мини-ПК>:7410/netrun/v1` (порт — в конфиге Моста; на площадке мини-ПК в LAN, TLS нет — дружеская модель угроз).
- Один текстовый кадр — одно JSON-сообщение в UTF-8. Бинарные кадры — ошибка `bad_request` и закрытие.
- Время — миллисекунды Unix (`Long`), ставит **только Мост**. Числа — целые; JSON без `NaN`.
- Пинг — кадры WebSocket ping/pong: клиент раз в 10 с; Мост закрывает соединение после 30 с тишины. Подписки при обрыве
  пропадают — после переподключения клиент делает `hello` и `sub` заново (получит снимок, раздел 4).
- Неизвестные поля в сообщениях и в `data` игнорируются (вперёд-совместимость); неизвестный `op` — ошибка `bad_request`.

## 2. Конверт

Запрос клиента:

```json
{"v": 1, "cid": "w-1842", "op": "get", "type": "node", "id": "node_07"}
```

| Поле | Что |
|---|---|
| `v` | версия протокола, всегда 1 |
| `cid` | номер запроса в рамках соединения, любая строка ≤ 64 символов; Мост возвращает его в `re`. Для сопоставления ответа, **не** для защиты от повтора |
| `op` | операция (разделы 3–7) |

Ответ — ровно один на каждый запрос, в порядке обработки (не обязательно в порядке отправки):

```json
{"v": 1, "re": "w-1842", "ok": true, "doc": {"type": "node", "id": "node_07", "ver": 12, "created": 1790000000000, "updated": 1790000412000, "data": {"tier": "STANDARD"}}}
```

Ошибка:

```json
{"v": 1, "re": "w-1843", "ok": false, "err": {"code": "version_conflict", "msg": "версия 12, а не 11", "doc": {"type": "node", "id": "node_07", "ver": 12, "created": 1790000000000, "updated": 1790000412000, "data": {"tier": "STANDARD"}}}}
```

Сообщение от Моста без запроса (поток изменений) — без `re`, с `push`:

```json
{"v": 1, "push": "chg", "seq": 50231, "doc": {"type": "session", "id": "s_9f2c", "ver": 3, "created": 1790000500000, "updated": 1790000530000, "data": {"state": "active"}}}
```

### Коды ошибок

| `code` | Когда | Что делать клиенту |
|---|---|---|
| `bad_request` | не JSON, нет поля, неверный тип, неизвестный `op` | ошибка в коде клиента, не повторять |
| `unsupported_version` | `v` или `proto` в `hello` не поддержан; соединение закрывается | обновить сборку |
| `unauthorized` | нет `hello` или неверный ключ роли | — |
| `forbidden` | роли эта операция не разрешена (раздел 3) | — |
| `not_found` | документа нет | — |
| `exists` | создание (`ver: 0`), а документ уже есть; в `err.doc` — текущий | перечитать |
| `version_conflict` | `ver` не совпал; в `err.doc` — текущий | перечитать, применить правку заново |
| `value_field` | общий `put`/`del` трогает ценность или тип `item`, `deck`, `payout`, `op_rid` (раздел 5) | использовать операцию из раздела 6 |
| `wrong_owner` | предмет сейчас не у того владельца, что ждёт операция; в `err.doc` — предмет | перечитать, это не повод повторять с новым `rid` |
| `protected_item` | операция уводит защищённого демона не на телефон | ошибка логики сервера мира |
| `session_state` | сессия не в нужном состоянии (например, `take` в закрытой) | перечитать сессию |
| `rid_mismatch` | `rid` уже использован с **другими** параметрами; ничего не сделано | ошибка в коде клиента |
| `req_state` | `master.decide` по уже решённому запросу другим решением (раздел 6a); в `err.doc` — запрос | показать мастеру итог |
| `bad_token` | токен терминала не сошёлся | очки не пускать |
| `cooldown` | `run.breach`: узел остывает для этого нетраннера (6.6); в `err.doc` — документ `runner` | показать «ОСТЫВАЕТ», награды нет |
| `claimed` | `op.take_from_node`: хранилище открыто взломом другой сессии (6.6); в `err.doc` — предмет | не брать, это не повод повторять |
| `loaded_item` | `op.give_item`: предмет — рабочий демон (ПРОГРАММЫ), отдавать нельзя (5, «Рабочие и груз») | ошибка логики сервера мира |
| `no_decrypter` | `op.decrypt_item`: нет рабочего DECRYPT тира ≥ тира шарда | не предлагать расшифровку |
| `ram_exceeded` | вход: RAM вне 6..13 или демоны не помещаются в RAM (раздел 8) | — (дека уже возвращается) |
| `internal` | сбой Моста; транзакция откатилась целиком | повторить **тот же** запрос (с тем же `rid`) |

## 3. Вход: `hello`, роли

Первое сообщение после подключения — `hello`. До него любой другой `op` → `unauthorized`.

```json
{"v": 1, "cid": "1", "op": "hello", "proto": 1, "role": "world", "client": "world-main", "key": "k8w2…"}
```

```json
{"v": 1, "re": "1", "ok": true, "proto": 1, "bridge": "0.3.0", "now": 1790000000000, "world_pub": "MFkwEwYH…"}
```

- `key` — общий секрет роли из конфига Моста (`roles.world.key`, `roles.master.key`); на площадке лежит в конфиге сервера
  мира и инструментов мастера. Модель угроз дружеская: это защита от ошибки, а не от взлома.
- `client` — имя клиента; вместе с ролью — пространство имён `rid` (раздел 6): `world-main` и `master-anna` не пересекутся.
- `world_pub` — публичный ключ мира (получатель карточек на телефоне).

| Операция | `world` (сервер мира) | `master` (инструменты) | `test` (фейки, только если Мост запущен с `--test`) |
|---|---|---|---|
| `get`, `list`, `sub`, `unsub` | да | да | да |
| `put`, `del` (кроме ценностей) | типы `node`, `session` (только `data.world`), `alert` | все типы | все |
| `terminal.auth`, `session.confirm`, `session.abort` | да | `session.abort` | да |
| `terminal.beat` | да | нет | да |
| `op.take_from_node`, `op.leave_in_node`, `op.issue_to_phone`, `run.finish`, `run.breach`, `op.give_item`, `op.decrypt_item` | да | да (ручной запуск — «кнопка раньше автоматики») | да |
| `master.pause`, `master.link`, `master.goal`, `master.goal_clear`, `master.template_apply` | нет | да | да |
| `master.decide`, `master.reply` | нет | да | да |
| `master.gate`, `net.query` | да | да | да |
| `op.submit_deck` | нет | нет | да (у настоящего Моста его вызывает только приём карточек с телефона, раздел 8) |

## 4. Документы: чтение, запись, подписка

### Схема документа

```json
{"type": "node", "id": "node_07", "ver": 12, "created": 1790000000000, "updated": 1790000412000, "data": {}}
```

| Поле | Что |
|---|---|
| `type` | тип, `[a-z_]{1,32}` (раздел 5) |
| `id` | `[A-Za-z0-9_.:-]{1,64}`; пара `type`+`id` уникальна; одинаковый `id` в разных типах связывает их (`node/node_07` и `node_cfg/node_07`) |
| `ver` | целое ≥ 1; +1 на **каждое** изменение (общим `put` или операцией с ценностью) |
| `created`, `updated` | время Моста; `updated` — по нему видно, что источник замолчал |
| `data` | JSON-объект; схема — по типу (раздел 5) |

### `get`

```json
{"v": 1, "cid": "2", "op": "get", "type": "terminal", "id": "t03"}
```
```json
{"v": 1, "re": "2", "ok": true, "doc": {"type": "terminal", "id": "t03", "ver": 4, "created": 1790000000000, "updated": 1790000300000, "data": {"node": "node_07", "label": "Подвал, стойка 3"}}}
```

Нет документа — `not_found`.

### `list` — все документы типа

```json
{"v": 1, "cid": "3", "op": "list", "type": "node"}
```
```json
{"v": 1, "re": "3", "ok": true, "seq": 50230, "docs": [{"type": "node", "id": "node_07", "ver": 12, "created": 1790000000000, "updated": 1790000412000, "data": {"tier": "STANDARD"}}]}
```

Фильтров нет (масштаб — сотни документов). `seq` — номер последнего изменения в Мосте на момент снимка.

### `put` — запись с проверкой версии

`ver` — версия, которую клиент видел; `0` — создать (документа быть не должно). `data` заменяется **целиком**.

```json
{"v": 1, "cid": "4", "op": "put", "type": "node", "id": "node_07", "ver": 12, "data": {"tier": "STANDARD", "lockdown_until": 1790000900000}}
```
```json
{"v": 1, "re": "4", "ok": true, "doc": {"type": "node", "id": "node_07", "ver": 13, "created": 1790000000000, "updated": 1790000420000, "data": {"tier": "STANDARD", "lockdown_until": 1790000900000}}}
```

Версия устарела — `version_conflict` с текущим документом; клиент перечитывает и решает заново. Повтор `put` после обрыва
безопасен: если первая запись прошла, второй придёт `version_conflict`, и по `err.doc` видно, что правка уже там.

### `del`

```json
{"v": 1, "cid": "5", "op": "del", "type": "alert", "id": "al_17", "ver": 2}
```
```json
{"v": 1, "re": "5", "ok": true}
```

### `sub` / `unsub` — поток изменений

```json
{"v": 1, "cid": "6", "op": "sub", "types": ["node", "session", "item", "terminal", "settings"]}
```
```json
{"v": 1, "re": "6", "ok": true, "seq": 50230, "docs": [{"type": "node", "id": "node_07", "ver": 13, "created": 1790000000000, "updated": 1790000420000, "data": {"tier": "STANDARD"}}]}
```

- Ответ — снимок всех документов этих типов на `seq`; затем каждое изменение с `seq` больше снимка приходит пушем `chg`
  (полный документ после изменения). Удаление — `chg` с `"deleted": true` и последней версией документа.
- `seq` — сквозной счётчик изменений Моста, хранится в SQLite, после перезапуска продолжается. Изменения одной транзакции
  (операция с ценностью трогает несколько документов) приходят подряд с одним `seq` и полем `"last": true` у последнего —
  клиент применяет их пачкой.
- Порядок пушей совпадает с порядком `seq`. Ответ на `sub` приходит раньше любого `chg` с большим `seq`.
- Повторный `sub` в том же соединении добавляет типы; снимок — по всем типам запроса, в том числе уже подписанным (сервер мира с несколькими узлами подписывается и получает полный снимок каждый раз). `unsub` `{"types": [...]}` — убрать.
- Пропусков не бывает, пока соединение живо. После обрыва — `hello` + `sub` заново, снимок заменяет всё, что было у клиента.
  Так же сервер мира берёт состояние после своего перезапуска (M5).

Два кадра одной транзакции:

```text
{"v": 1, "push": "chg", "seq": 50231, "last": false, "doc": {"type": "item", "id": "it_4c1a", "ver": 3, "created": 1790000500000, "updated": 1790000530000, "data": {"owner": "deck:s_9f2c", "kind": "SHARD", "payload": "…", "protected": false, "origin": "node:node_07"}}}
{"v": 1, "push": "chg", "seq": 50231, "last": true, "doc": {"type": "deck", "id": "s_9f2c", "ver": 4, "created": 1790000500000, "updated": 1790000530000, "data": {"items": ["it_01aa", "it_02bb", "it_4c1a"], "protected": "it_01aa"}}}
```

## 5. Типы документов (этапы 0–4)

«Ценность» — поле, которое меняется только операциями раздела 6; общий `put`/`del`, который его меняет (или создаёт/удаляет
документ целиком помеченного типа), получает `value_field`.

| Тип | `id` | Кто пишет | Ценность |
|---|---|---|---|
| `node` | `node_07` | мастер, сервер мира | `eddies` |
| `node_cfg` | как у узла | мастер | — |
| `terminal` | `t03` | мастер; `terminal.beat` сервера мира | — |
| `session` | `s_<16 hex>` | Мост; сервер мира — только `data.world` | весь документ, кроме `data.world` |
| `deck` | как у сессии | только Мост | весь документ |
| `item` | `it_<16 hex>` | только Мост | весь документ |
| `runner` | `r_<32 hex>` — первые 32 hex SHA-256 ключа игрока (ключ — в `data.key`) | Мост, мастер | — |
| `settings` | `global`, `rules`, … | мастер | — |
| `alert` | `al_<n>` | Мост (аудитор, раздел 6a), сервер мира; снимает мастер | — |
| `sec_alert` | `sa_<16 hex>` | только Мост (`run.breach`, 6.6); мастер может удалить | — |
| `master_req`, `net_query` | `<вид>:<ссылка>`, `nq_<n>` | только Мост (раздел 6a) | — |
| `template` | `tpl_<имя>` | мастер | — |

**`node`** — постоянное состояние узла.
```json
{"type": "node", "id": "node_07", "ver": 13, "created": 1790000000000, "updated": 1790000420000,
 "data": {"title": "Склад «Арасаки»", "tier": "STANDARD", "tutorial": false, "lockdown_until": 0, "eddies": 300}}
```
`tier` — как `Tier` приложения (`NIGHTMARE` и т. д.); `lockdown_until` — 0 или время конца локдауна; `eddies` — запас эдди в
узле (ценность, меняет только `op.take_from_node`). Предметы узла — документы `item` с `owner: "node:node_07"`.

**`node_cfg`** — числа и наполнение для правил и сервера мира (ICE, пороги). Схема свободная, её задают G/N-карточки.
```json
{"type": "node_cfg", "id": "node_07", "ver": 2, "created": 1790000000000, "updated": 1790000100000, "data": {"ice": [{"kind": "SOFT", "at": [3, 0, 7]}], "trace_per_s": 2}}
```

**`terminal`** — стойка с очками.
```json
{"type": "terminal", "id": "t03", "ver": 4, "created": 1790000000000, "updated": 1790000300000,
 "data": {"label": "Подвал, стойка 3", "node": "node_07", "token_sha256": "9b1f…", "silent": false}}
```
`token_sha256` — SHA-256 токена очков в hex (сам токен в документ не попадает, раздел 7). `silent` — флаг правила B2
«терминал молчит».

**`session`** — один забег одного игрока на одном терминале.
```json
{"type": "session", "id": "s_9f2c41d07a3e5b60", "ver": 3, "created": 1790000500000, "updated": 1790000530000,
 "data": {"state": "active", "terminal": "t03", "node": "node_07", "runner": "MFkwEwYH…", "callsign": "Призрак",
          "enter_rid": "e-7d1c", "confirmed_at": 1790000530000, "loot_eddies": 0,
          "ram": 6, "loaded": ["it_01aa7c90e1d4a3f5", "it_02bb7c90e1d4a3f5"], "breach": null, "opened": [],
          "outcome": null, "finished_at": 0, "world": {"connected": true, "trace": 0}}}
```
- `ram` — RAM персонажа (6..13) из запроса входа (раздел 8); пишет `op.submit_deck`, дальше не меняется. Буфер взлома хранилища = `ram`.
- `loaded` — id всех предметов, сданных при входе (с защищённым); пишет `op.submit_deck`, дальше не меняется. По нему делится дека
  (ниже, «Рабочие и груз»).
- `breach` — итог последнего `run.breach` сессии (6.6): `{"n", "node", "tier", "outcome", "effects", "eddies", "opened_n", "exhausted",
  "alert", "at"}`; `null` — взломов не было. `opened` — хранилища, открытые взломами этой сессии: `[{"item", "node", "until"}]`
  (истёкшие удаляются при следующей записи). Оба поля пишет только Мост.
- `world.breach_n` — номер последней начатой попытки взлома (пишет сервер мира `put` **до** показа сетки; 6.6).
Состояния: `pending` (дека сдана, очки показывают «Подключается: <позывной>») → `active` (курок нажат) → `closed`
(`outcome`: `clean` | `emergency` | `soft_ice` | `black_ice` | `aborted`). Одна сессия не в `closed` на терминал и на игрока.
`world` — свободный объект сервера мира (подключён ли, trace, `trace_level`, `effects`, `hunt`): его можно писать `put`, остальное — нет.
`world.hunt: true` — за сессией началась охота Black ICE: Мост шлёт быстрое событие `ice.hunt` (docs/netrun-world-records.md, раздел 8); конец охоты
событием не является, поле можно оставить `true` или вернуть в `false`.
`world.node` — **текущий узел** сессии (граф узлов, W1): сервер мира пишет его при входе и при каждом переходе через тоннель. От
него зависят операции с ценностями: `take_from_node`, `leave_in_node`, `run.finish` проверяют `node` по `world.node`, а если его
нет — по `session.node` (узел, куда сессию приняли); добыча и «мёртвая дека» ложатся в узел `node` вызова, то есть в текущий.
Правило сигнала СБ берёт фракцию, уровень и название узла тоже по текущему узлу.

**Рабочие и груз.** Предмет в `deck:<s>` — **рабочий** (ПРОГРАММЫ деки), если его id есть в `session.loaded`; всё остальное в
`deck:<s>` — **груз** (ГРУЗ: взятое в узле, полученное от других нетраннеров). Рабочий демон работает в забеге и занимает RAM; груз не
работает, его можно отдать (6.7), при исходе он — добыча. Признак по `origin` для этого не годится: у наполнения мастером
`origin: master:*`, у «мёртвой деки» — `phone:<погибший>` (тот же погибший, взяв свою мёртвую деку в новом забеге, получил бы
рабочего демона сверх RAM). Сессия без `loaded` (создана до К2): рабочий — `origin == "phone:" + runner`.

**`deck`** — что игрок принёс и что несёт сейчас; производный от `item.owner`, держится Мостом в той же транзакции.
```json
{"type": "deck", "id": "s_9f2c41d07a3e5b60", "ver": 4, "created": 1790000500000, "updated": 1790000530000,
 "data": {"items": ["it_01aa", "it_02bb", "it_4c1a"], "protected": "it_01aa"}}
```

**`item`** — предмет внутри Сети.
```json
{"type": "item", "id": "it_02bb7c90e1d4a3f5", "ver": 2, "created": 1790000500000, "updated": 1790000500000,
 "data": {"owner": "deck:s_9f2c41d07a3e5b60", "kind": "DAEMON", "payload": "<строка ItemPayload как в карточке>",
          "protected": false, "origin": "phone:MFkwEwYH…", "in_transfer": "tr_88e1", "out_transfer": null, "handover": null}}
```
- `origin` — откуда предмет: `phone:<ключ>` (принесён игроком), `node:<узел>` (добыча/наполнение узла), `master:<client>` (создан мастером, `master.stock_node`).
- `payload` — строка содержимого из карточки (`ItemPayload`) **байт в байт**; менять её никто не вправе. Единственное исключение —
  `op.decrypt_item` (6.8): одно поле флага «расшифрован».
- `daemon` / `shard` (M5b) — разбор `payload` для сервера мира, который формата карточки не знает. Мост пишет поле сам: при
  приёме карточки (`op.submit_deck`-путь, раздел 8) и при старте — документам без поля (принятым раньше), через `:rules`
  `ItemPayloadCodec`. Не разобралось — поля нет. Для `kind: "DAEMON"` — `"daemon": {"effect": "GHOST", "tier": 2,
  "name": "Призрак", "cells": ["1C", "BD"]}` (`effect` — имя `DaemonEffect`, `tier` — 1..3, `cells` — цепочка кодов).
  Для `kind: "SHARD"` — `"shard": {"tier": 1, "title": "…", "decrypted": true, "encrypted": false}` (тело и сумма не выносятся;
  `encrypted` = `decryptAction && !decrypted`, как ярлык «зашифрован» телефона; у документа без `encrypted` сервер мира считает
  `!decrypted`, К7 дописывает поле старым документам). Сервер мира
  берёт параметры эффекта по уровню из своих данных (`netrun/data/daemons/effects/<ЭФФЕКТ>.json`); эффект, которого в Сети
  ещё нет, — демон в деке виден, но применение отвечает `effect_unsupported` с причиной.
- `owner` — ровно один, из списка:

| `owner` | Значит |
|---|---|
| `inbox:<ключ>` | карточка с телефона принята (чек отправлен), деку ещё не собрали |
| `deck:<сессия>` | в деке забега (принесённое и взятое в узле) |
| `node:<узел>` | лежит в узле (наполнение мастером, оставленная добыча, «мёртвая дека») |
| `outbox:<ключ>` | выдаётся на телефон: карточка Handover в пути; `handover` — `PENDING`/`DELIVERED` |
| `phone:<ключ>` | чек получен — предмет ушёл из Сети; документ остаётся для журнала и аудитора |
| `burned:<сессия>` | сгорел (аварийный выход под охотой Black ICE); документ остаётся |
| `burned:master` | убран мастером из узла (`master.unstock_node`); документ остаётся для журнала, сессии у него нет |

**`runner`** — нетраннер с точки зрения Сети. Id документа — `r_` + первые 32 hex SHA-256 ключа игрока (сам ключ длиннее предела id в
64 символа); ключ — **обычный base64** X.509/SPKI, как `Ecdsa.encodeKey` в kit и у телефонов (не base64url), лежит в `data.key`.
```json
{"type": "runner", "id": "r_3f9a…(32 hex)", "ver": 5, "created": 1789990000000, "updated": 1790000600000,
 "data": {"key": "MFkwEwYH…", "callsign": "Призрак", "blocked": false, "blocked_reason": null, "runs": 3, "tutorial_done": true,
          "re_entry_after": 0, "allowed": true, "faction": "Корпа"}}
```
- `key`, `callsign`, `runs`, `tutorial_done` — Мост (`runs` +1 и `tutorial_done: true` при `run.finish`; при входе обновляется только `callsign`).
- `blocked` ставит Мост при `black_ice`, снимает мастер; `blocked_reason` — текст причины. `re_entry_after` — мс Unix конца паузы повторного входа после `soft_ice` (0 — нет). `tutorial_done: false` — первый вход идёт в учебный узел.
- `allowed` — допуск нетраннера в Сеть, ставит мастер (коллектор). Учитывается только при `settings/global.require_allowed == true`:
  тогда `op.submit_deck` без документа `runner` или без `allowed: true` отказывает `session_state` («нет допуска в Сеть»), предметы
  возвращаются на телефон, как при `blocked`. `newRunner` его не ставит.
- `faction` — фракция нетраннера, пишет мастер/коллектор; нужна правилу сигнала СБ (`SecAlertRules.decide`: на своём узле фракции сигнала нет).
- Мастер может создать документ `runner` до первого входа (`runs: 0`, `tutorial_done: false`, нужны `key` и `allowed`/`faction`): Мост при входе обновит только `callsign`.
- `breach_cooldown` — `{"<узел>": <мс Unix конца остывания>}`: узел остывает для этого нетраннера после взлома с совпадением
  (6.6). Пишет Мост в `run.breach` (истёкшие ключи удаляет той же записью); сервер мира читает из снимка (подписка на `runner`) и не
  предлагает взлом; мастер снимает остывание, удалив ключ общим `put`.

**`sec_alert`** — сигнал СБ, решённый `run.breach` и ждущий отправки (6.6). Переживает рестарт Моста, в отличие от памяти правила P3.
```json
{"type": "sec_alert", "id": "sa_5e0c19ab77d2f310", "ver": 1, "created": 1790000600000, "updated": 1790000600000,
 "data": {"state": "pending", "send_at": 1790000720000, "ttl_at": 1790002400000, "faction": "Арасака", "node": "node_07",
          "title": "Склад «Арасаки»", "tier": 2, "callsign": "Призрак", "precise_at": null, "session": "s_9f2c41d07a3e5b60", "rid": "breach:s_9f2c41d07a3e5b60:3"}}
```
`callsign`/`precise_at` — `null`, если не раскрываются (`AlertPlan`). Правило `sec_alert` Моста (раз в `sec_alert_tick_s`, как P3) в
`send_at` шлёт телефонам `settings/sec.factions[faction]`, которые сейчас в сети, то же сообщение `SEC//MB10`, что P3 (`containerName` —
`title`, без номера терминала: взлом не уровень trace), и ставит `state: sent`; после `ttl_at` (решение + 30 мин) — `expired` без отправки.
Рубильник связи выключен — ждёт, как P3. Телефоны вне сети сигнал не получают (как P3 и `SecAlertStore`). Склейка «полное сообщение раз в
15 мин на узел» — `SecAlertAggregator` из `:rules` в момент отправки (`BreachAlertRule`; память Моста, после рестарта окно начинается заново, как в приложении).
Правило пишет `sent`/`expired` **до** отправки: сбой между ними теряет один сигнал, но не шлёт его дважды. Документ `sec_alert` общим `put` писать нельзя
(`value_field`), удалять можно.

**`settings`** — числа правил и Моста; мастер правит на ходу.
```json
{"type": "settings", "id": "global", "ver": 7, "created": 1789990000000, "updated": 1790000000000,
 "data": {"confirm_timeout_s": 120, "inbox_timeout_s": 300, "disconnect_grace_s": 20, "soft_ice_reentry_pause_s": 180,
          "node_lockdown_s": 600, "terminal_silent_s": 30, "auditor_period_s": 60, "tutorial_node": "node_00", "require_allowed": false}}
```
- `soft_ice_reentry_pause_s` (по умолчанию 180) — пауза **нетраннера** после выброса Soft ICE: `runner.re_entry_after = конец забега + пауза`, вход
  в любой узел отказан (`session_state`) до этого срока.
- `node_lockdown_s` (по умолчанию 600) — локдаун **узла** для всех после выброса: `node.lockdown_until = конец забега + node_lockdown_s`.
  Это отдельная настройка (решение D1, netrun.md «Открытые вопросы», п. 1). Если в уже созданном документе настроек её нет — берётся 600,
  а не `soft_ice_reentry_pause_s`. Те же 600 — срок цели `lockdown` мастера без `value` (`master.goal`).
`require_allowed` — вход в Сеть только у нетраннеров с `runner.data.allowed == true` (по умолчанию нет/`false`: допуск не проверяется).

**`alert`** — тревога для дашборда (аудитор, сервер мира).
```json
{"type": "alert", "id": "al_17", "ver": 1, "created": 1790000700000, "updated": 1790000700000,
 "data": {"kind": "item_owner", "msg": "it_02bb: владелец deck:s_9f2c, но сессия закрыта", "items": ["it_02bb"]}}
```

## 6. Операции с ценностями

Общие правила для `op.*` и `run.finish`:

- **`rid`** — номер запроса, строка ≤ 128 символов, уникальна в пространстве `role/client`. Мост хранит `rid` вместе с
  параметрами и ответом (в той же транзакции, что и изменения, — в SQLite, бессрочно на сезон).
- **Повтор** с тем же `rid` и теми же параметрами не выполняется второй раз: возвращается сохранённый ответ с
  `"replayed": true` (даже если с тех пор документы изменились). Тот же `rid` с другими параметрами — `rid_mismatch`, ничего
  не сделано. Ответ с ошибкой (`wrong_owner`, `session_state`…) тоже сохраняется и повторяется; `internal` и `bad_request` — нет
  (транзакции не было).
- **Обрыв.** Не получил ответа — после переподключения отправить **тот же** запрос с тем же `rid`; новый `rid` для того же
  намерения запрещён. Сервер мира одноразовый, поэтому `rid` строит **детерминированно** из того, что переживёт его
  перезапуск: `take:<сессия>:<предмет>`, `leave:<сессия>:<предмет>`, `finish:<сессия>`. Тогда после рестарта он может
  повторить запрос вслепую, а снимок `sub` и так покажет итог.
- Каждая операция — **одна транзакция**: все документы (`item`, `deck`, `session`, `node`) меняются вместе или никак; их
  `chg` приходят с одним `seq`. Ошибка посреди — откат целиком, предмет остаётся у прежнего владельца.
- Ни одна операция не создаёт и не уничтожает документ `item`, кроме `op.submit_deck` (создаёт из принятой карточки).
  `burned` и `phone` — тоже владельцы, документ остаётся. Аудитор (`settings.auditor_period_s`) проверяет: у каждого `item`
  ровно один владелец из таблицы; `deck:<s>` — только у не закрытой сессии `s`; `deck.items` = предметы с `owner: deck:<s>`;
  `outbox` без исходящей карточки не бывает. Расхождение → документ `alert`.
- Защищённый демон (`protected: true`) может уйти только в `outbox`/`phone` своего владельца. Любая другая цель —
  `protected_item`.

### 6.1 `op.submit_deck` — сдать деку

Вызывает приём карточек телефона (раздел 8), когда пришёл подписанный запрос входа и все перечисленные в нём карточки уже
приняты (лежат в `inbox:<ключ>`). По WebSocket — только роль `test`.

```json
{"v": 1, "cid": "40", "op": "op.submit_deck", "rid": "enter:e-7d1c", "runner": "MFkwEwYH…", "callsign": "Призрак",
 "terminal": "t03", "items": ["it_01aa7c90e1d4a3f5", "it_02bb7c90e1d4a3f5"], "protected": "it_01aa7c90e1d4a3f5"}
```
```json
{"v": 1, "re": "40", "ok": true, "replayed": false, "session": "s_9f2c41d07a3e5b60", "state": "pending"}
```

Необязательное поле `"ram": 8` — RAM из запроса входа v2 (раздел 8); без него — правило v1. Оно входит в параметры `rid` **только
если передано**: повтор запроса v1, сохранённого до обновления Моста, не получает `rid_mismatch`.

Проверки: `runner` не `blocked`; нет его открытой сессии; терминал свободен; узел терминала не в локдауне (иначе
`session_state`); все `items` — `inbox:<runner>`; `protected` ∈ `items`; RAM (раздел 8, иначе `ram_exceeded`). Итог: `session` в
`pending` (узел — учебный, если `tutorial_done: false`) с `ram` и `loaded` = `items`, `deck`, предметы → `deck:<сессия>`. **Отказ** (любая проверка) — предметы остаются в `inbox`, и Мост
сам выдаёт их обратно на телефон (`op.issue_to_phone` с `rid` `refund:<rid входа>`): дека, сданная на занятый терминал, не
застревает. **Повтор**: тот же ответ, вторая сессия не создаётся. **Обрыв**: запрос внутренний, ответ уходит на телефон
чеком на запрос входа (раздел 8); телефон, не получивший чека, шлёт запрос входа заново с тем же `rid`.

Сессия в `pending` дольше `confirm_timeout_s` или `session.abort` → `closed`/`aborted`, вся дека → на телефон.

### 6.2 `op.take_from_node` — взять из узла

Сервер мира: игрок взял шард (или эдди MINER-ом).

```json
{"v": 1, "cid": "41", "op": "op.take_from_node", "rid": "take:s_9f2c41d07a3e5b60:it_4c1a0b2e9d7f6a81",
 "session": "s_9f2c41d07a3e5b60", "node": "node_07", "item": "it_4c1a0b2e9d7f6a81"}
```
```json
{"v": 1, "re": "41", "ok": true, "replayed": false, "item": {"type": "item", "id": "it_4c1a0b2e9d7f6a81", "ver": 3, "created": 1790000000000, "updated": 1790000600000, "data": {"owner": "deck:s_9f2c41d07a3e5b60", "kind": "SHARD", "payload": "…", "protected": false, "origin": "node:node_07", "in_transfer": null, "out_transfer": null, "handover": null}}}
```

Эдди — вместо `item` поле `"eddies": 50`: `node.eddies` −50, `session.loot_eddies` +50; запаса меньше — `wrong_owner`.

Проверки: сессия `active`; `node` — текущий узел сессии (`world.node`, иначе `session.node`), иначе `bad_request`; предмет `node:<node>`. Иначе — `session_state`/`wrong_owner` (в `err.doc` — где предмет сейчас:
двое схватили один шард — второй получает `wrong_owner` с `owner: deck:<первый>`). Предмет есть в живом (`until` > сейчас)
`opened` **другой** не закрытой сессии — `claimed` (хранилище открыто чужим взломом, 6.6). Своё открытие Мост не требует: «брать
только из открытого» проверяет сервер мира (учебный узел и забеги до К3 берут без взлома). **Повтор**: тот же ответ, предмет не
«берётся» второй раз. **Обрыв**: повторить с тем же `rid`; если сервер мира перезапустился — тот же детерминированный `rid`.

### 6.3 `op.leave_in_node` — оставить в узле

Сервер мира: игрок бросил предмет, или при исходе добыча/«мёртвая дека» остаётся в узле.

```json
{"v": 1, "cid": "42", "op": "op.leave_in_node", "rid": "leave:s_9f2c41d07a3e5b60:it_4c1a0b2e9d7f6a81",
 "session": "s_9f2c41d07a3e5b60", "node": "node_07", "item": "it_4c1a0b2e9d7f6a81"}
```
```json
{"v": 1, "re": "42", "ok": true, "replayed": false, "item": {"type": "item", "id": "it_4c1a0b2e9d7f6a81", "ver": 4, "created": 1790000000000, "updated": 1790000650000, "data": {"owner": "node:node_07", "kind": "SHARD", "payload": "…", "protected": false, "origin": "node:node_07", "in_transfer": null, "out_transfer": null, "handover": null}}}
```

Проверки: `node` — текущий узел сессии (`world.node`, иначе `session.node`), иначе `bad_request`; предмет `deck:<session>`; не `protected` (`protected_item`); сессия не `closed`. **Повтор** и **обрыв** — как 6.2.

### 6.4 `op.issue_to_phone` — выдать на телефон

Предметы из деки (или из `inbox` при отказе входа, или из узла — ручная выдача мастером) и эдди уходят на телефон
карточками Handover от ключа мира.

```json
{"v": 1, "cid": "43", "op": "op.issue_to_phone", "rid": "master-anna:give:17", "runner": "MFkwEwYH…",
 "items": ["it_4c1a0b2e9d7f6a81"], "eddies": 0, "reason": "ручная выдача"}
```
```json
{"v": 1, "re": "43", "ok": true, "replayed": false, "transfers": [{"item": "it_4c1a0b2e9d7f6a81", "transfer": "tr_c0de11"}], "eddies_transfer": null}
```

В одной транзакции: предметы → `outbox:<runner>`, `handover: PENDING`, `out_transfer` — id новой исходящей карточки; карточки
кладутся в `Outbox` Моста (kit). Дальше — обычный `Handover`: `deliver` ставит `DELIVERED` до отправки, откат в `PENDING`
только при `NOT_REACHED`; **`UNKNOWN` не повторяется по другому адресу и не откатывается**; по чеку (`confirmByReceipt`)
предмет → `phone:<runner>`. Адрес телефона — из подсказок коллектора и статического пира, отправка — через `PeerDirectory`.
Эдди — денежная карточка от ключа мира на `eddies` (эмиссия). **Повтор**: тот же ответ, вторых карточек нет. **Обрыв**:
ответ мог не дойти, но карточки уже в `Outbox` и доставятся; повторить с тем же `rid`. Ответ `ok` значит «выдача записана»,
а не «телефон получил» — это видно по `item.owner`.

### 6.5 `run.finish` — исход забега

Сервер мира закрывает сессию одним вызовом: какие предметы куда. Это пачка операций 6.3/6.4 и сгорания в одной транзакции —
чтобы рестарт сервера мира посреди выхода не оставил сессию наполовину разобранной.

```json
{"v": 1, "cid": "44", "op": "run.finish", "rid": "finish:s_9f2c41d07a3e5b60", "session": "s_9f2c41d07a3e5b60",
 "outcome": "emergency", "node": "node_07", "disconnect": false,
 "moves": [{"item": "it_02bb7c90e1d4a3f5", "to": "phone"}, {"item": "it_4c1a0b2e9d7f6a81", "to": "node"}]}
```
```json
{"v": 1, "re": "44", "ok": true, "replayed": false, "session": {"type": "session", "id": "s_9f2c41d07a3e5b60", "ver": 6, "created": 1790000500000, "updated": 1790000900000, "data": {"state": "closed", "outcome": "emergency", "finished_at": 1790000900000}},
 "transfers": [{"item": "it_01aa7c90e1d4a3f5", "transfer": "tr_a1"}, {"item": "it_02bb7c90e1d4a3f5", "transfer": "tr_a2"}], "eddies_transfer": null}
```

- `to`: `phone` (как 6.4), `node` (как 6.3, в узел `node`), `burned`.
- Мост сам добавляет защищённого демона в `phone` и требует, чтобы после `moves` дека была пуста: предмет из деки, не
  упомянутый в `moves`, — `bad_request`, ничего не сделано.
- Мост проверяет `moves` по таблице исходов из netrun.md («Забег»): добыча (груз — предмет не из `session.loaded`, раздел 5; исправлено в К4:
  раньше добычей считался только `origin: node:*`, и шард из наполнения мастером, `origin: master:*`, при `soft_ice`/`emergency` уходил на
  телефон вместо узла; сервер мира делит `moves` так же, по `session.loaded` — `GrayNode.finish_moves`/`is_working_item`, для сессии без
  `loaded` — по `origin == phone:<runner>`; иначе предмет `phone:<чужой>` из мёртвой деки или отдачи ушёл бы как демон и Мост отказал бы
  `bad_request` без повтора) при `clean` — только `phone`, при
  остальных — только `node`; демоны при `black_ice` — только `node` («мёртвая дека»), при `emergency` — `phone` или `burned`
  (сервер мира знает, была ли охота), при `clean`/`soft_ice` — только `phone`. Нарушение — `bad_request`.
- `loot_eddies` уходят на телефон только при `clean`, иначе возвращаются в `node.eddies`.
- `node` — текущий узел сессии (`world.node`, иначе `session.node`), иначе `bad_request`; `to: node` кладёт предмет в него.
- Побочные изменения той же транзакции: `soft_ice` → `node.lockdown_until` узла `node` (срок `node_lockdown_s`) и `runner.re_entry_after` (срок `soft_ice_reentry_pause_s`) (пауза повторного входа на нетраннере: `op.submit_deck` в любой узел отказывает `session_state`, пока она не кончилась); `black_ice` → `runner.blocked`, `alert`
  «ФЛЭТЛАЙН» (`disconnect: true` — «обрыв до флэтлайна»); `runner.runs` +1, `tutorial_done: true`.
- **Повтор**: тот же ответ. **Обрыв**: повторить `finish:<сессия>`; если сессия уже `closed` другим `rid` — `session_state`
  с документом сессии (исход уже записан).
- Дека могла измениться между чтением и вызовом (пришёл предмет по `op.give_item`, 6.7): Мост отвечает `bad_request` «не упомянут
  в moves», запись `rid` не создаётся. Сервер мира перечитывает деку, пересобирает `moves` и шлёт **тот же** `rid` (это не новое
  намерение: без записи `rid` повтор с другими параметрами разрешён).

### 6.6 `run.breach` — итог взлома хранилища

Сервер мира: попытка взлома хранилища закончилась (буфер полон, таймер, досрочно — [дизайн деки](netrun-deck-design.md) §7.2). Сетку, ходы и совпадения считает
сервер мира (порт `BreachEngine`, golden); Мост по итогу считает ценности и последствия функциями `:rules` — эдди, MINER, выбор
хранилищ, остывание, сигнал СБ — и пишет их одной транзакцией. Учебный узел `run.breach` не зовёт (взлом без Моста).

```json
{"v": 1, "cid": "60", "op": "run.breach", "rid": "breach:s_9f2c41d07a3e5b60:3", "session": "s_9f2c41d07a3e5b60", "node": "node_07",
 "n": 3, "tier": "HARD", "selected": ["it_02bb7c90e1d4a3f5", "it_03cc7c90e1d4a3f5"], "matched": ["it_02bb7c90e1d4a3f5"],
 "active": ["GHOST"], "vaults": ["it_4c1a0b2e9d7f6a81", "it_5d2b0b2e9d7f6a81"], "open_s": 60}
```
```json
{"v": 1, "re": "60", "ok": true, "replayed": false, "outcome": "PARTIAL", "effects": ["EXTRACT_SHARD", "GHOST"], "eddies": 5,
 "loot_eddies": 5, "opened": [{"item": "it_4c1a0b2e9d7f6a81", "until": 1790000660000}], "exhausted": false,
 "cooldown_until": 1790002400000, "alert": {"id": "sa_5e0c19ab77d2f310", "send_at": 1790000720000, "callsign": false, "precise": false}}
```

| Поле | Что |
|---|---|
| `n` | номер попытки, целое ≥ 1, = `session.world.breach_n` этой попытки; `rid` = `breach:<сессия>:<n>` |
| `tier` | тир сетки, которую играл игрок: `BASE` / `HARD` / `NIGHTMARE`. Мост считает по нему; если `node.tier` — другой допустимый `Tier`, пишет в журнал `breach.tier_mismatch` и всё равно считает по `tier` |
| `selected` | рабочие демоны сессии, выбранные во взлом (≥ 1, без повторов, сумма длин цепочек ≤ `session.ram`) |
| `matched` | совпавшие, подмножество `selected` |
| `active` | эффекты активных окон заряженных демонов на момент конца попытки, из `GHOST`, `TIMESKEW`, `BLACKOUT` (может быть `[]`) |
| `vaults` | предметы, лежащие сейчас в хранилищах узла, хранилище панели первым (может быть `[]`) |
| `open_s` | на сколько секунд открыть хранилище, 1..600 (`vault_open_sec` графа) |

**Что считает Мост** (по порядку, одна транзакция; функции — из `:rules` после К0, не копии):

1. **Исход** (`BreachResult`): `matched` пуст — `FAIL`; `matched` = `selected` — `SUCCESS`; иначе `PARTIAL`. Сервер мира исход не
   присылает: противоречить нечему.
2. **Эффекты** для сигнала: эффекты `matched` (из `item.daemon.effect`) ∪ `active`.
3. Дальше — только не `FAIL`. **Эдди**: `min(ContainerEddies.roll(tier, rnd) + (MINER среди matched ? minerBonus(tier) : 0), node.eddies)`;
   `rnd` — `Random(первые 8 байт sha256("<namespace>|<rid>"))`, сумма детерминирована (тесты, разбор журнала). `node.eddies` −,
   `session.loot_eddies` + (выплата — при `clean`, как сейчас).
4. **Хранилища** (`SlotClaimStore.pickSlot`): для каждого демона из `matched` с `EXTRACT_SHARD`/`EXTRACT_DAEMON`, в порядке `selected`, —
   первый предмет из `vaults`: `owner = node:<node>`, `kind` SHARD/DAEMON по эффекту, тир (`shard.tier`/`daemon.tier`) ≤ тира демона, не
   выбран этим же взломом, не в живом `opened` другой сессии и не в живом `opened` этой же (мастер мог сбросить остывание). Нашёлся — `session.opened += {item, node, until: now + open_s·1000}`;
   нет — `exhausted: true` («КЭШ ОЧИЩЕН»). Предмет из `vaults`, который уже не в узле (взяли за миг до того), пропускается без ошибки.
   Владельца предмета `run.breach` **не меняет**: его берёт рука, `op.take_from_node` (6.2).
5. **Остывание**: `runner.breach_cooldown[node] = now + max(breach_cooldown_s, open_s)·1000` (`settings/global`, по умолчанию 1800 — 30 мин `MockBreach`; не короче
   времени открытия хранилища: пока оно открыто, тот же узел снова не взломать).
6. **Сигнал СБ** — и при `FAIL`: `SecAlertRules.decide(owner, intruder, tier, outcome, effects, now)`; `owner` — `node.owner_faction`,
   иначе `settings/sec.default_faction`; `intruder` — `runner.faction` (как P3). Не `null` — документ `sec_alert` (раздел 5) с id
   `sa_` + 16 hex от `sha256("<namespace>|<rid>")`; отправка — после коммита, правилом, в `send_at`.
7. `session.breach` = `{n, node, tier, outcome, effects, eddies, opened_n: <число открытых>, exhausted, alert: <id | null>, at}`; истёкшие
   записи `session.opened` удаляются.

Ответ: `outcome`, `effects`, `eddies` (этого взлома), `loot_eddies` (всего в забеге), `opened`, `exhausted`, `cooldown_until` (0 при
`FAIL`), `alert` (`null` — сигнала не будет). Строку итога («СБ получит сигнал через 2 мин» / «сигнала нет») собирает сервер мира.

| Отказ | Код | Сохраняется по `rid` |
|---|---|---|
| нет поля, `n` < 1, неизвестный `tier`/эффект в `active`, `open_s` вне 1..600, `matched` ⊄ `selected`, повторы; предмет из `selected` — не рабочий демон этой сессии; сумма цепочек > `ram`; `node` — не текущий узел | `bad_request` | нет (ошибка кода сервера мира) |
| нет сессии или узла | `not_found` | нет |
| сессия не `active`; у неё `world.finish` (идёт исход); `n` ≤ `session.breach.n` (устаревшая попытка); `node` — учебный (`node.tutorial: true` или `settings/global.tutorial_node`) | `session_state` | да |
| `runner.breach_cooldown[node]` > сейчас | `cooldown` | да |

При любом отказе ничего, кроме записи `rid`, не меняется: ни эдди, ни хранилищ, ни сигнала.

**Повтор** `rid` с теми же параметрами — сохранённый ответ: эдди не разыгрываются второй раз, второго `sec_alert` нет. **Обрыв**:
сервер мира держит итог попытки в памяти до ответа и шлёт тот же запрос. **Рестарт сервера мира** посреди взлома: сетка и ходы
пропали — попытки не было (ни награды, ни сигнала, дизайн деки §5.5). Чтобы `rid` не повторился, сервер мира пишет `world.breach_n = n`
**до** показа сетки и без успешной записи попытку не начинает; после рестарта следующая попытка — `max(world.breach_n,
breach.n) + 1`. Рестарт после отправки, до ответа: если `session.breach.n` = `n` — итог записан, открытые хранилища — из
`session.opened`; если меньше — попытка потеряна (повторить нельзя: параметров нет). **Рестарт Моста**: транзакция либо
зафиксирована (повтор вернёт ответ), либо нет (выполнится заново); `sec_alert` в документе переживает рестарт.

Сервер мира **до** начала попытки сам проверяет допуск, как `CheckBreachAccess`: остывание — по снимку `runner.breach_cooldown`
(COOLDOWN), хранилища узла пусты (EXHAUSTED); Мост повторяет только первую проверку.

### 6.7 `op.give_item` — отдать предмет из груза

Сервер мира: игрок отправил шард или демона из ГРУЗа другому игроку (дизайн деки §9.2): нетраннеру в Сети (в его деку) или на телефон
(карточкой `Handover`). Отдаётся только груз: защищённый демон — `protected_item`, рабочий — `loaded_item`. Эдди не отдаются.

```json
{"v": 1, "cid": "61", "op": "op.give_item", "rid": "give:s_9f2c41d07a3e5b60:it_4c1a0b2e9d7f6a81:4", "session": "s_9f2c41d07a3e5b60",
 "item": "it_4c1a0b2e9d7f6a81", "ver": 4, "to_session": "s_77ab03c1d2e4f5a6"}
```
Получатель — ровно одно из `to_session` (сессия нетраннера в Сети; в дизайне деки — `to_runner`) и `to_phone` (ключ телефона, обычный
base64 SPKI). `ver` — версия предмета, которую видел сервер мира; `rid` = `give:<сессия>:<предмет>:<ver>`: версия в `rid` нужна,
потому что предмет может вернуться (A → B → A) и уйти снова — без неё второй раз сработал бы повтор старого ответа.

```json
{"v": 1, "re": "61", "ok": true, "replayed": false, "item": {"type": "item", "id": "it_4c1a0b2e9d7f6a81", "ver": 5, "…": "…"}, "to": "deck:s_77ab03c1d2e4f5a6", "transfer": null}
```
Для `to_phone`: `"to": "outbox:<ключ>"`, `"transfer": "tr_…"` (id карточки).

Одна транзакция: `item.owner` → `deck:<to_session>` либо → `outbox:<ключ>` с `handover: PENDING` и `out_transfer` (как в 6.4: id
`tr_` + 12 hex от `sha256("<namespace>|<rid>|<предмет>")`, карточка от ключа мира кладётся в `Outbox` после коммита); `deck.items`
отправителя −предмет, получателя (`to_session`) +предмет. `payload` и `origin` не меняются; у получателя предмет — груз (его нет в
`loaded`), работать он не будет.

| Отказ | Код | Сохраняется |
|---|---|---|
| не ровно один получатель; `to_session` = `session`; `to_phone` не разбирается как ключ или = ключ отправителя (`session.runner`); нет `ver`; `kind` не SHARD/DAEMON | `bad_request` | нет |
| нет сессии, предмета, сессии-получателя | `not_found` | нет |
| отправитель или получатель не `active` либо с `world.finish` (идёт исход) | `session_state` | да |
| предмет не `deck:<session>` | `wrong_owner` | да |
| `item.ver` ≠ `ver`; в `err.doc` — предмет | `version_conflict` | да |
| `protected: true` | `protected_item` | да |
| id предмета в `session.loaded` | `loaded_item` | да |

Проверки — в порядке таблицы (в `err.doc` у трёх последних кодов и у `wrong_owner` — предмет).

Шард, сданный при входе (id в `session.loaded`), по этой таблице тоже `loaded_item`, как и рабочий демон: проверка идёт по id, а не по виду предмета.
Сервер мира заранее не предлагает такое игроку (поле `give` строки груза) и не шлёт в Мост то, что отказано без вариантов.

После `version_conflict` (например, шард расшифровали) сервер мира перечитывает предмет и, если он всё ещё в грузе, шлёт запрос с
новым `ver` — это новый `rid` по правилу выше, не нарушение «новый `rid` для того же намерения».

**Повтор** — сохранённый ответ, вторых карточек нет. **Обрыв / рестарт сервера мира**: по снимку — предмет уже не в деке отправителя
значит передача прошла; иначе тот же `rid` (версия не изменилась). **Телефон не в сети**: карточка ждёт в `Outbox` (`PENDING`),
забег от этого не зависит — предмет уже вне риска забега (решение владельца). Получатель карточку не принял — предмет остаётся в
`outbox:<ключ>`, как у 6.4. **Исход забега**: сервер мира не начинает `run.finish` отправителя, пока его `op.give_item` в полёте
(как с `op.take_from_node`), и не отдаёт предмет сессии, у которой исход уже идёт; гонку с исходом получателя закрывает `session_state`
и правило 6.5 «не упомянут в moves».

Событие игрокам (`give` отправителю и получателю-нетраннеру) шлёт сервер мира по ответу; Мост — обычные `chg` предмета и дек.

### 6.8 `op.decrypt_item` — расшифровать шард в деке

Сервер мира: игрок прошёл мини-игру расшифровки (дизайн деки §3.1). Мост помечает шард расшифрованным **в `payload`** — единственное
исключение из «payload байт в байт»: формат `ItemPayloadCodec` уже несёт флаг, телефон берёт его из карточки
(`ItemTransferStore`, `decrypted = shard.decrypted`), и шард приходит на телефон открытым. Формат строки не меняется — версий
не поднимаем.

```json
{"v": 1, "cid": "62", "op": "op.decrypt_item", "rid": "decrypt:s_9f2c41d07a3e5b60:it_4c1a0b2e9d7f6a81:5", "session": "s_9f2c41d07a3e5b60", "item": "it_4c1a0b2e9d7f6a81", "ver": 5}
```
`rid` = `decrypt:<сессия>:<предмет>:<ver>`, `ver` — версия предмета, которую видел сервер мира (та же причина, что в 6.7: предмет
может уйти из деки и вернуться, и сохранённый отказ `wrong_owner` не должен отвечать на новый запрос).
```json
{"v": 1, "re": "62", "ok": true, "replayed": false, "changed": true, "title": "Схемы", "body": "…", "item": {"type": "item", "id": "it_4c1a0b2e9d7f6a81", "ver": 6, "…": "…"}}
```

**Перекодирование.** `payload.split("|")`, поле с индексом 9 (флаг `decrypted`) := `"1"`, `join("|")`. Все остальные байты — как были,
включая поля после десятого. **Не** `decodeShard` + `encodeShard`: это выбросило бы поля будущих версий и могло бы иначе
закодировать base64. После замены Мост разбирает строку `decodeShard` и сверяет: `decrypted` стал `true`, прочие поля равны
прежним; иначе `internal` (откат). `shard.decrypted` := `true`, `shard.encrypted` := `false`. `owner`, `origin`, `protected`,
`in_transfer`, `out_transfer`, `handover` и id документа не меняются — поэтому повтор входящей карточки по-прежнему отсекается по
`in_transfer`, а id предмета (`it_` от `<ключ>|<id карточки>`) тот же.

Только в деке (`deck:<session>`): у предмета в `outbox` карточка уже подписана старым `payload`, а `PhoneDelivery` пересобирает
карточку из документа при каждой досылке — замена посреди доставки дала бы две разные карточки с одним id.

| Отказ / случай | Код | Сохраняется |
|---|---|---|
| нет `ver`; `kind` не SHARD или `payload` не разбирается (в наполнении мастера его не проверяют) | `bad_request` | нет |
| нет сессии или предмета | `not_found` | нет |
| сессия не `active` или с `world.finish` | `session_state` | да |
| предмет не `deck:<session>` | `wrong_owner` | да |
| `item.ver` ≠ `ver` | `version_conflict` | да |
| нет рабочего (`loaded`) демона DECRYPT с тиром ≥ тира шарда (`DecryptRules.bestDecrypter`) | `no_decrypter` | да |
| шард уже открыт (`decryptAction = 0` или `decrypted = 1`) | `ok`, `changed: false`, записей кроме `rid` нет | да |

Успех мини-игры решает сервер мира — Мост ему доверяет, как `op.take_from_node`. **Повтор** — сохранённый ответ (с телом).
**Обрыв / рестарт**: тот же `rid`; после успеха версия предмета другая, и любой поздний вызов (новый `rid`) видит `changed: false`.

### 6.9 Хранилища узла: наполнение и открытие (правила сервера мира)

- **Свободный предмет узла** — `owner = node:<узел>`, `kind` SHARD **или DAEMON**, не лежит в другом хранилище и не в живом `opened`
  чужой сессии. Пополнение хранилища берёт свободный предмет любого из двух видов (сейчас — только SHARD), по возрастанию id, как
  сейчас. Демоны «мёртвой деки» (`black_ice` → `node:`) и демоны наполнения мастера — такие же свободные предметы: их достаёт
  `EXTRACT_DAEMON` (К8). Тир хранилища — `shard.tier` / `daemon.tier`; предмет без разобранного поля в хранилище не кладётся
  (предупреждение в журнал).
- **Открыто** — запись в `session.opened` (её пишет только `run.breach`). Сервер мира показывает хранилище открытым для этой сессии
  до `until` и даёт `grab` только по своему открытому; чужой `op.take_from_node` Мост отклонит `claimed`.
- **Рестарт сервера мира**: открытые — из `session.opened` сессий снимка; груз сессии — предметы `deck:<s>` не из `loaded` (не по
  `origin`: см. раздел 5, «Рабочие и груз»; нынешний `recover` и `_origin_is_mine` смотрят на `origin: node:*` и шарды мастера не
  видят).
- **Дека в сервере мира** (`deck_from_items`): рабочими берутся только демоны из `session.loaded`, остальное — груз; RAM — `session.ram`
  (нет поля — 6).

### 6.10 Сводка отказов для новых операций

| Ситуация | `run.breach` | `op.give_item` | `op.decrypt_item` |
|---|---|---|---|
| Дубль запроса (тот же `rid`, те же параметры) | сохранённый ответ, эдди и сигнал один раз | сохранённый ответ, одна карточка | сохранённый ответ |
| Тот же `rid`, другие параметры | `rid_mismatch` | `rid_mismatch` | `rid_mismatch` |
| Обрыв WebSocket до ответа | тот же запрос после `hello` | то же | то же |
| Рестарт Моста посреди операции | транзакция целиком или никак; повтор доводит | то же | то же |
| Рестарт сервера мира | попытка без ответа: по `session.breach.n` | по владельцу предмета в снимке | по `shard.decrypted` в снимке |
| Телефон не в сети | не участвует; сигнал — только телефонам в сети | карточка ждёт в `Outbox` | не участвует |
| Гонка за тот же предмет | второе открытие не выберет его (`opened`) | `wrong_owner` / `version_conflict` | `wrong_owner`, если предмет уже отдан |
| Исход сессии одновременно | `session_state` | `session_state`; `run.finish` получателя — 6.5 | `session_state` |

## 6a. Инструменты мастера (роль `master`)

«Кнопка раньше автоматики» (`docs/netrun.md`, «Устройство Моста»): каждая ручная операция — сообщение ниже; правила Моста
(`MasterRules`) вызывают те же методы, а не пишут документы мимо них. Роль проверяется: `master.*` из `world` — `forbidden`;
`test` разрешён везде (фейки). Операции задают состояние, поэтому повтор безопасен и без `rid`; единственное исключение —
сообщения канала (`mid`). Все ответы — `{"doc": …}` изменённого документа, если не сказано иное. Каждая — одна транзакция.

**Пауза Сети.** `{"op": "master.pause", "on": true, "node": "node_07"}`; без `node` — вся Сеть. Пишет `settings/global.paused`
(+ `paused_at`) или `node_cfg/<узел>.paused`; узла нет — `not_found`. Сервер мира перед шагом ICE и trace читает оба флага:
пауза узла = `settings.global.paused` **или** `node_cfg.<узел>.paused` (`MasterOps.isPaused`); на паузе ICE и trace замирают.
При снятии паузы сроки активных целей (`goal.deadline`) сдвигаются на время паузы; на паузе цели не срабатывают.

**Рубильник связи с площадкой.** `{"op": "master.link", "on": false}` → `settings/global.venue_link` (по умолчанию `true`).
Пока `false`, быстрые события на точки (`netrun-world-records.md`, раздел 3) не отправляются; записи синка и данные мира это
не затрагивает (`MasterOps.venueLinkOn`).

**Цели и сроки узла.** `{"op": "master.goal", "node": "node_07", "kind": "open", "value": 120, "in_s": 600}` (или абсолютный
`"deadline": <мс>`). Пишет `node_cfg/<узел>.goal = {kind, value, deadline, set_at, done, result}`; новая цель заменяет прежнюю,
`master.goal_clear` (`node`) убирает. Правила используют цель вместо сырых чисел: `open` — к сроку снять локдаун узла;
`lockdown` — к сроку закрыть узел на `value` секунд (по умолчанию `node_lockdown_s`, иначе 600), критический шаг — через
«ждём мастера» ниже. Остальные `kind` (`trace`, `ice`, …) читает сервер мира: «к значению `value` примерно к `deadline`».
Выполненная цель получает `done: true` и `result` (`applied` | `denied` | `no_node`). `eddies` узла автоматика не трогает.

**«Ждём мастера».** Перед критическим шагом (`flatline`, `lockdown`, `nightmare`, …) сервер мира или правило спрашивает
`{"op": "master.gate", "kind": "flatline", "ref": "<сессия>", "node": "node_07", "summary": "ФЛЭТЛАЙН: Призрак"}`. Ответ
`{"mode": "auto" | "wait" | "decided", "decision": "approve" | "deny" | null, "req": <документ master_req> | null}`:

- `auto` — для вида выключено (`settings.global.await_<kind>` ≠ 1): применять исход сразу;
- `wait` — создан (или ещё не решён) запрос `master_req/<kind>:<ref>`, исход **не применять**, повторить вызов позже; при
  создании поднимается тревога `master_request` (панель мастера звонит);
- `decided` — мастер решил (`master.decide`) или вышел срок; поступать по `decision`.

`master_req.data`: `kind`, `ref`, `node`, `summary`, `state` (`pending` | `decided`), `default`, `expires_at`, `decision`,
`decided_by` (`master` | `timeout`), `decided_at`. Срок — `settings.global.await_timeout_s` (по умолчанию 60), действие по
таймауту — `await_default_<kind>` (`approve` | `deny`, по умолчанию `approve`); таймаут решает правило `master_req_timeout`
(раз в `master_poll_s`, по умолчанию 1 с), а также любое обращение к просроченному запросу. Новый шаг — новый `ref` (иначе
вернётся старое решение). Ничего в Мосте не убивает персонажа само: флэтлайн по-прежнему применяет вызывающий после `decided`.
Сервер мира (P4, `GrayNode`) перед ожиданием пишет в `session.data.world` пометку `{finish: "flatline", disconnect}`, затем
спрашивает `master.gate` вида `flatline` с `ref` = сессия перед `run.finish(black_ice)` и повторяет вызов раз в секунду, пока
ответ `wait`. `approve` (и `auto`) — `black_ice`; `deny` («пощадить до применения») — `run.finish` с исходом `soft_ice` (дека не
мёртвая, без блокировки). Сбой связи или отказ Моста решением не считается: опрос продолжается (срок и действие по таймауту ведёт
Мост), исход сервер мира сам не назначает. Рестарт сервера мира посреди ожидания: `recover` видит пометку и продолжает тот же
флэтлайн (окна возврата и `emergency` нет). Пока исход уходит в Мост, сервер мира не пускает игрока в эту сессию (отказ в `auth`).
Решение: `{"op": "master.decide", "req": "flatline:s_1", "decision": "approve"}`; то же решение повторно — тот же ответ,
другое (или опоздавшее после таймаута) — `req_state`. Автоматика (`bridge`) решать за мастера не может.

**Заготовки.** Документы `template/<id>` (мастер пишет обычным `put`): `{"title", "settings": {…}, "node_cfg": {…}}`.
`{"op": "master.template_apply", "template": "tpl_night", "nodes": ["node_07", "node_08"]}` — одна транзакция: `settings`
сливается в `settings/global` (`world_pub` игнорируется; пишется `template_applied = {id, at}`), `node_cfg` — в
`node_cfg/<узел>` каждого узла. Нет заготовки или узла — `not_found`, ничего не записано; `node_cfg` без `nodes` — `bad_request`.
Ответ: `{"template", "nodes", "settings": [ключи]}`.

**Наполнение узла.** Запас шардов, демонов и эдди закладывает мастер через коллектор; Мост предметы сам не выдумывает. Это операции
с ценностями: `rid` по общим правилам раздела 6 (повтор с теми же параметрами — сохранённый ответ с `replayed: true`, другие
параметры — `rid_mismatch`), роли `master` и `test`, из `world` — `forbidden`; одна транзакция.
`{"op": "master.stock_node", "rid": "stock:17", "node": "node_07", "items": [{"kind": "SHARD" | "DAEMON", "payload": "<ItemPayloadCodec>"}], "eddies": 100}` —
узла нет → `not_found`; пустой список и `eddies` 0, `eddies` < 0, неизвестный `kind`, пустой `payload` → `bad_request`. Создаёт документы
`item` с id `it_` + 16 hex от `sha256("<namespace>|<rid>|<индекс>")` (детерминированно: повтор не плодит копий), `owner: "node:<узел>"`,
`origin: "master:<client>"`, `protected: false`, `in_transfer`/`out_transfer`/`handover` — `null`, `daemon`/`shard` разобраны из
`payload` как при приёме карточки. `eddies` прибавляется к `node.eddies`. Ответ: `{"node", "items": [id…], "eddies": <новый запас>}`.
`{"op": "master.unstock_node", "rid": "unstock:17", "node": "node_07", "items": ["it_…"], "eddies": 50}` (`items`, `eddies` необязательны, но
что-то одно нужно) — убирает предметы, лежащие в `node:<узел>` (иначе `wrong_owner`, ничего не меняется): `owner` → `burned:master`, документ
остаётся для журнала (аудитор такой предмет не считает нарушением). `eddies` вычитается из запаса; больше запаса или < 0 — `bad_request`.
Ответ: `{"node", "items", "eddies": <остаток>}`.

**Запрос к Сети.** Канал мастер ↔ нетраннер — документы `net_query/nq_<n>`: `{"runner", "state": "open" | "answered",
"messages": [{"mid", "from": "runner" | "master", "text", "at"}]}`.
`{"op": "net.query", "runner": "Призрак", "mid": "m1", "text": "Где шард?"}` (роли `world`, `master`, `test`; `query` — id,
чтобы дописать в существующий, иначе создаётся новый и поднимается тревога `net_query`) и
`{"op": "master.reply", "query": "nq_5", "mid": "r1", "text": "…"}` (ответ → `answered`). Повтор с тем же `mid` не дублирует
сообщение; текст ≤ 2000 символов.

## 7. Терминал и сессия игрока

Очки не знают ни ключей, ни Моста. В конфиге приложения очков (кладётся через adb при установке стойки) — `terminal` и
`token` (32 случайных байта, base64url). Мастер создаёт документ `terminal` с `token_sha256` этого токена.

1. Очки → сервер мира по ENet: в `auth_callback` — `{"terminal": "t03", "token": "…"}`.
2. Сервер мира → Мост `terminal.auth`:

```json
{"v": 1, "cid": "50", "op": "terminal.auth", "terminal": "t03", "token": "q3Zb…"}
```
```json
{"v": 1, "re": "50", "ok": true, "terminal": {"type": "terminal", "id": "t03", "ver": 4, "created": 1790000000000, "updated": 1790000300000, "data": {"node": "node_07", "label": "Подвал, стойка 3", "token_sha256": "9b1f…", "silent": false}}, "session": null}
```

   `ok: false`, `bad_token` — сервер мира отказывает в `auth_callback`. `session` — открытая сессия терминала (`pending`
   или `active`) или `null` (экран ожидания с внеигровыми правилами). Результат не кешируется: проверка дешёвая.
3. Появилась `pending`-сессия на этот терминал (сервер мира видит её в `sub` на `session`) — очки показывают «Подключается:
   <`callsign`>». Курок → сервер мира:

```json
{"v": 1, "cid": "51", "op": "session.confirm", "session": "s_9f2c41d07a3e5b60", "terminal": "t03"}
```
```json
{"v": 1, "re": "51", "ok": true, "session": {"type": "session", "id": "s_9f2c41d07a3e5b60", "ver": 3, "created": 1790000500000, "updated": 1790000530000, "data": {"state": "active", "confirmed_at": 1790000530000}}}
```

   Идемпотентна по состоянию: уже `active` — тот же ответ; `closed` — `session_state`. Отказ игрока или таймаут:

```json
{"v": 1, "cid": "52", "op": "session.abort", "session": "s_9f2c41d07a3e5b60", "reason": "отказ в очках"}
```
```json
{"v": 1, "re": "52", "ok": true, "session": {"type": "session", "id": "s_9f2c41d07a3e5b60", "ver": 3, "created": 1790000500000, "updated": 1790000560000, "data": {"state": "closed", "outcome": "aborted"}}}
```

   Только из `pending`; дека — на телефон (как 6.4, `rid` `abort:<сессия>`). Повтор — тот же ответ.
   **Heartbeat терминала.** Сервер мира раз в несколько секунд (рекомендуется 5 с) шлёт `terminal.beat` — он обновляет документ
   `terminal`, а правило «терминал молчит» (`terminal_silent_s`) считает молчание по его `updated`. Поля, кроме `terminal`,
   необязательны: `battery` (заряд очков, %), `fps` (кадры в секунду), `link` (качество связи, 0–100); все целые.

```json
{"v": 1, "cid": "53", "op": "terminal.beat", "terminal": "t03", "battery": 80, "fps": 72, "link": 95}
```
```json
{"v": 1, "re": "53", "ok": true, "ver": 5}
```

   Мост пишет в документ `data.battery`/`fps`/`link` (если пришли) и `data.beat_at` (время Моста, меняется на каждый вызов), флаг
   `silent` не трогает. Нет терминала — `not_found`. Роли: `world`, `test`.
4. **Игрок — это сессия, не peer id.** Сервер мира хранит `сессия → peer`; переподключение очков с новым peer id проходит шаг 2
   и получает ту же `active`-сессию → тот же аватар (`node_07/avatar_<сессия>`). 20 с после обрыва (`disconnect_grace_s`)
   отсчитывает сервер мира, затем `run.finish` с `outcome: emergency` и `disconnect: true`. Состояние связи сервер мира пишет в
   `session.data.world` через `put`.

## 8. Канал телефона (для M2/M3)

**QR стойки** (печатается мастером на стойке терминала, читается приложением как любой другой QR Мегаблока, `Mb10QrCodec`):
`MB10:RACK:v1:<терминал>:<base64 host:port>:<world_pub>[:<base64 подпись>]`. `терминал` — id документа `terminal` (`t03`); адрес Моста —
порт `--line-port`, в base64, чтобы двоеточие IPv6 не ломало разбор; `world_pub` — публичный ключ мира как в `settings.global.world_pub`
(стандартный base64 без двоеточий); подпись для игрока («Подвал, стойка 3») необязательна. Телефон запоминает ключ и адрес (статический
пир `PeerTable`) и принимает от этого ключа добычу и эдди без «Принять».

Телефон и Мост — участники kit: Мост держит сервер строк как у приложения, телефон шлёт на адрес из QR стойки (статический
пир) **обычные карточки предметов** (`SendItem`, получатель — `world_pub`), каждая с чеком по `HandoverRules`
(`rejectIncoming`, чек `id|ключ`). Принятый предмет — документ `item` с `owner: inbox:<ключ>`, `in_transfer` = id карточки;
повтор карточки отсекает журнал входящих Моста (тот же `in_transfer` — второй документ не создаётся, чек повторяется).

Транспорт — тот же, что у телефонов (kit `LineServer` с конвертом `MB10TO` и квитанцией `MB10ACK`, `PeerTable`/`PeerDirectory`):
Мост слушает порт `--line-port` (по умолчанию 7411; телефон берёт адрес из QR стойки), а адрес телефона узнаёт из порта в
конверте его строк или из статической записи. Карточка едет телом личного сообщения `MB10CHAT` (как между телефонами), Мост отвечает
чеком тоже личным сообщением. Ключ мира — пара ECDSA в файле `<база>.worldkey` (создаётся при первом старте), публичная часть —
`settings.global.world_pub` и `world_pub` в `hello`; `--world-pub` теперь только сверка (не совпадает с файлом — Мост не стартует).

После карточек телефон шлёт **запрос входа** — подписанную ключом игрока строку `MB10ENTER:v1:<rid>:<терминал>:<ключ>:<base64
позывной>:<transfers через запятую>:<protected_transfer>:<ts>:<подпись>` (подпись — над `ENTER1|rid|терминал|ключ|позывной|
transfers|protected|ts`; в `WireVersion` приложения — `ENTER`, `ENTERED`, кодек — `netrun/NetrunWire.kt`, близнец `PhoneWire` Моста), содержимое — такое:

```json
{"rid": "e-7d1c", "terminal": "t03", "runner": "MFkwEwYH…", "callsign": "Призрак",
 "transfers": ["tr_88e1", "tr_88e2"], "protected_transfer": "tr_88e1", "ts": 1790000499000, "sig": "MEUCIQ…"}
```

Мост ждёт, пока все `transfers` придут в `inbox` (не дольше `inbox_timeout_s`), и зовёт `op.submit_deck` с
`rid: enter:<rid>`. Ответ на телефон — подписанный ключом мира результат: `{"rid": "e-7d1c", "ok": true, "session": "s_9f2c…"}`
или `{"rid": "e-7d1c", "ok": false, "code": "session_state", "msg": "терминал занят"}` (дека в этом случае уже выдаётся
обратно). Телефон без ответа повторяет запрос с тем же `rid`. Карточки в `inbox` без запроса входа дольше `inbox_timeout_s` —
обратно на телефон (`rid` `refund:<in_transfer>`). Флаг нетраннера (коллектор) проверяет M2 до `op.submit_deck`.

**Запрос входа v2 (RAM).** Сеть должна знать RAM персонажа: это буфер взлома хранилища и предел ПРОГРАММ деки. Строка
`MB10ENTER:v2:<rid>:<терминал>:<ключ>:<base64 позывной>:<transfers через запятую>:<protected_transfer>:<ram>:<ts>:<подпись>` (11
частей), подпись — над `ENTER2|rid|терминал|ключ|позывной|transfers|protected|ram|ts` (`ENTER2`, а не `ENTER1`: подпись v1 нельзя
выдать за v2). `ram` — десятичное `Identity.ramCapacity`. В приложении `WireVersion.ENTER = 2`; ответ `MB10ENTERED` не меняется и
остаётся v1. Мост принимает обе версии:

| | v1 | v2 |
|---|---|---|
| `session.ram` | `max(6, сумма длин цепочек сданных демонов)` — телефон проверил деку против своей RAM, которую Мост не знает | из запроса |
| `ram_exceeded` | сумма > 13 | `ram` вне 6..13 или сумма длин цепочек всех сданных демонов (с защищённым, как `NetrunEntry.validate`) > `ram` |
| `ram` в параметрах `rid` входа | нет (как до К2) | да |

`ram_exceeded` — отказ внутри транзакции входа: предметы сразу возвращаются (`refund:`), как при остальных отказах. Порядок выкладки:
**сначала Мост**, потом приложение (старый Мост строку v2 не разберёт: телефон уйдёт в тайм-аут ожидания, карточки вернутся по
`inbox_timeout_s`). Запрос, сохранённый приложением до обновления (в prefs нет `ram`), переотправляется строкой v1 с прежней подписью.

На проводе ответ — строка `MB10ENTERED:v1:<rid>:<1|0>:<base64 сессия>:<base64 code>:<base64 msg>:<подпись ключа мира>` (подпись над
`ENTERED1|rid|ok|сессия|code|msg`), отправляется телефону тем же транспортом без повторов: потерялась — телефон повторит запрос, Мост
ответит из сохранённого результата по `rid`. Флаг заблокированного нетраннера из коллектора (M4) Мост пока не читает: действует только
`runner.blocked` в документах Моста (его ставит `black_ice`).

## 9. Что не входит

Записи для коллектора и быстрые события на точки — C2 (`docs/netrun-world-records.md`; записи взлома и передачи — его разделы 2.5 и
2.7). Каталог событий Сети и правила (B2) — свои документы; здесь только то, что ходит по WebSocket. `NETRUN_PROTO` остаётся 1:
новые операции и поля только добавляются (старый Мост на новую операцию ответит `bad_request`).

## 10. Что меняется у соседей ради деки (К2, К4, К5б, К7)

**Мост** (`:netrun-bridge`): `PhoneWire` — разбор v1 и v2 запроса входа; `ValueOps` — `ram`/`loaded` в `submitDeck`, `runBreach`,
`giveItem`, `decryptItem`, проверка `claimed` в `takeFromNode`, деление груза в `planMoves` по `loaded`; тип `sec_alert` и правило его
отправки; `ItemDecode` — `shard.encrypted` и дописывание его старым документам; `WorldRecordDeriver` — записи раздела 2.5/2.7 C2;
`WorldCollectorTransport` — слать при `world_records ≥ 2`, а не `== 1`.

**Сервер мира** (`netrun/server`): `world.breach_n` до сетки; подписка на `runner`; `deck_from_items` и `recover` — по `loaded`;
`moves` в `_finish_in_bridge` — по `loaded`; пополнение хранилищ демонами (6.9); `op.give_item` в полёте задерживает исход.

**Приложение** (`app/`, правило `app-invariants.md`: смена формата — с версией):
1. `NetrunWire`: `EnterRequest.ram`, строка и байты подписи v2 (раздел 8); `WireVersion.ENTER = 2`, `ENTERED` остаётся 1; кодер v1
   сохранить для попыток, записанных до обновления.
2. `NetrunEntry.enter`: `ram = me.ramCapacity`; `NetrunStore` — новое поле prefs `attempt_ram` (нет поля — попытка v1).
3. Константы RAM 6 и 13 (`Identity.kt`) — в `:rules` (Мосту они нужны для `ram_exceeded`), вместе с переносом К0.
4. Получатель `op.give_item` по `to_phone` видит карточку от ключа мира («Мост»): если стойку он сканировал — `WorldAutoAccept` примет
   без «Принять» и погасит баннер «Подключено» (`onWorldCard`), даже если его забег идёт; иначе карточка ждёт «Принять». От кого
   предмет, карточка не говорит (поля нет) — подпись «из Сети от <позывной>» требует отдельного сообщения; пока не делаем.
5. Расшифрованный шард (`decrypted = 1` в `payload`) телефон уже принимает открытым (`ItemTransferStore`) — правок нет, нужен тест.

**Коллектор** (`admin-web/`, соседняя сессия): поле `net.breach` и причина `NET_BREACH` (C2, раздел 2.7, подписи и тип в ленте),
`capabilities.world_records = 2`; `NET_ITEM_OWNER` с `op: give_item` и `NET_ENTER` с `ram` приходят в принятом уже формате — правки
только в подписях ленты (по желанию).
