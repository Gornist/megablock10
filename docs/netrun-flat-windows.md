## 1. Сервер в том же процессе — да

- `NetServer` и `NetClient` берут сеть через `multiplayer` узла. Два поддерева с отдельным `SceneMultiplayer` (`get_tree().set_multiplayer(SceneMultiplayer.new(), путь)`) уже работают рядом в `tests/teleport_proto_test.gd`, `restart_test.gd`, `tools/bench_world.gd` (сервер + боты + клиенты в одном процессе).
- Поток не нужен и не получится: `SceneTree` не потокобезопасен, серверу мира (`WorldServer`) нужен свой `Node`-тик. Всё в главном потоке: сервер добавляет к кадру клиента время тика. Замер — `bench_world.gd` с одним узлом (цифры не снимала; снять в PR 1).
- Транспорт — ENet по петле: `127.0.0.1`, свободный порт. Тот же путь кода, что в e2e и на очках, ноль новой сетевой логики. Подводный камень: `NetServer.start` зовёт `enet.create_server(port, 32)` — слушает **все** интерфейсы, и Windows при первом запуске покажет тестеру окно брандмауэра. Лечение: однострочная правка (`set_bind_ip("127.0.0.1")` до `create_server`, поле в `NetConfig`), по умолчанию как раньше. Запасной вариант, если брандмауэр всё равно мешает, — свой `MultiplayerPeerExtension` без сокетов (~150 строк, но в `NetServer`/`NetClient` есть ENet-специфика: статистика RTT, `disconnect_peer`, таймауты — нужны ветки): не делать, пока петля не подведёт.
- Вход: новый режим `SOLO` в `RunMode`/`main.gd` (для Windows-сборки — по умолчанию, признак — custom feature в пресете). `main.gd` грузит сервер по пути (`SERVER_SCRIPT`), exe сервер уже содержит: пресет «Flat debug (Linux)» не исключает `server/`.
- Мост: в соло — `FakeBridge` с фикстурой (`--bridge=fake`, как стенд e2e), токен генерируется при старте, в аргументы не светится. **Не проверено:** что нужная соло-игре часть фикстуры (терминал, кошелёк, инвентарь) полная — смотреть в PR 1; обмен шардом с другим игроком (`GiveService`) и телефон (`RemotePhoneLink`, TCP-сервер WebSocket) в соло не нужны — выключить, чтобы второй порт не открывался.
- Закрытие: выход из клиента = остановка сервера = `quit()`; сейчас `rig.exit_requested → net.request_exit` ведёт на чистый выход площадкой, плюс Esc 3 с — экстренный.

## 2. Экспорт Windows с devbox

- Шаблоны экспорта на devbox есть: `windows_release_x86_64.exe` (и debug, console, x86_32, arm64) в `~/.local/share/godot/export_templates/4.7.2.stable/` — версия совпадает с редактором. Новых установок не нужно.
- Нужен пресет «Windows Desktop»: `embed_pck=true` (один exe), `custom_features="flat,solo"`, `exclude_filter` как у плоской сборки (`addons/gdUnit4/*, tests/*, reports/*`; `server/*` НЕ исключать), `texture_format/s3tc_bptc=true`. Размер: 4 МБ ассетов, остальное — шаблон движка (десятки МБ; точное — после первой сборки).
- `application/modify_resources` (иконка, версия через rcedit) на Linux требует wine — отключить, exe без иконки. Подпись: без сертификата Windows SmartScreen покажет «Защитник Windows предотвратил запуск» (Подробнее → Выполнить всё равно); антивирусы изредка ругаются на неподписанные exe Godot. Текстовая инструкция тестеру — в карточке сборки. Подпись — решение владельца (платный сертификат), для узкого плейтеста не нужна.
- Запуск exe на Windows мне проверить негде (Mac и Ubuntu). Предложение: GitHub Actions `windows-latest` — дымовой прогон `--headless` экспортированного exe (сервер + клиент в одном процессе, вердикт строкой); картинки без GPU не проверяются. Первый настоящий кадр — у тестера: нужен один человек владельца с логом.

## 3. Рендер для слабых ПК

- Сейчас `project.godot`: `renderer/rendering_method="mobile"` (Vulkan). На старом ПК без Vulkan 1.2 exe не стартует. Режим `gl_compatibility` (OpenGL 3.3) идёт на всём, что старше.
- В шейдерах окружения нет `hint_screen_texture`, `hint_depth_texture`, `normal_roughness` — самые частые причины поломки Compatibility. Список под проверку: `alpha_to_coverage` (3 шейдера: облако, вуаль, юбка), два `shader_type particles` (тело, руки), облако — `MultiMesh` с пользовательскими данными (в Compatibility работает, но скорость на слабой видеокарте неизвестна). **Не проверено:** внешний вид в Compatibility против вида очков — решать по кадрам `dev.sh shot` (сетка, до/после), как принят единый вид Сети.
- Выбор рендера в готовом exe: двойной клик без аргументов, а `rendering_method` читается до сцены. Три пути: (а) собирать из копии проекта, где скрипт сборки подменил `rendering_method` (рекомендую: один exe, ноль магии у тестера); (б) `override.cfg` рядом с exe (нарушает «один exe»); (в) перезапуск самого себя с `--rendering-method`. Рекомендация: собрать **один exe на Compatibility**; если по кадрам вид теряет заметно — второй exe на Mobile для тестеров с хорошей картой. Оценка слабого ПК — только через владельца (1–2 тестера с любой видеокартой, лог с `perf = "on"` — уже есть `FramePerf`, `[render] perf` в `netrun.cfg`).
- Что отключить на плоской сборке: слои композитора OpenXR (`layers` — только очки), фовеацию; `msaa = 2` оставить (на ПК дешёвый), параметры — через тот же `netrun.cfg` рядом с exe (`NetConfig.default_paths()` ищет внешний каталог и `user://`).

## 4. Журнал прохождения рядом с exe

- Журнал уже есть: `MbLog` пишет `событие ключ=значение` (старт, режим, рендер, `shard.stowed`, `grab.miss`, `away.*`, `perf`…) в `user://logs/netrun-*.log`. На Windows `user://` — `%APPDATA%\Godot\app_userdata\<имя>`: тестер не найдёт. Нужно: каталог `logs/` рядом с `OS.get_executable_path()`, при недоступной записи (Program Files, защищённый каталог) — запасной `user://logs`. `DIR` в `MbLog` — константа: стать функцией с проверкой записи (мелочь, ~2 ч с тестом).
- «Журнал прохождения» (что игрок сделал, где остановился) сейчас — только клиентская часть. Нужны итоговые события: вход в узел, смена тревоги/trace, вскрытия, шарды, поражение/чистый выход, сколько секунд на узел — часть серверных событий в соло доступна в том же процессе. Предлагаю тонкий слой: подписка клиентской сцены на сигналы (`alarm_changed`, `shard_stowed` …) плюс итоговая строка при выходе; `FileAccess.flush()` на каждую строку, чтобы журнал пережил падение. Что именно нужно Game для разбора плейтеста — вопрос к Game (см. ниже).

## 5. Доводка плоского вида до вида в очках

Уже есть:
- Мышь на деке и колесо: `DeckPointer` считает луч от камеры по `InputEventMouse` (`_hit_for_mouse`), события уходят в `SubViewport` панели. Клетки взлома — `Control` с `MOUSE_FILTER_STOP`, ЛКМ. **Не проверено:** что панель взлома на плоской сборке реагирует на мышь так же, как дека (это отдельная панель, тот же `DeckPointerMath`).
- HUD и «опасное в центре» — `world_ui` в мире, привязан к камере; 25 мест `rig.xr_active` — места, где плоская ветка ведёт себя иначе: пройти их по списку.
- Q/E — плавный поворот; в очках — щелчок 45° (`RigMath.snap_turn`, `snap_step_deg`). Включить щелчок на Q/E и мышью (скачок, возврат в центр) — ~2 ч.

Нужно сделать:
1. Курсор: сейчас осмотр — ПКМ+мышь. Для людей без VR привычнее захват курсора мышью + поворот щелчком, и **свободный курсор для деки и панели взлома** (удержание/переключатель, например Tab). Решение владельца/Game: какая схема. Подсказки клавиш — слой в углу, зависит от схемы.
2. Новый HUD: тревога над тиком, «опасное в центре» — в очках это объекты в мире; на плоском экране нужен тот же слой (2D `CanvasLayer` или `Label3D`-ряд на камере — по размеру кадра на 1080p и 4K).
3. Пауза/меню/выход/перезапуск: в очках выход — площадка и Esc 3 с; для человека за ПК нужен Esc-меню («продолжить, выйти, открыть папку с журналом»); перезапуск прохождения без перезапуска exe.
4. Звук: клиент слушает серверные сигналы, `phone_voice` и голос в соло не нужны — отключить, чтобы не просить доступ к микрофону.
