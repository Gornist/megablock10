## Этап A — инфраструктура проверок

~~**A1. Скриншот-тесты — в отдельной JVM.**~~ `test<Variant>UnitTest` гоняет только `screenshots/*` (Paparazzi привязан к ней), все
остальные тесты — `test<Variant>UnitTestNoScreenshots`, от которой она зависит; каждый тест идёт ровно один раз (`app/build.gradle.kts`,
комментарий у задач). Остались `-javaagent` ByteBuddy и `allowAttachSelf` — нужны Paparazzi в любой JVM (стережёт `AgentPreloadTest`).
Обходы `robolectric.sqliteMode=LEGACY` и повтор в `check.sh` сняты: 5 прогонов подряд зелёные на M1, ни сбоя агента, ни SIGSEGV.

~~**A2. Контракт журнала — тестом.**~~ `scripts/e2e/log-contract.tsv` + `log/LogContractTest`: каждая строка контракта есть в коде в
файле со своим тегом и в стенде, каждый тег `logcat -s` стенда есть в контракте. Переименование события в коде роняет unit-тест, а не
стенд через 17 минут.

~~**A3. e2e на PR.**~~ `e2e.yml`: `pull_request` в `main` с фильтром путей (`app/`, `kit/`, `rules/`, `netrun*/`, `admin-web/server/**` кроме
`*.test.ts`, `scripts/e2e/`; документы не считаются), плюс ночной и ручной запуск; `concurrency` отменяет недоигранный прогон при новом
пуше. Цена ≈17–19 минут раннера на PR; журналы красных сценариев печатаются в лог job.

~~**A4. Стенд без статических пиров, если NSD работает.**~~ **Оставлено: `link.sh` нужен.** Проверено прогонами `static_peers=false`:
на CI (Linux) mDNS между эмуляторами ходит, и после B2 все сценарии зелёные без статических пиров; на **macOS не ходит вообще**
(`up.sh`: «NSD: эмуляторы не нашли друг друга за 60 с»), так что локальный стенд без `link.sh` не поднять. Решение владельца: эмуляторы
— свидетель логики приложения, а не NSD, поэтому `e2e.yml` по умолчанию со статическими пирами (`E2E_STATIC_PEERS=1`); режим «только NSD»
— ручной запуск со снятым `static_peers`. NSD проверяют JVM-тесты и телефоны. Статические пиры маскируют класс «порт прошлого процесса»
— он закрыт не стендом, а архитектурно (этап D). Перед каждым сценарием `run-all.sh` зовёт `heal_peer_link` (проверка связи через
оба redir, [scripts/e2e/README.md](../scripts/e2e/README.md)).

~~**A5. Pre-push — только быстрое.**~~ Хук гоняет `scripts/check.sh --fast`: detekt, Animal Sniffer, Lint, `:kit:test`, тесты сервера —
по изменённым путям, без Robolectric и Paparazzi (они — CI и `check.sh --all`). После правки `.kt` на прогретом демоне Gradle — около
16 с (≤ 1 мин с запасом); холодный демон (после клона, `--stop`, перезагрузки) — до 6 мин, почти всё в Lint, один раз за сессию.

## Этап B — сетевой код

~~**B1. `PeerDirectory` вместо сырого списка пиров.**~~ Одно место адресации (kit): `online` (игроки без адреса, по одному на ключ),
`send(ключ, строка): SendOutcome`, `sendToAll`, `isOnline`, `describe`. `PeerInfo` с host/port не выходит за `presence/` (источник
адресов) и `collector/` (подсказки сервера); `ChatStore`, `OutboxStore`, `CardResender`, `SlotClaimStore`, `CallManager`,
`ContactDirectory`, `SecAlertStore` ходят только через него.

~~**B2. Таблица пиров — по ключу игрока.**~~ Kit `PeerTable`: записи по `pubKeyB64` со списком адресов по источникам; у записи NSD
история из 3 адресов (имя сервиса одно во всех процессах, кэш mDNS после перезапуска отдаёт то новый порт, то прошлый); свежее
событие первым, `NOT_REACHED` — в конец до удачи, `UNKNOWN` не трогает; подсказка сервера не выбрасывается, когда NSD знает
игрока; loopback-подсказка (стенд) — порт с host-ом из NSD. Число игроков на экранах и очередь — по одному адресу на игрока
(`bestPerPlayer`). Тесты: `playerRestartedWithNewPortFirstSendGoesToTheNewPort`, `staleNsdAnswer…`, `loopbackHint…` в `PeerTableTest`.

~~**B3. `SessionController` — одно место для фоновой работы.**~~ Входы: «процесс стартовал», «личность появилась/сброшена», «экран
открыт», «сброс». Он решает, что запущено: сеть, синк, foreground-сервис (с правилами Android 12+). Таблица — `SessionControllerTest`,
«никто другой не зовёт `mesh.start/stop`, синк и `MeshForegroundService.start`» — `SessionGuardTest`. NSD по одной операции:
`presence/NsdSlot` (желаемое → фактическое, следующая операция после ответа Android, тайм-аут, повтор; снять незавершённую регистрацию
нельзя по построению) и `NsdResolveQueue` (на Android до 14 одновременное разрешение падает с `FAILURE_ALREADY_ACTIVE`, а на площадке
десятки телефонов разом). Сервер строк открывается **до** привязки к Wi-Fi: сокет, открытый после `bindProcessToNetwork`, помечен сетью
и умирает вместе с ней, не принимая через `emu redir`.

## Этап D — адрес игрока без догадок (решение владельца 25.09)

Класс сбоя: адрес менялся при каждом перезапуске (`ServerSocket(0)`), и его заново искали через самый капризный канал (mDNS). Всё, что
лечили в B2 и A4, — следствия. Вместо всё более умного поиска меняющегося адреса — адрес, который не меняется, и проверка, что по нему тот
самый игрок.

- ~~**D1. Фиксированный порт.**~~ Сервер строк слушает `CHAT_PORT` 47100 (занят — случайный, событие в журнале). На площадке IP стабилен
  (аренда DHCP на всю игру, [network-spec.md](network-spec.md) §5), значит адрес игрока — его IP.
- ~~**D2. Ответ получателя с ключом.**~~ Kit `LineEnvelope`/`LineAck`, `LineServer` (проверка «мне ли», ответ после обработчика,
  `onHeard`), `LineSocketClient` (`expectAckFrom`), `PeerTable.heard`. Исходы отправителя: `ok` ожидаемого ключа — доставлено;
  `wrong` — там другой игрок, строку не обработал: следующий адрес, таблица узнаёт владельца IP; закрыто без ответа — старая версия
  (как раньше); ответа нет после записи — `UNKNOWN`. Версия конверта — `WireVersion.ENVELOPE`. Тесты — `LineAckTest` на настоящих сокетах.
- ~~**D3. Статусы сообщений.**~~ `chat_messages.status` (миграция 16→17) и `MessageStatus`: не ушло «…» / ушло «✓» / доставлено «✓✓»
  (ответ `ok`) / прочитано «✓✓» цветом; только вверх; ставят отправка, очередь исходящих и переотправка карточек.
- ~~**D4. «Прочитано».**~~ `chat/ReadReceipts`: `MB10READ:v1:<читатель>:<автор>:<до T>` — отдельный протокол, водяной знак по времени
  (отдельный id сообщения не понадобился); уходит, пока тред на экране, один раз на водяной знак, не дошло — в очередь; переключатель
  «Отчёты о прочтении» в Настройках (`chat_prefs`, по умолчанию включён; выключен — свои не уходят, чужое «прочитано» показывается как
  «доставлено»).

## Этап C — после проверки на телефонах

**C1. Личность в Room, в одной транзакции со стартовыми данными.** Сейчас личность живёт в SharedPreferences (`identity_prefs`), данные
— в Room (версия схемы 17), и выдача по QR идёт в два шага: личность → транзакция Room (записи, баланс). Окно между ними закрывает
`ProvisionStore.resumeInterrupted`. Перенос личности в Room убирает окно и два источника правды; нужна миграция с переносом ключей
из `identity_prefs` без потери (ключ = личность игрока). *Готово, когда:* `MigrationDataTest` переносит ключи; выдача — одна транзакция;
`resumeInterrupted` для выдачи не нужен. В коде не сделано (личность по-прежнему в `identity_prefs`).

## Этап F — софт физических точек (QR-дисплей и звук на ESP32, 03.10; зона «Физические узлы»)

Рефактор без смены поведения: протокол v1 и общие векторы, HTTP API, схема БД, форматы flash/SD, тексты — те же. Сделано: общие `util.h`
и разделение `device.cpp` в прошивке (`firmware/display`); класс `ClipUpload` для докачки клипа; на сервере (`admin-web/server`) один
`DisplaySession.request` вместо семи копий «кадр → OK», `config.ts`/`pushProgress.ts`/`battery.ts` из `manager.ts`, общие проверки
ввода; на клиенте `useDeviceData`/`useDeviceEditor` и разбиение `AnnouncePanel`/`DeviceDetail`.

Ошибка, найденная по ходу (была и на `main`): прошивка для ПК вешалась, когда процесс просыпался на «старое соединение закрыто» и
«новое пришло» — блокирующий `recv` уходил на новый, молчащий сокет. Цикл соединений вынесен в ядро (`endpoint.*`) с регрессионным
тестом `testEndpoint`; плата ESP32 имела прежний цикл без этой ошибки (`available()` не ждёт) и ждёт самопроверки Wokwi. Не тронуто
сознательно: `src/esp32/main.cpp`, `audio.cpp`, `selftest.cpp` (без железа не разбить без риска для таймингов); `SdCard::trackCount`
на ESP32 читает карту без блокировки — правка меняет поведение, отдельной задачей; старые имена «группа»/«дисплей» в текстах и
aria-label (на них опираются тесты и API). Подробности — [firmware-plan.md](firmware-plan.md).
