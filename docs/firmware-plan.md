# План: прошивка QR-дисплея и её проверка без железа

Контракт, который прошивка должна выполнить, — [displays.md](displays.md) (протокол v1, требования к прошивке MVP). Сервер,
дашборд и mock-дисплей уже готовы. Этот план — этапы 3–8 из ТЗ, перестроенные так, чтобы **почти всё проверить до того, как
плата окажется в руках**, а день с платой свёлся к «прошить, прогнать тот же набор проверок, замерить то, что без железа не
измерить».

## Главная идея: одна прошивка — две сборки

Протокол, проверки, версии, хранение кадра и машина состояний — обычный C++ без Arduino. Он собирается дважды:

```
                      firmware/display/lib/core  (протокол, CRC, HMAC, сессия, состояния)
                                  │
              ┌───────────────────┴───────────────────┐
     сборка ESP32-S3 (CrowPanel)             сборка для ПК (Linux/macOS)
     Wi-Fi, lwIP-сокеты, GxEPD2,             POSIX-сокеты, файл вместо flash,
     LittleFS, LEDC, АЦП, task WDT           PNG вместо e-paper, заглушки
              │                                       │
         реальная плата               ← тот же сервер admin-web, тот же набор проверок →
```

Сборка для ПК — не второй mock, а **та же прошивка** с другими драйверами: сервер мастера подключается к ней так же, как будет
подключаться к плате. Всё, что отличается у платы (панель, Wi-Fi, flash, подсветка, батарея), спрятано за узкими
интерфейсами, и у каждого есть вариант для ПК.

## Структура

```
firmware/display/
  platformio.ini            # env: crowpanel579 (ESP32-S3), host (программа для ПК), native (unit-тесты)
  lib/core/                 # без Arduino и без ESP-IDF
    protocol.h/.cpp         # заголовок 92 байта, разбор потока, NACK-коды — зеркало admin-web/.../protocol.ts
    crc32.h/.cpp            # та же таблица, что на сервере
    sha256.h, hmac.h        # переносимая реализация (27 КБ за миллисекунды и без аппаратного SHA)
    session.h/.cpp          # одно соединение: HELLO с nonce → приём → проверки в порядке displays.md → ответы
    app.h/.cpp              # BOOT → WIFI_CONNECTING → ONLINE → RECEIVING → VALIDATING → DISPLAY_UPDATING → ONLINE; ERROR → BACKOFF
    backoff.h               # 1, 2, 4, 8, 16, 30 с
    hal.h                   # интерфейсы: Panel, Storage, Net (TcpServer), Clock, Random, Backlight, Battery, Watchdog, Log
  src/esp32/                # CrowPanel: GxEPD2_579_GDEY0579T93 (CS 45, DC 46, RST 47, BUSY 48, SCK 12, MOSI 11 — сверить
                            # со схемой Elecrow), WiFi + WIFI_PS_MIN_MODEM, LittleFS, NVS, LEDC, АЦП, esp_task_wdt, кнопка
  src/host/                 # ПК: сокеты, каталог вместо flash, PNG кадра, «батарея» и «подсветка» в лог, режимы сбоев
  test/                     # unit-тесты ядра (pio test -e native, Unity)
  test/vectors/             # общие с сервером тестовые векторы (см. ниже)
```

Решения внутри ядра, которые стоит зафиксировать сразу:

- **Кадр во flash** — файл LittleFS `/frame.bin`: свой маленький заголовок (magic, версия картинки, ширина, высота, CRC32) и
  кадр. Запись атомарная: `/frame.tmp` → `rename`. При загрузке кадр с неверным CRC не показывается (остаётся то, что на
  панели, — e-paper держит картинку без питания). Износ flash — сотни записей за игру, это ничто.
- **Поворот и полярность** — у панели родное 792×272 (альбом), кадр приходит 272×792 (портрет): `setRotation`, и 1 в кадре =
  чёрный, как `drawBitmap(…, GxEPD_BLACK)` у GxEPD2. Кадр 26 928 байт — буфер в RAM, ESP32-S3 это не заметит.
- **Одно соединение**: новое вытесняет старое (полуоткрытое после обрыва Wi-Fi не должно блокировать дисплей навсегда).
- **Настройки** — NVS: SSID, пароль, id, секрет (32 байта), порт, ширина, высота. Первичная запись — через USB-консоль
  (`config set …` / вставить JSON, который выдаёт дашборд). Одинакового секрета на партию нет.
- **Порядок при загрузке**: питание панели (у CrowPanel — вывод питания e-paper, по примерам Elecrow GPIO 7) → показать кадр
  из flash → Wi-Fi → TCP-сервер.

## Общие тестовые векторы с сервером

Так же, как у `lootCrypto` (один секрет и один ожидаемый hex в тестах Kotlin и TS), протокол закрепляется общим файлом:

- скрипт на сервере (`admin-web/server/src/scripts/displayVectors.ts`) пишет `firmware/display/test/vectors/protocol-v1.json`:
  ключ, nonce, байты кадров (корректный IMAGE, HELLO, команды, испорченные — magic, версия, длина, CRC, подпись, чужой id,
  старая версия, обрыв) и ожидаемое решение для каждого (принять / NACK с кодом / закрыть);
- серверный тест проверяет, что файл совпадает с тем, что даёт `protocol.ts` сейчас (изменили протокол — забыли обновить
  векторы — красный тест, как `LogContractTest`);
- тесты ядра прошивки читают тот же файл. Расхождение реализаций красит один из двух наборов, а не всплывает на площадке.

Плюс известные значения: `crc32("123456789") = 0xCBF43926`, векторы HMAC-SHA256 из RFC 4231.

## Набор проверок совместимости (conformance)

Один инструмент для любой реализации дисплея — mock, сборка для ПК, Wokwi, QEMU, настоящая плата:

```bash
cd admin-web/server
npm run display-conformance -- --host 127.0.0.1 --port 47217 --id display-017 --secret <hex> [--width 272 --height 792]
```

Скрипт шлёт кадры сам, в том числе заведомо битые (обычный сервер такие не отправит), и сверяет ответы. Итог — таблица
«сценарий → ок / не ок, что пришло». Сценарии:

| № | Сценарий | Ожидается |
|---|---|---|
| C1 | подключиться | HELLO с верной подписью, id, размер панели, показанная версия |
| C2 | корректный IMAGE, версия выше | RECEIVED, затем DISPLAYED; HELLO следующего соединения показывает новую версию |
| C3–C5 | неверный magic / версия протокола / длина больше буфера | NACK с кодом и закрытие соединения |
| C6 | заголовок и половина payload, дальше тишина | соединение закрыто по таймауту payload, кадр не показан |
| C7 | испорченный байт payload | NACK BAD_CRC, показанная версия не изменилась |
| C8 | чужой секрет | NACK AUTH_FAILED |
| C9 | кадр, подписанный nonce прошлого соединения | NACK AUTH_FAILED (защита от повтора команд) |
| C10–C11 | версия ниже / равна показанной | NACK STALE_VERSION |
| C12–C13 | чужой id / не тот размер кадра | NACK WRONG_DEVICE / BAD_FORMAT |
| C14 | TEST, BACKLIGHT, REBOOT | OK; после REBOOT — снова HELLO с той же версией |
| C15–C16 | уровень подсветки 9 / неизвестный тип | NACK BAD_LENGTH / UNSUPPORTED_TYPE |
| C17 | второе соединение при открытом первом | обслуживается второе, первое закрыто |
| C18 | соединение без данных | закрыто по таймауту заголовка |
| C19 | 20 картинок подряд | все DISPLAYED, версии по порядку |
| C20 | IMAGE, пока идёт обновление панели | NACK BUSY или очередь — без показа старого поверх нового |

Сначала набор прогоняется против существующего mock-дисплея (в CI сервера) — так проверяется сам набор. Дальше против каждой
новой реализации — без правок.

## Этапы

У каждого этапа — чем проверить без платы и когда он считается готовым. Порядок важен: следующий этап опирается на
проверки предыдущего.

### Ф0. Решения до начала (владелец)

- Каркас: **PlatformIO + Arduino-ESP32 3.x** (рекомендую: GxEPD2 уже работает на этой панели, есть готовые примеры) или
  чистый ESP-IDF (больше контроля над Wi-Fi и питанием, но драйвер панели писать самим).
- Панель и плотность QR (см. «Размер QR» в displays.md): оставаться на 272 px и ≤ 2 слотах или брать панель крупнее; нужен ли
  уровень коррекции L для дисплеев.
- Способ первичной настройки плат: USB-консоль (рекомендую) или файл настроек, прошиваемый вместе с программой.
- Wokwi для CI: нужен токен Wokwi CI (есть бесплатный лимит — уточнить при регистрации); без него Wokwi только вручную.
- Есть ли на плате измерение напряжения батареи (делитель на АЦП) — по схеме Elecrow; нет — `batteryMv` в HELLO не шлём.

### Ф1. Ядро и unit-тесты (только ПК)

- `lib/core`: протокол, CRC, SHA-256/HMAC, сессия, машина состояний, backoff — через интерфейсы `hal.h`.
- Скрипт векторов на сервере + серверный тест «векторы актуальны».
- Тесты ядра (`pio test -e native`): векторы сервера, RFC 4231, разбор потока кусками произвольной длины, порядок проверок,
  монотонность версии, backoff, переходы состояний (включая «сбой → BACKOFF → WIFI_CONNECTING»).
- CI: новый `firmware.yml` (правка `firmware/` или `admin-web/server/src/displays/`) — тесты ядра.

**Готово, когда:** все векторы сервера проходят в C++, ветвление по каждому NACK покрыто тестом.

### Ф2. Прошивка на ПК против настоящего сервера (software-in-the-loop)

- `src/host`: TCP-сервер на POSIX-сокетах, «flash» — каталог, «панель» — PNG (как у mock), лог в stdout.
- Режимы сбоев флагами: задержка обновления панели, отказ панели, «упасть посреди записи кадра» (проверка атомарности),
  «зависнуть» (проверка сторожа — на ПК это внешний таймер, который убивает процесс).
- `npm run display-conformance` против сборки для ПК: C1–C20 зелёные.
- Живой прогон с дашбордом: добавить дисплей, прошить (записать настройки в «NVS» — файл), отправить контейнер, декодировать
  PNG обычным QR-декодером, сравнить со строкой печати (как уже сделано для mock).
- Отказоустойчивость на ПК:
  - `kill -9` в момент записи кадра → запуск → показан либо старый, либо новый кадр, не битый;
  - `kill -STOP` (дисплей «завис») → сервер: таймауты, 3 попытки, FAILED; `kill -CONT` → опрос досылает картинку;
  - остановить процесс → «нет связи»; запустить → «на связи», досылка не дошедшего.
- CI: сборка для ПК + набор совместимости против неё (секунды, без эмуляторов).

**Готово, когда:** сервер не отличает сборку для ПК от mock-дисплея, все сценарии C1–C20 и сбои выше — зелёные в CI.

### Ф3. Сборка для ESP32-S3 — компиляция и драйверы

- `src/esp32`: GxEPD2 (`GxEPD2_BW<GxEPD2_579_GDEY0579T93, …>`), Wi-Fi с backoff и энергосбережением, lwIP-сокеты (тот же код
  сессии), LittleFS, NVS, LEDC для подсветки, АЦП батареи, `esp_task_wdt`, кнопка подсветки, USB-консоль настроек,
  диагностический экран TEST.
- CI: `pio run -e crowpanel579` — сборка без предупреждений, отчёт о размере прошивки и RAM (кадр 27 КБ + буфер GxEPD2 27 КБ —
  следить, что остаётся запас).
- Проверка без платы — только компиляция и ревью драйверов по примерам Elecrow/GxEPD2 для этой панели.

**Готово, когда:** сборка для платы зелёная в CI, всё платформенное — за интерфейсами `hal.h`, в ядре нет ни одного `#ifdef ESP32`.

### Ф4. Wokwi: настоящая сборка ESP32-S3 в эмуляторе

- Wokwi эмулирует ESP32-S3 с Wi-Fi; порт TCP-сервера пробрасывается на ПК (`[[net.forward]]` в `wokwi.toml`), так что
  сервер мастера и набор совместимости подключаются к эмулируемой плате как к настоящей.
- Панель 5.79″ Wokwi не эмулирует: вариант сборки `crowpanel579-wokwi` с заглушкой панели, которая печатает в serial CRC кадра
  и версию (вместо GxEPD2). Всё остальное — Wi-Fi, сокеты, LittleFS, NVS, сторож, машина состояний — настоящее.
- Что проверяем: C1–C20 через проброс порта; загрузка без Wi-Fi и повторное подключение с backoff (сценарий Wokwi с отключением
  сети, если поддерживается, иначе — вручную); перезагрузка по REBOOT и по сторожу; восстановление кадра из LittleFS.
- CI (если есть токен): `wokwi-cli` в `firmware.yml` — прогон со сценарием и проверкой строк serial-лога.

**Готово, когда:** набор совместимости зелёный против эмулируемой ESP32-S3; сторож перезапускает зависший цикл, кадр
восстанавливается.

### Ф5. QEMU от Espressif (необязательно, если Wokwi хватило)

QEMU Espressif запускает ESP32-S3 с сетью через эмулируемый Ethernet (openeth). Wi-Fi-стек так не проверить (нужна отдельная
сетевая прослойка в сборке), зато бесплатно и без аккаунта — годится как запасной путь для CI: загрузка, flash, сторож,
TCP-сессия.

### Ф6. Нагрузка без железа

- 30 экземпляров сборки для ПК (разные порты, разные секреты) + сервер: групповая отправка на 1, 5, 10, 30; время до
  «показан» по каждому, лимит `DISPLAY_MAX_CONCURRENT`, один «зависший» (`kill -STOP`) не задерживает остальных.
- Плохая сеть на ПК (Linux `tc netem`: задержка 200 мс, потери 5–10 %) — повторы и таймауты сервера в условиях, похожих на
  дальние точки mesh. Подобрать `DISPLAY_*_TIMEOUT_MS` по результату.

**Готово, когда:** 30 из 30 при нормальной сети, при потерях — FAILED только с понятной ошибкой и досылка по опросу.

### Ф7. Читаемость QR — бумага в масштабе панели

Без платы, но на реальных телефонах игроков: кадр из предпросмотра печатается в физическом размере (≈145 dpi, лист
47,6 × 138,6 мм). Контейнеры на 1, 2, 3 слота; расстояние и свет как на площадке; несколько моделей телефонов. Итог — сколько
слотов допустимо на выбранной панели (и нужен ли уровень L). Это главный риск всей затеи, его стоит закрыть **до закупки
партии**.

### Ф8. День с платой

Когда появится первая плата — ничего нового не писать, только прогнать готовое:

1. Прошить, записать настройки через USB-консоль, добавить в дашборд.
2. `npm run display-conformance` против платы — те же C1–C20.
3. Отсканировать QR с e-paper телефонами игроков (сравнить с бумагой из Ф7).
4. Замерить то, что без железа не измерить (таблица ниже), и заполнить таблицу токов в displays.md.
5. Проверки на площадке из displays.md: mesh, роуминг, дальние точки, 30 устройств.

## Что без железа не проверить

| Что | Почему | Когда |
|---|---|---|
| Время и качество обновления e-paper, «призраки» | эмуляторы панель 5.79″ не моделируют | Ф8 |
| Контраст и читаемость QR на самом e-paper, с подсветкой | бумага — оптимистичная оценка | Ф8 (после Ф7) |
| Токи: Wi-Fi в простое, приём, обновление панели, подсветка; автономность 3–5 суток на 21700 | нужны плата и амперметр | Ф8 |
| Wi-Fi: modem sleep и задержка входящего соединения, roaming в UniFi mesh, дальние точки | эмулятор не моделирует радио | Ф8, на площадке |
| Реальные выводы и схема платы (питание панели, делитель батареи, кнопка) | только по документации Elecrow | Ф8 |

## Что уже можно сделать на сервере до прошивки

- Режимы сбоев mock-дисплея флагами командной строки (сейчас только в тестах) — для ручных прогонов.
- Скрипт «сервер + N mock-дисплеев одной командой» — для Ф6 до появления сборки для ПК.
- `display-conformance` и векторы — они нужны уже в Ф1–Ф2 и сразу проверяются на mock-дисплее.
