## Досье
- Сообщение мира `state` (в `tick`-режиме): у каждого ICE `c` [x,z] клетка, `d` [dx,dz] направление, `st` 0..3 (Патруль, Взгляд, Проверка, Поиск), `nc`/`nd` клетка и направление после следующего шага, `aw` счётчик 0..6, плюс прежние `id,p,f,s,b`; в корне `tk`: `{n, at, win, inh, mv}`
  (`n` — номер такта, `at` — время последнего такта (в часах сервера, как `k`), `win` — окно, `inh` — «вдох» идёт, `mv` — твой ход уже принят). Сервер: `gray_node.gd` `_add_tick_fields` / `_tick_field`.
- Клиент: `rig_test_scene.gd` `apply_state` (≈215: ICE по `id` создаются `_make_ice`, позиции — через `remote.on_state`, `RemoteTracks.ice_pose`, задержка `ICE_DELAY` 0,15 с), `IceView` (`ice_view.gd`: состояния 0..3, метка «?/!»), `TeleportAim` (`ui/teleport_aim.gd`: `show_at(start, target, ok, charge, kind, reason)`, рамка клетки, метка причины),
  `XRRig._show_aim` / `_fire_teleport` (`xr_rig.gd`: `grid.pick` → `kind` hop/wait/denied, `teleport_cooldown_left`, `teleport_attempted`).
- Общий код видимости: `TickVision.classify(grid, ice_cell, dir, target_cell, sight_cells, half_deg, focus_deg)` (0 не виден, 1 периферия, 2 фокус), `TickVision.visible_cells(...)`; константы конуса: 50° / 25°.
- Шаг ICE между клетками: плавно за 0,4 с (не рывок) — сейчас ICE приходит 10 раз/с, а клетка меняется скачком на 2 м.

## Что сделать (один коммит на шаг; после каждого — `netrun/tools/dev.sh test <наборы>`)

1. **`TickForecast`** (`class_name TickForecast`, `RefCounted`, статические чистые функции): `threat(grid: NodeGrid, intents: Array, cell: Vector2i) -> int` — 0 зелёный (никто из ICE не увидит клетку после следующего такта), 1 жёлтый (периферия), 2 красный (фокус; или ICE в состоянии Поиск, чей `nc` не дальше 2 м от клетки — предзахват);
   `intents` — список словарей `{c, d, st, nc, nd, sc}` (клетки как `Vector2i`), прогноз считается по `nc`/`nd`. `static func parse_intents(ice_list: Array) -> Array` — из поля `ice` сообщения (пропускает записи без `c`; Black ICE — по `c`/`d` без намерения).
   Сервер: `_add_tick_fields` добавляет `sc` (число клеток зрения ICE; Black — его дальность в клетках, `round(sight_range / NodeGrid.CELL_M)`). Тесты `tick_forecast_test.gd`: зелёный за колонной; жёлтый на периферии следующего шага; красный в фокусе; предзахват: Поиск, `nc` рядом — красный; пустой список — 0; разбор сообщения.
2. **Приём на клиенте.** `RemoteTracks`: хранит последние намерения (`intents`) и `tick` (`tk`) из `on_state`; методы `intents() -> Array`, `tick_info() -> Dictionary` (пусто в `realtime`). Шаг ICE на клиенте — плавно 0,4 с: когда клетка ICE сменилась, позиция идёт от старого центра к новому ровно 0,4 с
   (реализуй так, как проще и надёжнее: например, твин в `IceView` на смену `c`, а `p` из сообщения — только первое появление; поворот глаза — тоже плавно). Тесты на `RemoteTracks`/логике шага.
3. **Свет зрения на полу и стрелка.** `TickFloor` (`Node3D`; клиент создаёт одну на узел): по намерениям каждого ICE рисует на полу клетки зрения — `TickVision.visible_cells` для текущей позиции (фокус ярче, периферия тусклее; цвет по состоянию `st`: белый / жёлтый / оранжевый / красный, прозрачность ≈ 0,35 и 0,15 для фокуса и периферии) и для будущей позиции (`nc`/`nd`) — тусклее и другим оттенком; клетки — через `MultiMesh` из плоских квадратов (не по узлу на клетку).
   Над ICE — стрелка к `nc` (если ICE сдвинется или повернётся; стоит — без стрелки); при предзахвате стрелка красная и целится в клетку игрока. Глаз ICE: цвет по `st` (белый, жёлтый, оранжевый, красный) на модели ICE (`IceView`): небольшой светящийся элемент у головы; метка «?/!» остаётся. Вдох: когда `tk.inh` стал 1 — свет пола один раз пульсирует за 0,5 с (яркость ×1,6 и обратно);
   звук вдоха — НЕ делать. В `realtime`-режиме `TickFloor` не создаётся.
4. **Рамка прицела по прогнозу и ходы.** `TeleportAim.show_at`: для `kind == "hop"` в тактовом режиме цвет рамки — `TickForecast.threat` целевой клетки: зелёный / жёлтый / красный (цвета `OK_COLOR`, новая `WARN_COLOR`, `NO_COLOR`); «ход принят» (`tk.mv == 1`): рамка нейтральная, метка «ХОД ПРИНЯТ», прыжок не запрашивается до следующего такта;
   `wait` (своя клетка): метка «ЖДАТЬ · ОКНО ЧЕРЕЗ N» (N — секунды до такта по окну: `tk.at + tk.win − сейчас`, округлить вверх; считать по часам сервера клиента `ServerClock`/`remote.clock`), и в тактовом режиме курок на своей клетке посылает серверу `request_teleport` на центр своей клетки (сервер считает это ходом «ждать»).
   Красная рамка «залипает» (С9): прыжок на красную клетку — только если рамка простояла на этой клетке ≥ 0,4 с, иначе отмена без запроса. В тактовом режиме клиентская перезарядка телепорта не применяется (сервер сам: `moved`); отказ сервера с причиной `moved` показывается меткой «ХОД ПРИНЯТ». `teleport_attempted` для залипания — причина `hold`.
   Журнал клиента: строка `tick n=… inh=… mv=…` при каждой смене номера такта (одна на такт), в `rig.teleport` — поле `threat=0|1|2` (если есть прогноз). Тесты: цвет рамки по `threat`, метка «ХОД ПРИНЯТ», метка «ЖДАТЬ» с числом, залипание красной (чистая функция в `TickForecast` или `RigMath`: `red_hold_ok(held_sec)`), `TickFloor` строит ожидаемое число экземпляров для известного намерения, `realtime` — ничего нового.
5. **Кадр для проверки глазами.** Добавь в `rig_test_scene.gd` метод `show_tick_demo()` (как `show_ended`): две колонны узла, ICE в состоянии Проверка смотрит вдоль прохода с колонной (свет фокус/периферия, стрелка к следующей клетке), второй ICE в Поиске с красной стрелкой на клетку игрока, рамка прицела жёлтая на соседней клетке. Сними `netrun/tools/dev.sh shot` (одна сетка ≤ 1024 px) и отдай кадр агенту `visual-reviewer` с чек-листом:
   «колонны видны; свет на полу двух цветов (фокус ярче периферии); есть стрелки; красная стрелка у Поиска; рамка цветная; кадр не чёрный». Результат (PASS/FAIL по строкам) — в отчёт; провалы чини.
6. **Полный прогон:** `netrun/tools/dev.sh test --all` — только в фоне; итог — число тестов и падений.
