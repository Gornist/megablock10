# Замер G2: 12 узлов в одном мире

Стенд — `netrun/tools/bench_world.gd`. Вопрос: тянет ли один процесс Godot без экрана (сервер мира) 12 узлов в одном мире,
по 1–2 ICE в каждом, и десять нетраннеров. Мини-ПК класса M920q — целевая машина (docs/netrun-vr-hardware.md).

## Как запускать

```sh
godot --headless --path netrun --quit-after 6000 -s res://tools/bench_world.gd -- --nodes=12 --bots=10 --seconds=60
```

- **`--quit-after` — до `--`.** После `--` Godot его не видит, и процесс не выходит. Число кадров — с запасом (кадры
  ограничены 60/с, `seconds=60` — 3600 кадров); штатно стенд выходит сам по `--seconds`.
- Первый раз на чистой копии — `godot --headless --path netrun --import --quit-after 200` (кэш классов, без него `-s` не видит `class_name`).
- Аргументы после `--`: `--nodes=12`, `--bots=10`, `--seconds=60`, `--occupied=<узлов с ботами>` (по умолчанию две трети узлов:
  при 12 узлах — 8, остальные 4 пустые, их ICE спит), `--port=18400`.
- Один процесс за раз. Мост не используется (токены из словаря, ценностей нет). Сервер и боты — в одном процессе, у каждого свой
  `MultiplayerAPI`, как в `tests/multi_client_test.gd`; боты ходят кругами у входа (LOITER) и не заканчиваются.

Состав: по экземпляру `GrayNode` на узел (`node_01`…), в чётных по номеру узлах 2 ICE, в нечётных 1; боты раздаются по первым
`occupied` узлам по кругу. Первая строка — `bench start …` (сколько узлов и ICE), дальше раз в 5 с строка `bench`, в конце `bench ИТОГ`.

## Поля

| Поле | Что это |
|---|---|
| `t` | секунды с начала замера |
| `nodes`, `bots` | узлов и ботов |
| `step_avg_us` | за окно 5 с: сумма времени `_physics_process` всех узлов на один физический тик (60 Гц), мкс. Это вся работа сервера мира на тик |
| `step_max_us` | наибольший шаг одного узла с начала замера (мкс), накопительный |
| `frame_avg_ms` | средняя за окно работа кадра: `_process` + физика по `Performance`, мс. Стенные часы кадра не годятся: `max_fps` = 60 держит 16.7 мс всегда. Включает работу ботов-клиентов в том же процессе (без отрисовки), то есть чуть завышена против чистого сервера |
| `mem_mb` | статическая память Godot, МБ |
| `sent_kbps` | байты полезной нагрузки сервер → клиенты за окно (`NetServer.bytes_sent_total`, без заголовков ENet/UDP), кбит/с, суммарно по всем ботам |

Итог (`bench ИТОГ`) дополнительно: сколько ботов подключено и сколько узлов с игроками; `sent_kbps_avg` — среднее за весь замер.
Бюджет: 60 Гц — 16 667 мкс на тик; шаг сервера должен занимать малую долю, `step_max_us` — не вылезать за 16.7 мс.

## Известные ограничения стенда

- Игровая логика пока рассчитана на один узел: геометрия комнаты и маршруты ICE — константы `NodeLayout`, позиции аватаров
  зажимаются в эту комнату. Поэтому 12 экземпляров `GrayNode` разделены логически (`NetServer.set_node`, фильтр видимости
  и «ICE спит без игроков»), а не координатами. На стоимость кадра это почти не влияет, но «разнесение в пространстве» пока не проверено.
- Каждый `GrayNode` подписан на `session_joined` и заводит `DaemonSession` и `TraceMeter` для каждой сессии, а не только своего узла
  (в логе — «вошёл в node_07» по числу узлов на каждого бота), и `_tick_traces` обходит все сессии в каждом узле. Растёт как
  узлы × игроки; на 12 × 10 мало, но это кандидат на исправление при реальном многоузловом мире (в игровой код стендом не вмешивались).
- `step_max_us` накопительный: один выброс остаётся в нём до конца замера.

## Долгий прогон (P7)

`netrun/tools/soak.sh --hours=1` на devbox (i7-9700T, Ubuntu 24.04): настоящий Мост (`--test --seed`), сервер мира, 8 ботов
отдельными процессами (половина — с эмуляцией потерь и задержки в клиенте), плановые убийства сервера мира раз в 20 мин и
ботов посреди забега. Нагрузка примерно на порядок выше живой игры.
