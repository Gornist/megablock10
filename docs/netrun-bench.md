# Замер G2: 12 узлов в одном мире

**Статус:** актуально как описание стенда сервера мира; цифры — состояние на 02.10.2026 (прежний devbox, Ubuntu 24.04), после перехода на тактовую игру и
переустановки машины 25.10 не пересняты. Стенд `bench_world.gd` не менялся с создания (`3e62b793`), опирается на `GrayNode.step_stats()` (есть в `server/node/gray_node.gd`);
запуск на текущем коде в этой сверке не гонялся. Сверено с main 30.10.2026.
Замеры **кадра на очках** (GPU мс, `[render] bench`, `probe`, пресеты `pico_stand.sh`) — другой стенд и в этом файле их нет: они в `netrun/tools/pico_stand.sh` (комментарий пресетов),
[netrun-refactor-plan.md](netrun-refactor-plan.md) и журналах серий `~/pico-series/<время>` на devbox.

Стенд — `netrun/tools/bench_world.gd`. Вопрос: тянет ли один процесс Godot без экрана (сервер мира) 12 узлов в одном мире,
по 1–2 ICE в каждом, и десять нетраннеров. Мини-ПК класса M920q — целевая машина (docs/netrun-vr-hardware.md).

## Как запускать

```sh
godot --headless --path netrun --quit-after 6000 -s res://tools/bench_world.gd -- --nodes=12 --bots=10 --seconds=60
```

- **`--quit-after` — до `--`.** После `--` Godot его не видит, и процесс не выходит. Число кадров — с запасом (кадры
  ограничены 60/с, `seconds=60` — 3600 кадров); штатно стенд выходит сам по `--seconds`.
- Первый раз на чистой копии — `godot --headless --path netrun --import --quit-after 200` (кэш классов, без него `-s` не видит `class_name`).
- Аргументы после `--`: `--nodes=12`, `--bots=10`, `--seconds=60`, `--occupied=<узлов с ботами>` (по умолчанию две трети узлов:
  при 12 узлах — 8, остальные 4 пустые, их ICE спит), `--port=18400`.
- Один процесс за раз. Мост не используется (токены из словаря, ценностей нет). Сервер и боты — в одном процессе, у каждого свой
  `MultiplayerAPI`, как в `tests/multi_client_test.gd`; боты ходят кругами у входа (LOITER) и не заканчиваются.

Состав: по экземпляру `GrayNode` на узел (`node_01`…), в чётных по номеру узлах 2 ICE, в нечётных 1; боты раздаются по первым
`occupied` узлам по кругу. Первая строка — `bench start …` (сколько узлов и ICE), дальше раз в 5 с строка `bench`, в конце `bench ИТОГ`.

## Поля

| Поле | Что это |
|---|---|
| `t` | секунды с начала замера |
| `nodes`, `bots` | узлов и ботов |
| `step_avg_us` | за окно 5 с: сумма времени `_physics_process` всех узлов на один физический тик (60 Гц), мкс. Это вся работа сервера мира на тик |
| `step_max_us` | наибольший шаг одного узла с начала замера (мкс), накопительный |
| `frame_avg_ms` | средняя за окно работа кадра: `_process` + физика по `Performance`, мс. Стенные часы кадра не годятся: `max_fps` = 60 держит 16.7 мс всегда. Включает работу ботов-клиентов в том же процессе (без отрисовки), то есть чуть завышена против чистого сервера |
| `mem_mb` | статическая память Godot, МБ |
| `sent_kbps` | байты полезной нагрузки сервер → клиенты за окно (`NetServer.bytes_sent_total`, без заголовков ENet/UDP), кбит/с, суммарно по всем ботам |

Итог (`bench ИТОГ`) дополнительно: сколько ботов подключено и сколько узлов с игроками; `sent_kbps_avg` — среднее за весь замер.
Бюджет: 60 Гц — 16 667 мкс на тик; шаг сервера должен занимать малую долю, `step_max_us` — не вылезать за 16.7 мс.

## Известные ограничения стенда (на момент замера 02.10; не пересмотрены)

- Игровая логика пока рассчитана на один узел: геометрия комнаты и маршруты ICE — константы `NodeLayout`, позиции аватаров
  зажимаются в эту комнату. Поэтому 12 экземпляров `GrayNode` разделены логически (`NetServer.set_node`, фильтр видимости
  и «ICE спит без игроков»), а не координатами. На стоимость кадра это почти не влияет, но «разнесение в пространстве» пока не проверено.
- Каждый `GrayNode` подписан на `session_joined` и заводит `DaemonSession` и `TraceMeter` для каждой сессии, а не только своего узла
  (в логе — «вошёл в node_07» по числу узлов на каждого бота), и `_tick_traces` обходит все сессии в каждом узле. Растёт как
  узлы × игроки; на 12 × 10 мало, но это кандидат на исправление при реальном многоузловом мире (в игровой код стендом не вмешивались).
- `step_max_us` накопительный: один выброс остаётся в нём до конца замера.

## Замер на очках без человека

Очки лежат на столе, голова не вертится — но трекинг всё равно шлёт позу. Поэтому поза камеры фиксируется целиком, а сравнения идут внутри одного запуска
игры (шум между запусками ±1 мс). Код — `netrun/client/bench_run.gd` (`BenchRun`), ключи — `[render]` в `netrun.cfg` (описание в шапке `shared/render_config.gd`).

| Ключ | Умолчание | Смысл |
|---|---|---|
| `bench` | `""` | пресет `EyePresets` (`entry`, `wedge`, `floor_down`, `floor_horizon`, …); пусто — замера нет |
| `bench_lock` | `true` | после прогрева каждый кадр: `rig.global_transform = поза_камеры_пресета * camera.transform.affine_inverse()` — поза `XRCamera3D` (позиция, наклон, крен) совпадает с пресетом при любом трекинге. `false` — прежнее: один раз по позиции и рысканию |
| `bench_settle_s` | 10 | прогрев до первого окна, с |
| `bench_runs` | 3 | число окон; с `bench_ab` округляется вверх до чётного |
| `bench_run_s` | 20 | длина окна, с |
| `bench_ab` | `""` | `имя=a\|b` — A/B внутри сессии, окна идут A,B,A,B… |
| `bench_ab_settle_s` | 2 | выдержка после смены варианта перед окном, без учёта |

Новые пресеты для пола: `floor_down` (вход, глаза 1,2 м, взгляд вдоль комнаты на 15° ниже горизонта) и `floor_horizon` (тот же вход, взгляд на горизонт).

**A/B.** `msaa` — `Viewport.msaa_3d` (0/2/4/8): проверка счётчика GPU, на Pico MSAA 4× дороже 2× больше чем на 2 мс. Ручки `AssetMaterials.KNOBS` меняются живьём,
только если это прямой uniform шейдера облака (`cloud_dark`) на уже созданных материалах: `dust_cell`, `dust_fps`, `dust_fill`, `dust_fill_lo`, `dust_fill_hi`, `dust_sharp`,
`cloud_edge_mix` и ручки света облака `cloud_light`, `lit_ambient`, `lit_dim`, `lit_edge`, `lit_tint`. Остальные ручки читаются при создании материалов (`apply()`):
замер идёт без A/B, в журнале строка `[bench] ab: ручка <имя> не меняется живьём` — их сравнивают двумя запусками (серией `pico_series.sh`).

**CSV кадров.** `user://bench/<пресет>-<ГГГГММДД-ЧЧММСС>.csv` (на очках `files/bench/`), строка на кадр окна, заголовок `run,variant,frame,t_ms,frame_ms,gpu_ms`:
`run` с 1, `variant` — `A`/`B`/`-`, `frame` с 0 в окне, `t_ms` от начала окна, `gpu_ms` = −1 — рендерер не отдал время. Запись — в конце каждого окна (файл переписывается целиком).
Путь ОС — строка `[bench] csv=<путь>`. Кадры выдержки A/B в CSV не попадают.

**Строки журнала.**
- `[bench] proj p11_l=… p11_r=… viewport=WxH msaa=N` — один раз после прогрева; `p11` — `[1][1]` проекции левого и правого глаза со знаком (знак `PROJECTION_MATRIX[1][1]` в шейдерах на Pico).
- `[bench] run=i fps=… avg_ms=… max_ms=… gpu_avg_ms=… frame_p50=… frame_p95=… frame_peak=… frame_over=… gpu_p50=… gpu_p95=… gpu_peak=… gpu_over=… [variant=A|B]` — окно.
- `[bench] ИТОГ preset=… runs=… median_fps=… … avg_max=…` — старые поля (медиана окон, min/max окон), дальше в конце перцентили по сырым кадрам всех окон.
- `[bench] AB-var …` по варианту (медианы его окон) и `[bench] AB name=… a=… b=… d_gpu_p50=… d_gpu_p95=… d_frame_p50=…` — разница B − A (`n/a`, если нет данных GPU).
- Перцентили — по сырым кадрам: сортировка, индекс `ceil(q·n) − 1`. `*_over` — доля кадров строго дольше 11,11 мс (бюджет 90 Гц); `*_peak` — максимум. Кадры без GPU-времени в статистику GPU не входят.

Читать: сначала `gpu_p95` и `gpu_over` (хвост важнее среднего: кадры > 11,11 мс — пропуски 90 Гц), потом `gpu_p50`; `frame_*` — то, что видит игрок, `gpu_*` — вклад рендера;
расхождение окон одного варианта (`AB-var`, строки `run=`) — шум замера: разница `B − A` меньше него не значима.

**Серия.** `pico_series.sh` забирает CSV в `<результаты>/<имя>-bench/` (через `adb exec-out run-as com.megablok10.netrun tar c files/bench`, запасной путь —
`/sdcard/Android/data/com.megablok10.netrun/files/bench/`), в `<имя>.txt` попадают строки `[bench] AB`, `proj`, `csv` и итог. Пример — цена MSAA 4× против 2× на полу:

```
pico_series.sh "ab=bench bench=floor_down bench_ab=msaa=2|4"
```

Живая ручка: `pico_series.sh "ab=bench bench=floor_down bench_ab=cloud_light=0|1"`.
