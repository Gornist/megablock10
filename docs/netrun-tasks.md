# «Сеть»: план работ по задачам для отдельных агентов

План [netrun.md](netrun.md) разбит на задачи, каждую из которых можно отдать отдельному агенту или сессии. Цель — экономия
лимитов: дорогая модель (Opus) только проектирует контракты, принимает решения на воротах этапов и проверяет код, который
двигает ценности. Остальное делают Sonnet и Haiku по карточкам ниже, не читая весь план.

## Как пользоваться

1. Выбрать задачу, у которой выполнены зависимости (колонка «После» в сводке).
2. Создать рабочую копию от интеграционной ветки: `scripts/agent-worktree.sh new netrun-<id> agent/netrun`
   (например, `netrun-b1`). Одна задача — одна ветка — один исполнитель.
3. Открыть новую сессию в этой копии с моделью из карточки и вставить **общий промпт** (ниже) и **карточку задачи** целиком.
4. Агент заканчивает коротким отчётом (формат в общем промпте). Вливает в `agent/netrun` владелец или сессия-координатор:
   `git -C ../megablock10-wt/netrun merge --ff-only agent/netrun-<id>` (или rebase, если `agent/netrun` ушла вперёд).
   В `main` — только по команде владельца, как и всё остальное.
5. Отметить задачу в сводке: `[x]`, хеш коммита.

Задачи с пометкой **Opus-ревью** после выполнения отдаются на проверку дорогой модели с одним вопросом: «проверь diff
`agent/netrun..agent/netrun-<id>` на нарушение инвариантов из карточки». Это дешевле, чем писать код дорогой моделью.

### Какая модель где

| Модель | Когда |
|---|---|
| **Opus** | контракты между частями (протокол Моста, формат записей мира), извлечение общего кода из `:app`, ревью операций с ценностями, решения на воротах этапов |
| **Sonnet** | почти весь код: Godot, Мост, приложение, CI, тесты, сценарии e2e |
| **Haiku** | механика: скрипты adb, чек-листы, протоколы плейтестов, каталоги событий, разбор журналов по готовой инструкции |
| **Владелец** | всё, что нужно почувствовать в очках или решить за игру; агент только готовит сборку, чек-лист и разбирает журнал |

Сабагенты внутри одной сессии (инструмент Agent с `model: sonnet`/`haiku`) тоже подходят, но отчёт всё равно читает
родительская модель — держите отчёты короткими.

## Общий промпт (вставлять перед каждой карточкой)

```
Ты работаешь в репозитории LARP «Мегаблок №10» над частью «Сеть» — VR-клиентом нетраннера.
Коротко: нетраннер садится у стойки-терминала, телефоном сдаёт «деку» программ (демонов), надевает Pico 4 и сидя проходит
3D-киберпространство: узлы с данными (шардами) и защитой (ICE). Добыча возвращается на телефон.
Части:
- netrun/ — один проект Godot 4: клиент для Pico 4 (APK, стандартный OpenXR), сервер мира (--headless, метка
  dedicated_server), плоская отладочная сборка для разработки и ботов. Сервер решает всё, клиент — только своё движение.
- :netrun-bridge — Мост, Kotlin + :kit, на том же мини-ПК. Хранит документы (тип, id, версия, JSON) в памяти и SQLite,
  API: чтение, запись с проверкой версии, поток изменений по WebSocket. Предметы меняют владельца только отдельными
  операциями с номером запроса (повтор не выполняется второй раз).
- Мост — такой же участник, как телефон: обменивается с телефонами подписанными карточками с квитанциями (kit Handover),
  синхронизируется с коллектором (kit SyncEngine). Центрального хранилища у игры нет.
- Интернета на площадке нет. Всё работает в локальной сети по Wi-Fi.

Правила:
- Прочитай CLAUDE.md и только те разделы docs/netrun.md, что указаны в карточке. Весь план не читай.
- Делай только свою карточку. Чего-то не хватает или карточка противоречит коду — остановись и напиши об этом в отчёте,
  не расширяй задачу сам.
- Не трогай admin-web/ (это соседняя сессия). Нужна правка там — опиши её в отчёте.
- Коммиты на русском: что и почему. Добавляй файлы по пути, не git add -A. После каждого коммита сборка и тесты зелёные.
- Не пушь и не открывай PR, если карточка не говорит иначе.
- Отчёт в конце — не больше 15 строк: что сделано (коммиты), как проверено (команды и результат), что не сделано и почему,
  вопросы владельцу.
```

## Карточки задач

Каждая карточка — самостоятельное задание. «Читать» — какие разделы `docs/netrun.md` и какие файлы открыть, кроме CLAUDE.md.

### Подготовка

**R1. Подбор очков и софта** · Sonnet с доступом в интернет
- Задание целиком — [netrun-vr-hardware-brief.md](netrun-vr-hardware-brief.md). Общий промпт не нужен.
- Результат: `docs/netrun-vr-hardware.md`. Из него берётся закреплённая версия Godot для G0 и список закупки для R2.

**C1. Контракт: протокол Моста** · Opus
- Читать: «Архитектура», «Устройство Моста», «Сервер мира и клиент», «Забег»; kit `handover/Handover.kt`, `HandoverRules.kt`.
- Сделать: `docs/netrun-bridge-protocol.md` — сообщения WebSocket в JSON (чтение, запись с версией, подписка на изменения,
  ошибки), схема документа, список типов документов этапов 0–4 (узел, сессия, дека, предмет в узле, терминал, настройки),
  операции с ценностями (сдать деку, взять из узла, выдать на телефон, оставить в узле) с номером запроса и ответами, токен
  терминала и сессия игрока, версия протокола. По примеру на каждое сообщение.
- Готово: по документу B0, B1, F1 и V2 можно писать без вопросов; каждая операция с ценностями описывает, что будет при
  повторе и при обрыве.

**C2. Контракт: записи мира и быстрые события** · Opus
- Читать: «Архитектура», «Инструменты мастера», «Площадка и эксплуатация»; kit `sync/SyncEngine.kt`; как коллектор
  принимает записи (`admin-web/server` — только чтение).
- Сделать: `docs/netrun-world-records.md` — какие записи Мост пишет в коллектор (вход, выход, флэтлайн, смена владельца
  предмета, тревога аудитора), формат совместимый с текущим синком, и быстрые события на точки (что, кому, как). Отдельным
  разделом — запрос к сессии коллектора (M7).
- Готово: формат не ломает текущий коллектор (неизвестные записи он игнорирует или это указано как правка для M7).

**G2. Замер: 12 узлов в одном мире** · Sonnet

- Готово: цифры на машине разработчика; оценка запаса для мини-ПК класса M920q.

**B0. Мост: документы и хранилище** · Sonnet

- Сделать: модуль `:netrun-bridge` (чистый JVM, зависит от `:kit`); хранилище документов в памяти с записью каждого изменения

- Готово: JUnit — конфликт версий, перезапуск сохраняет всё, оборванная транзакция не оставляет половины. `./gradlew

**B1. Мост: API по WebSocket** · Sonnet

- Сделать: сервер WebSocket по протоколу C1: чтение, запись, подписка на поток изменений по типу документа; проверка токена.
- Готово: тест с настоящим клиентом WebSocket — два подписчика видят одно изменение; запись со старой версией отклонена.

**B2. Мост: правила** · Sonnet
- Читать: «Устройство Моста» (правила, «кнопка раньше автоматики»), код B0.
- Сделать: регистрация правил «на изменение документа типа X» и «по таймеру»; числа правил читаются из документов настроек;
  правило не может менять ценности (только через B3). Одно правило-пример: «терминал молчит дольше N с → флаг в документе
  терминала».
- Готово: тесты с поддельными часами.

**B3. Мост: операции с ценностями и аудитор** · Sonnet, Opus-ревью
- Читать: «Устройство Моста» (ценности, аудитор), C1 (операции), kit `HandoverRules.kt`, раздел «Инварианты» в CLAUDE.md.
- Сделать: четыре операции из C1 — каждая одна транзакция, номер запроса хранится с ответом, повтор возвращает тот же ответ;
  аудитор раз в N секунд проверяет «у каждого предмета ровно один владелец» и пишет тревогу документом.
- Инварианты для ревью: ни один путь не создаёт и не теряет предмет; повтор не выполняется второй раз; ошибка посреди
  операции не оставляет предмет без владельца или с двумя.
- Готово: тесты на повтор, на обрыв посреди операции, на гонку двух операций за один предмет.

**F1. Фейки** · Sonnet
- Читать: C1, `netrun/README.md`.
- Сделать: в Godot — фейковый Мост (GDScript, тот же протокол, данные из JSON-фикстуры), чтобы сервер мира запускался без
  Kotlin; в `:netrun-bridge` — фейковый сервер мира (тестовый клиент, который входит, берёт шард и выходит).
- Готово: оба фейка используются хотя бы одним тестом на своей стороне.
