# Прогоны на двух эмуляторах + дашборд

Стенд из двух эмуляторов (Alice/Neon и Bob/Rats), коллектора `admin-web` и сценариев с проверками.
Нужны: Android SDK с AVD `Medium_Phone_API_35` и `Second_API_35` (клон первого), `node@22` (Homebrew; подойдёт и `node@20`), `sqlite3`, `gradle` c JDK 17.

```bash
scripts/e2e/up.sh            # сервер + эмуляторы + APK + персонажи + связь пиров (~3 мин)
scripts/e2e/run-all.sh       # все сценарии; код возврата 1, если что-то красное
scripts/e2e/perf-breach.sh    # грубый замер нагрузки CPU от матрицы взлома (нужен up.sh)
scripts/e2e/seed.sh          # насытить стенд тестовыми данными для показа интерфейсов (~1 мин), см. ниже
scripts/e2e/scenarios/slot-race.sh   # или один сценарий
scripts/e2e/shot.sh имя      # скриншоты обоих экранов
scripts/e2e/down.sh          # остановить всё
```

`up.sh` флаги: `--no-build` (не пересобирать APK), `--keep-data` (не сбрасывать БД сервера и данные телефонов), `--clock N` (игровые часы в N раз быстрее, по умолчанию 60), `--timer N` (таймер взлома ×N, по умолчанию 10).

## Сценарии-провокаторы для детекторов аномалий

Детекторы коллектора (тревоги «Требует внимания») проверены юнит-тестами, а здесь — на живом сервере. `scripts/e2e/anomaly-all.sh` гоняет `scenarios-anomaly/*.sh`: каждый сценарий делает провокацию, ждёт тревогу нужного вида (`kind`) и проверяет, что **без провокации** этой тревоги нет (ложные срабатывания так же важны). Эмуляторы не нужны: сценарии идут на **отдельном** сервере (порт 2518, пустая БД в `/tmp/mb10-e2e-anom`, ускоренные окна `PULSE_INTERVAL_MS=2000`, `ONLINE_WINDOW_MS=15000`, `CHANGES_RATE_PER_MIN=60`, `ATTN_TRANSFER_STUCK_MIN=0.1`), основной стенд не затрагивается. Поддельные устройства делает `fakedev.mjs` (пара EC P-256, подписи как у приложения). Нужны Node ≥22 и `python3`; в CI шаг идёт в job `admin-web`.

```bash
scripts/e2e/anomaly-all.sh                       # все, кроме silent-phone
scripts/e2e/anomaly-all.sh anomaly-clock        # один
scripts/e2e/anomaly-all.sh --phones             # плюс silent-phone (нужен ./up.sh с эмуляторами)
```

| Сценарий | Провокация | Ожидаемая тревога |
|---|---|---|
| `anomaly-mass-silence` | 6 устройств на связи 15 с, затем молчат | `mass_silence` (срочная) |
| `anomaly-reject-spike` | 15 записей с чужой подписью | `reject_spike` (срочная, «подпись») |
| `anomaly-rate-limit` | 100 heartbeat с одного адреса | `rate_limited` |
| `anomaly-secret` | 5 запросов без кода игры (на сервере с `GAME_SECRET`) | `secret_denied` |
| `anomaly-duplicate-receive` | один `sourceRef` с `TRANSFER_IN` у двух игроков | `duplicate_receive` (срочная) |
| `anomaly-amount-mismatch` | списано 100, получено 300 | `transfer_amount_mismatch` (срочная); честная пара 50/50 тревоги не даёт |
| `anomaly-chain-break` | `oldValue` не равен прошлому `newValue` | `balance_chain_break` |
| `anomaly-unexplained-jump` | +5000 по причине `RAM_UPGRADE` | `balance_unexplained` (срочная); тот же рост за взлом не даёт |
| `anomaly-clock` | запись, датированная на 30 мин вперёд | `clock_skew` |
| `anomaly-stuck-transfer` | `TRANSFER_OUT` без пары; вариант с отменой | `transfer_stuck` (ровно один) |
| `anomaly-outlier` | 6 игроков по 3 взлома, у одного 40 | `player_outlier` |
| `anomaly-emission` | 55 с спокойной игры, потом 3 награды по 500 | `emission_spike` |
| `provision-conflict` | копия применённого QR персонажа | отказ `provision code already applied on another device`, игрока-копии на дашборде нет, тревога `provision_conflict` |
| `provision-reissue` | «Выдать заново» и применение нового кода | у старого ключа `replacedBy`, у нового `replaces`, остаток старого не входит в «Экономику» и «Обзор» |
| `provision-void-code` | код погашен повторной выдачей до применения | отказ `provision code is no longer valid (issued again)` |
| `session-reset` | сброс сессии на устройстве | позывной, фракция и баланс остаются в снимке, `sessionResetAt`, в «Обзоре» не считается |
| `anomaly-silent-phone` | настоящий эмулятор Bob уходит в авиарежим | `went_silent` (порог на стенде 45 с) |

После каждого сценария в `/tmp/mb10-e2e-anom-artifacts` (в CI — артефакт `anomaly-replay`) сохраняется вывод `GET /api/anomalies/replay` — по нему подбирают пороги `ANOM_*`. Проверять тревоги нужно по полю `kind`, а не по тексту.

`zz-provisioning.sh` (последним, разрушает состояние Alice) проверяет на настоящем приложении: QR, выданный самим сервером (`POST /api/provisions`), принимается; повторно не применяется; сброс сессии стирает игровые данные; при отказе сервера по коду (код уже применён другим телефоном) приложение показывает плашку и не зацикливает синхронизацию.

Сценарий `zz-honest-traffic.sh` в обычном `run-all.sh` после всех остальных проверяет, что честный трафик двух эмуляторов не породил тревог о подделке (`duplicate_receive`, `transfer_amount_mismatch`, `balance_unexplained`, `clock_skew`, `reject_spike`). Тревога `balance_chain_break` на стенде появляется всегда и ложной не считается: отладочные команды `--es balance N` меняют баланс без записи об изменении, поэтому цепочка на стенде рвётся (в игре так делает только мастер, а его правки детектор исключает).

**Порог `ATTN_SILENT_MIN` на стенде нельзя ставить меньше ~40 с**: телефон шлёт heartbeat раз в 30 с, при более коротком пороге честный телефон всё время будет «пропадать со связи».

## Устойчивость стенда

Красный сценарий должен значить «сломалось приложение или коллектор», а не «глюк эмулятора». Для этого в `lib.sh`:

- **Проверка живости экрана.** `dump_ui` убеждается, что дамп `uiautomator` содержит узлы. Упавший SystemUI, блокировка или чёрный экран дают пустой дамп, раньше это выглядело как «нужного текста нет».
- **Лестница восстановления** (`revive_screen`): разбудить и снять блокировку → перезапустить SystemUI → перезагрузить эмулятор (≈1 мин) и заново связать пиров. `REVIVE_FORCE_REBOOT=1` включает сразу последнюю ступень (для проверки самой лестницы).
- **Предполёт** (`preflight`, зовётся из `reset_ui` перед каждым сценарием в `run-all.sh` и в конце `up.sh`): устройство на связи, система загружена, экран не спит и отвечает. Выключить для отладки: `E2E_NO_PREFLIGHT=1`.
- **Пометка сбоя стенда.** Если экран так и не ожил, красная строка получает пометку `[сбой стенда: экран … не отвечает, не вина приложения]`.
- **Wi-Fi эмулятора** (`ensure_wifi_on`, `heal_host_reach`). Состояние Wi-Fi переживает перезапуск AVD. Приложение разрешает взлом только при подключённом Wi-Fi (`MeshLink.isOnline`, игровое правило), поэтому выключенный Wi-Fi краснит сценарии со взломом. `up.sh` включает Wi-Fi, только если он выключен (лишнее включение поверх работающего переподключает сеть). Обратная особенность эмулятора: приложение, привязанное к виртуальному Wi-Fi, иногда не достукивается до хоста `10.0.2.2`; `heal_host_reach` тогда выключает Wi-Fi у пострадавшего эмулятора, а сценарии, которым он нужен (`wifi-bind`, `breach()`), включают его обратно.
- **После холодного старта** `up.sh` до трёх раз перезапускает приложения, если `link.sh` не нашёл их порты (приложение бывает заморожено системой).

## Что ускоряет прогон

- **Ускоренные часы** (`DebugConfig.clockSpeed`): кулдаун контейнера 30 мин → 30 с, задержка сигнала СБ 2 мин → 2 с, TTL и агрегация — так же.
- **Растянутый таймер взлома** (`breachTimerFactor`): на медленном эмуляторе тапать сетку вручную не успеть.
- **Автосолвер** (`autoSolve`): сетка решается сама (`BreachAutoSolver`, с тестом).
- **Debug-команды** (`DebugQrReceiver`, только debug-сборка): создать персонажа, задать позывной/фракцию/RAM/баланс, выдать демона, сбросить кулдауны, создать и отменить перевод, подать QR без камеры.
- Анимации системы выключены, лишние системные окна («не отвечает») закрываются автоматически.

Все ручки живут только в debug-сборке (приёмник объявлен в `app/src/debug`), в release значения по умолчанию: часы реальные, автосолвер выключен.

## Сценарии (`scenarios/`)

Стенд одноразовый: `zz-provisioning` (последний) стирает Alice, у неё новый ключ и порт. Следующий `run-all.sh` — только после `./down.sh && ./up.sh`; без этого он откажется запускаться (метка `$E2E_DIR/stand_used`).

| Сценарий | Что проверяет |
|---|---|
| `slot-race.sh` | гонка за последний экземпляр слота: ровно один победитель, тираж на дашборде |
| `sec-alert.sh` | сигнал СБ доходит до владельца узла и считается на дашборде |
| `transfer-cancel.sh` | отмена недоставленного перевода + запрет отмены доставленного |
| `offline-sync.sh` | очередь синка копится без сервера и доезжает после его возвращения |
| `master-override.sh` | правка RAM и баланса с дашборда доходит до устройства |
| `announcement.sh` | объявление мастера доходит до телефона, показывается окном, после «Принято» дашборд видит доставку (`DEVICES=emulator-5554` — проверить только один эмулятор) |
| `game-secret.sh` | код игры на сервере: с неверным кодом записи копятся и не теряются, после исправления доходят. Работает только на стенде с кодом: `E2E_GAME_SECRET=строка ./up.sh`, иначе пропускается |
| `wrong-recipient.sh` | карточка платежа адресована конкретному получателю: чужую копию принять нельзя, повтор своей не зачисляется |
| `item-transfer.sh` | передача демона между игроками: отмена недоставленного возвращает предмет, доставленный отменить нельзя, принятие в чате, чек, без дублей |

Новый сценарий — скопировать любой, подключить `lib.sh`; полезные хелперы: `container`, `breach`, `q` (SQL к БД телефона), `api` (дашборд), `dbg`, `check`/`eq`, `wait_until`, `tap_text`.

Правило проверок: `dbg`, тап и сеть отрабатывают асинхронно, поэтому «действие; `sleep N`; разовое чтение» запрещено — оно читает данные до
того, как приложение их записало, и краснеет на медленном эмуляторе. Ожидаемый результат — `eq_wait <с> "описание" ожидаемое <команда>`
(или `check … wait_until`), значение из logcat — `await <с> <команда>`. Проверки «не изменилось / не появилось» ожиданием не доказать:
сначала дождаться свидетельства, что действие отработало (строка в logcat, число попыток), потом `eq`. Так же — значения, которые по пути
проходят через ожидаемое (баланс при серии переводов): не `eq_wait`, а ожидание конца серии и потом `eq`.

## Демо-ролик для стейкхолдеров

`scripts/e2e/seed.sh` (после `up.sh`) быстро, без тапов по экрану, готовит данные для показа: Alice и Bob с деньгами и демонами, переписка (личная и фракционная), сведённый перевод на 100 €$ и второй на 40 €$, который ждёт вашего «Принять» на телефоне Alice, узел и объявление на дашборде. Повторный запуск на том же стенде даст дубли — поднимайте `up.sh` заново. Если Alice не видна на дашборде, скрипт сам выключает её виртуальный Wi-Fi (особенность эмулятора: привязка к виртуальному Wi-Fi отрезает хост).

`scripts/e2e/demo.sh` записывает ≈4-минутный ролик экрана Alice (эмулятор A): сделка с Bob в чате, перевод 100 эдди, передача демона-«блэкаута», пошаговый
взлом узла «Арасака-404» с репликами ICE и демоном-майнером, зашифрованный шард (набор символов → мини-игра дешифратором → текст), пересылка шарда,
оплата 300 эдди и сообщение от неизвестного. Нужны `ffmpeg` (`brew install ffmpeg`) и **свежий** стенд (`up.sh`): сюжет двигает предметы и деньги.

```bash
scripts/e2e/up.sh && scripts/e2e/demo.sh     # результат: /tmp/mb10-e2e/demo/demo.mp4 и demo.gif
RECOMPOSE=1 scripts/e2e/demo.sh              # пересобрать ролик из уже записанных кусков (скорости сцен — speed_of в скрипте)
TARGET=120 RECOMPOSE=1 scripts/e2e/demo.sh   # ужать до ~2 минут (по умолчанию сцены идут почти в реальном темпе, ≈4 мин)
```

Каждая сцена пишется отдельным куском (`screenrecord` ограничен 180 с), ffmpeg склеивает их с разной скоростью и держит последний кадр куска
(`screenrecord` не пишет кадры без изменений экрана). Сообщения Bob и Alice отправляются debug-командами (`say`, `pay`, `give`, `sayas`), потому что
`adb input text` не умеет кириллицу.

## Видео веб-интерфейса мастера

`scripts/e2e/dashboard-demo.mjs` записывает ≈2-минутный обход дашборда с подписями по сценам приложения: обзор с живой лентой событий, игроки,
история Alice и Bob (переводы, передача демона и шарда, расшифровка), узел «Арасака-404», реестр тиражей, переводы, мастерская. Запускать сразу
после `demo.sh` на том же стенде: данные для подписей берутся из API сервера. Без зависимостей: Node ≥ 22 (встроенные WebSocket и fetch),
Google Chrome (headless, управление по протоколу DevTools; кадры screencast приходят только при изменении страницы), `ffmpeg`.

```bash
node scripts/e2e/dashboard-demo.mjs          # результат: /tmp/mb10-e2e/dash/dashboard.mp4
```

## Ограничения

Пиры на Mac связываются `DEBUG_PEER` + `emu redir` (`link.sh`; после перезапуска приложения порты меняются, запустить `link.sh` заново): mDNS между двумя AVD на macOS не ходит вовсе. На CI (Linux) mDNS ходит (`peer.found … addr=10.0.2.16/17`), но стенд проверяет логику приложения, а не mDNS эмуляторов: `e2e.yml` по умолчанию тоже со статическими пирами; только NSD — ручной запуск со снятым `static_peers` (`E2E_STATIC_PEERS=0`, `link.sh` лишь ждёт, что эмуляторы нашли друг друга). NSD проверяется JVM-тестами и на телефонах. См. A4 в `docs/refactor-plan.md`. Камера заменена `DEBUG_QR` (нужен открытый экран «Кибердека»). Звук звонков, реальный Wi-Fi и нагрузка на слабые телефоны — только на физических устройствах.


## Как ускорить и не ломать прогоны (практики)
- **Не гасите эмуляторы между прогонами.** Холодный старт двух эмуляторов ≈ 1,5 мин; `./up.sh --no-build` при уже запущенных эмуляторах пересоздаёт только приложения и сервер (≈ 1 мин). Снимки AVD (`snapshot load/save`) на этой связке (Apple Silicon, headless) не работают: «Error -22 while loading VM state».
- **Полный `run-all.sh` ≈ 4 мин** на чистом стенде; в конце печатается время каждого сценария. Если прогон идёт заметно дольше, значит сценарии ждут таймауты красных проверок — смотрите на первый красный, а не на общее время.
- **Не запускайте `run-all.sh` через `| tail`**: сервер, поднятый сценарием `offline-sync`, наследует канал и не даёт команде завершиться. Пишите вывод в файл (`> /tmp/ra.log 2>&1 < /dev/null`).
- **Перед каждым сценарием `run-all.sh` вызывает `reset_ui`**: закрывает «Сообщение от мастера» и возвращает приложение на передний план — иначе окно, оставшееся от прошлого сценария, перехватывает тапы и красит все следующие.
- **Порт приложения** берётся у самого приложения (`DEBUG_CONFIG --es port '?'`), а не из logcat: сценарии делают `logcat -c`, и после этого `link.sh` раньше не находил порт.
- **Ручные эксперименты грязнят стенд** (баланс, контейнеры, незавершённый взлом): перед прогоном сценариев — `./up.sh --no-build`.
- `double-spend.sh` проверяет гонку «двойной тап» (8 одновременных переводов при балансе, хватающем на три) — `pay ... --ei burst N` в debug-приёмнике.

## Журналы приложения в стенде

Приложение пишет подробный журнал (`docs/live-test-plan.md`, раздел 2). Стенд его использует:

- `journal_count <serial> <подстрока>` — сколько строк журнала содержит подстроку; сценарии ждут по журналу («карточка дошла до Bob»), а не фиксированные секунды (`item-transfer.sh`);
- при красном сценарии `finish` сохраняет в `$E2E_DIR/journals/`: журналы обоих телефонов, дамп экрана и скриншот каждого (`<сценарий>-…`); CI кладёт эту папку в артефакты `e2e-artifacts`;
- `open_chat` проверяет, что тред открылся, и повторяет тап: строка списка сдвигается, когда в этот момент приходит сообщение.
- всё, что стенд ищет в выводе приложения (события журнала, строки `MB10DBG`, теги `logcat -s`), перечислено в `log-contract.tsv`;
  unit-тест приложения `LogContractTest` сверяет его с кодом — переименование события ломает `./gradlew verifyPaparazziDebug`, а не прогон стенда.
